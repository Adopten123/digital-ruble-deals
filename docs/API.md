# Контракт API первого MVP «ПоАкту»

Статус: проектный контракт до начала реализации. Маршруты ещё не реализованы. Расчёты и ЭДО эмулируются; это не API Банка России или конкретного оператора ЭДО.

## 1. Общие правила

- Браузерный API — `/api/v1`, JSON UTF-8; исключения — загрузка PDF, просмотр и экспорт. Frontend и API работают с одного origin.
- **Изменение предыдущего черновика:** все денежные поля, включая `amount_kopecks`, передаются в JSON **десятичными строками**, например `"30000000"`. В Go и PostgreSQL это целые `int64` / `BIGINT` копейки. JSON-числа, float, экспоненциальная запись, знак `+`, дроби и ведущие нули запрещены. `"0"` допустим для остатков; суммы сделок и зачислений положительны. Верхняя граница — `9223372036854775807`; арифметическое переполнение отклоняется.
- Валюта — `RUB`. ID — непрозрачные строки; версии — положительные целые числа; время — RFC 3339 UTC. Сроки проверяются по серверному времени.
- Неизвестные поля команд, неверные типы и несколько JSON-значений в теле отклоняются. Субъект, его организация и роль определяются сессией, а не телом запроса.
- Чужой ресурс, включая сделку, акт, уведомление и счёт, возвращает `404`; запрещённое действие с доступным ресурсом — `403`.
- Маршрута выплаты в обход условий нет. Любое списание учитывает активные резервы.
- Списки: `{items: [], next_cursor: null}`; `limit` по умолчанию 20, максимум 100; `cursor` непрозрачный. Сортировка по времени создания и ID от новых к старым. Поиск, счётчики, фильтры и экспорт ограничены доступными ресурсами.

## 2. Пользователь, организация и сессия

Регистрация создаёт пользователя, **новую учебную организацию**, членство `ORG_OWNER` и счёт с нулевым остатком. В MVP у пользователя одна организация. Название / реквизиты чужой организации не дают членства. Регистрация не подтверждает реальные полномочия.

`ORG_OWNER` действует за свою организацию. Заказчик и исполнитель — роли организации в конкретной сделке, не роли аккаунта. Организации сторон различаются. Системный `DEMO_OPERATOR` создаётся только начальным наполнением: он зачисляет тестовые средства, запускает сценарии событий и читает тестовый аудит, но не согласует условия и не подписывает за стороны, не снимает спор и не обходит проверки выплаты. Саморегистрации оператора нет.

Сессия — случайный токен не менее 256 бит; в БД только его хеш. Cookie `pa_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 24 часа от выдачи, `Secure` при HTTPS. Локальный HTTP допускается только в явно заданном DEMO_MODE. Вход меняет идентификатор сессии; выход отзывает её на сервере. Пароли хранятся как Argon2id-хеши. Вход и регистрация ограничиваются по частоте; ошибка входа не раскрывает существование email. Пароль — 12–128 символов.

Все браузерные изменяющие запросы, включая регистрацию, вход и выход, требуют `X-CSRF-Token` и проверки origin. `GET /auth/csrf` выдаёт токен, связанный с защищённой cookie и при наличии сессией. Получение токена разрешено до входа и не создаёт пользовательскую сессию; после входа / регистрации токен обновляется. Внутренний маршрут ЭДО не использует браузерные cookie.

| Метод и путь относительно `/api/v1` | Тело / результат | Доступ |
|---|---|---|
| `GET /auth/csrf` | `{csrf_token}` | Без сессии / пользователь |
| `POST /auth/register` | `{email, password, organisation: {name, kind}}`; `kind`: `COMPANY` или `IP`; `201`, пользователь, организация и cookie сессии | Без сессии |
| `POST /auth/login` | `{email, password}`; `200`, пользователь, организация и cookie сессии | Без сессии |
| `POST /auth/logout` | Пустое тело; `204`, отзыв и очистка cookie | Пользователь |
| `GET /auth/me` | `{user: {id, email, system_role}, organisation: {id, name, kind, role}, session_expires_at}`; организация оператора может быть `null` | Пользователь |
| `GET /organisations` | `q`, `limit`, `cursor`; только `id`, `name`, `kind`, `is_demo` | Пользователь |
| `GET /organisations/me` | Своя организация и `{account: {id, currency, total_kopecks, reserved_kopecks, available_kopecks}}` | `ORG_OWNER` |

Названия не уникальны: контрагент выбирается по ID. Справочник не раскрывает email, состав участников, остатки, сделки и документы организаций.

## 3. Версии и состояния сделки

Основной путь: `DRAFT → AGREED → FUNDED → READY_TO_SETTLE → SETTLED`.

| Состояние | Значение |
|---|---|
| `DRAFT` | Нет двух согласований текущих условий и акта; заказчик может редактировать |
| `AGREED` | Обе стороны согласовали одну версию условий и точные байты PDF; возможен резерв |
| `FUNDED` | Полная сумма зарезервирована; разрешены тестовые подписи |
| `READY_TO_SETTLE` | Сохранены две подписи; ожидается проверка события |
| `SETTLED` | Завершён единственный расчёт |
| `DISPUTED` | Спор блокирует автоматическую выплату |
| `CANCELLATION_PENDING` | Запрошена согласованная отмена; автоматическая выплата заблокирована |
| `REVIEW_REQUIRED` | Нужен разбор исключения; нет автоматической выплаты / освобождения резерва |
| `CANCELLED` | Согласованная отмена без созданного резерва |
| `REFUNDED` | По согласованной отмене освобождён резерв; это локальное освобождение, не банковский обратный перевод |

Изменение условий или активного документа увеличивает `deal_version`, сбрасывает действующие согласования и переводит в `DRAFT`; исторические факты согласий / подписей сохраняются. `PATCH` условий разрешён только в `DRAFT`; документ можно создавать / заменять в `DRAFT` и `AGREED` до первого резерва. После резерва условия и PDF неизменяемы.

Согласия, подписи, резерв и смена статуса сами по себе не увеличивают `deal_version`. Внутренний технический `row_version` не подменяет её и не вводит новый обязательный параметр API. `expected_version` в PATCH — ожидаемая версия условий. Модель хранения и транзакций — в [DATA_MODEL.md](DATA_MODEL.md).

Фактическое изменение условий через PATCH снимает активную привязку PDF для новой версии. Прежний файл остаётся в истории; до согласования требуется заново загрузить / сгенерировать акт. Без актуального документа — DOCUMENT_REQUIRED. Проверка загруженного PDF не является автоматической смысловой сверкой его текста с условиями; стороны явно согласуют точные байты и контекст сделки.

Создание сделки не считается согласием автора: обе стороны явно принимают одну версию. Согласие связывает `deal_version`, документ, его версию и SHA-256. Без окончательного PDF согласование и резерв невозможны.

`deadline_at` — согласованный предельный срок автоматического исполнения. Наступление срока переводит активную незавершённую сделку в `REVIEW_REQUIRED`, без автоматической выплаты / возврата. Активный запрос отмены сохраняется и может быть завершён; срок остаётся блокировкой выплаты. Проверка срока есть внутри денежных транзакций, независимо от фоновой задачи. Возобновления выплаты из `DISPUTED` / `REVIEW_REQUIRED` в MVP нет: можно согласовать отмену и создать новую сделку. Срок не доказывает отсутствие исполнения работ.

Объект сделки: `id`, `deal_version`, `status`, `customer_party_id`, `supplier_party_id`, `title`, `description`, `amount_kopecks`, `currency`, `deadline_at`, текущий документ, согласия сторон, подписи, резерв данной сделки, `payment_id`, активный спор / запрос отмены, даты создания / изменения. Чужих остатков и других сделок в нём нет.

## 4. Сделки, резерв, спор и отмена

Команды этого раздела требуют `Idempotency-Key`. Версия проверяется под блокировкой сделки.

| Метод и путь относительно `/api/v1` | Тело / действие | Доступ |
|---|---|---|
| `POST /deals` | `{supplier_party_id, title, description, amount_kopecks, currency, deadline_at}`; описание макета в `description`, без отдельной загрузки; заказчик из сессии; `201`, `DRAFT`, версия 1 | `ORG_OWNER` |
| `GET /deals` | `q`, `status`, `role=customer\|supplier`, `created_from`, `created_to`, `limit`, `cursor`; поиск по ID / названию сделки и ID / названию контрагента | Участник |
| `GET /deals/{id}` | Объект сделки | Участник |
| `PATCH /deals/{id}` | `{expected_version, ...изменяемые поля создания}`; только `DRAFT`, ответ — новая версия | Заказчик |
| `POST /deals/{id}/agree` | `{deal_version, document_id, document_version, document_sha256}`; согласие своей стороны, второе — `AGREED` | Участник |
| `POST /deals/{id}/reserve` | `{deal_version}`; резерв всей суммы из `AGREED`; `201`, резерв и сделка | Заказчик |
| `POST /deals/{id}/disputes` | `{deal_version, reason}`; запись спора и блокировка выплаты | Участник |
| `POST /deals/{id}/cancellation-requests` | `{deal_version, reason}`; запрос и одно согласие инициатора; `201`, `CANCELLATION_PENDING` | Участник |
| `POST /deals/{id}/cancellation-requests/{request_id}/accept` | `{deal_version}`; согласие другой стороны, затем однократная отмена / освобождение | Другая сторона |
| `POST /deals/{id}/cancellation-requests/{request_id}/reject` | `{deal_version, reason}`; запрос закрывается, `REVIEW_REQUIRED`, без возобновления выплаты | Другая сторона |
| `GET /deals/{id}/audit` | `type`, `from`, `to`, `limit`, `cursor`; история | Участник |
| `GET /deals/{id}/audit/export` | `format=csv\|json`, `type`, `from`, `to`; файл истории сделки | Участник |

`available_kopecks = total_kopecks − reserved_kopecks`. Резерв не уменьшает общий остаток. Выплата уменьшает общий остаток заказчика и активный резерв и увеличивает общий остаток исполнителя на ту же сумму. Отмена освобождает резерв без зачисления исполнителю. Счета, резерв, проводки, состояние, успешный результат команды и outbox изменяются атомарно.

Спор разрешён из `AGREED`, `FUNDED`, `READY_TO_SETTLE`, `REVIEW_REQUIRED`. В `CANCELLATION_PENDING` он фиксируется без потери запроса отмены; выплата остаётся заблокирована. После `SETTLED`, `CANCELLED`, `REFUNDED` команда отклоняется; автоматического возврата нет.

Отмену можно запросить в любом нетерминальном состоянии. Есть не более одного активного запроса; повтор инициатора не создаёт согласие второй стороны. Два действия одной организации не заменяют две организации. После отказа новый запрос имеет новый ID, старые согласия не переносятся. Завершение без резерва даёт `CANCELLED`, с освобождением активного резерва — `REFUNDED`. `SETTLED`, `CANCELLED`, `REFUNDED` терминальны.

Спор, отмена и выплата сериализуются одной дисциплиной блокировок сделки / резерва / счетов. Если блокировка выплаты зафиксирована раньше, расчёт запрещён. Если расчёт уже зафиксирован, следующая блокирующая команда получает конфликт и не меняет деньги. Клиентское время не определяет победителя гонки.

## 5. PDF и тестовые подписи

| Метод и путь относительно `/api/v1` | Тело / действие | Доступ |
|---|---|---|
| `POST /deals/{id}/documents` | `multipart/form-data`: `expected_deal_version`, `file`; точные байты PDF, SHA-256; `201`, документ и новая версия сделки | Заказчик |
| `POST /deals/{id}/documents/generate` | `{expected_deal_version, template_id: "printing-acceptance-v1"}`; готовый учебный акт по условиям, те же правила версии / хеша | Заказчик |
| `GET /documents/{id}` | Метаданные; `version` необязателен, иначе текущая | Участник сделки |
| `GET /documents/{id}/view` | Обязательный `version`; PDF для безопасного просмотра | Участник сделки |
| `GET /documents/{id}/download` | Обязательный `version`; те же байты, `Content-Disposition: attachment` | Участник сделки |
| `POST /documents/{id}/sign` | `{deal_version, document_version, document_sha256}`; тестовая подпись своей организации | Участник сделки |

Изменяющие запросы требуют `Idempotency-Key`. Максимум PDF — **5 MiB**. Проверяются расширение, MIME, сигнатура и возможность разбора; активное содержимое, неподдерживаемые и зашифрованные файлы отклоняются. Имя не используется как путь. Просмотр авторизуется и не исполняет HTML / сценарии; публичных URL хранилища нет.

`document_id` обозначает документ сделки, `document_version` растёт монотонно; каждая версия неизменяема и имеет SHA-256 точных байтов. Новая версия сбрасывает согласования сделки. Старые версии доступны участникам в истории, но не для новых подписей / выплаты.

Подписывать можно только в `FUNDED` / `READY_TO_SETTLE`, текущие согласованные версии до срока, без блокирующего состояния. Факт подписи содержит `signature_id`, пользователя и организацию, сделку и её версию, документ и его версию/хеш, время. Уникальность — организация + версия сделки + версия документа. Повтор возвращает существующий факт; подстановка чужой организации невозможна.

Первая подпись не меняет деньги. Вторая переводит сделку в `READY_TO_SETTLE` и транзакционно создаёт outbox-задание имитатору ЭДО. Это тестовые действия пользователей; HMAC источника не является подписью сторон или квалифицированной электронной подписью.

Основание outbox фиксирует устойчивые event_id, время и привязки события в той же транзакции второй подписи. Смысл события не строится заново из изменяемой карточки. Исходные байты тела сохраняются до первой доставки; повторы меняют только транспортные timestamp / HMAC.

## 6. История, уведомления и оператор

| Метод и путь относительно `/api/v1` | Действие | Доступ |
|---|---|---|
| `GET /notifications` | `unread`, `limit`, `cursor`; уведомления текущему пользователю | Пользователь |
| `POST /notifications/{id}/read` | Пустое тело, идемпотентная отметка, `204` | Получатель |
| `GET /demo/accounts` | Учебные счета, `q` по ID / названию организации, пагинация | `DEMO_OPERATOR` |
| `POST /demo/accounts/{id}/credits` | `{amount_kopecks, reason}` и `Idempotency-Key`; положительное тестовое зачисление с проводкой / аудитом | `DEMO_OPERATOR` |
| `POST /demo/accounts/{id}/debits` | `{amount_kopecks, reason}` и `Idempotency-Key`; служебное списание на системный учебный счёт через общий реестр и блокировки всех активных резервов | `DEMO_OPERATOR` |
| `POST /demo/edo/events` | `{deal_id, template, replay_event_id?}` и `Idempotency-Key`; сервер формирует / доставляет событие; `202`, `{job_id, event_id}` | `DEMO_OPERATOR` |
| `GET /demo/edo/events/{event_id}` | Метаданные, статус доставки и результат обработки (`http_status`, `result` / `error_code`) без секретов | `DEMO_OPERATOR` |
| `GET /demo/audit` | `deal_id`, `type`, `from`, `to`, `limit`, `cursor`; тестовый аудит | `DEMO_OPERATOR` |

Шаблоны: `valid`, `single_signature`, `wrong_amount`, `wrong_parties`, `wrong_document`, `wrong_document_version`, `wrong_document_hash`, `wrong_deal_version`, `invalid_hmac`, `replay`, `same_id_different_body`. Для `replay` обязателен `replay_event_id`: сохраняются тело / ID исходного события, транспортная подпись формируется заново. `same_id_different_body` проверяет конфликт дедупликации. `valid` использует только сохранённые подписи; оператор не создаёт подписи за стороны. Произвольное подписание тел и HMAC-секрет браузеру недоступны.

Служебное списание нужно для проверки конкурирующих денежных операций: оно не является выплатой сделки и не погашает её резерв. Проверка доступного остатка, блокировки счетов / резервов, проводки и идемпотентный результат выполняются одной транзакцией через тот же реестр. Сумма положительна, получатель — фиксированный системный учебный счёт, а не произвольный контрагент; отрицательный остаток и расходование активного резерва запрещены.

Уведомления внутри приложения: новая сделка, согласование, резерв, подписи, расчёт, спор, запрос / отказ / завершение отмены, переход в проверку. Создаются через outbox после доменной транзакции и не дублируются при повторной доставке. После первой подписи создаются только факт подписи и уведомление; расчётное событие ЭДО появляется после второй. Почта / внешние мессенджеры не обязательны.

Аудит содержит действие, ресурс / версию, пользователя / источник, серверное время, результат, request ID; не содержит паролей, токенов, HMAC-секрета и байтов PDF. Экспорт соответствует правам и фильтрам экранной истории; CSV UTF-8 защищает значения от выполнения как формул. Уведомления и аудит не заменяют денежные проводки.

Начальное наполнение: разные аккаунты заказчика, исполнителя и оператора; остатки заказчика `"50000000"`, исполнителя `"0"`; начальное зачисление имеет проводку. Новые регистрации начинают с `"0"`. Пересоздание демонстрации — отдельная CLI-команда: новый изолированный учебный сценарий с новыми ID и явными проводками начального зачисления. Старые пользователи, сценарии, история и проводки сохраняются. HTTP reset и прямой HTTP-платёж отсутствуют; панель может показывать инструкцию CLI. Точная команда фиксируется при реализации в инструкции запуска.

## 7. Идемпотентность

Ключ обязателен для доменных изменяющих команд. Авторизация и отметка прочтения используют собственную семантику и не требуют `Idempotency-Key`. Ключ — непрозрачная строка длиной 16–128 символов.

Область: **организация / оператор + операция + ресурс + ключ**; у создания ресурс — коллекция. Хеш нормализованного тела учитывает значимые поля; у загрузки — поля и точные байты файла, но не случайную multipart-границу. То же тело возвращает сохранённые HTTP-статус / результат; другой хеш — `409 IDEMPOTENCY_CONFLICT`. Авторизация проверяется и при повторе.

Одновременные одинаковые команды сериализуются уникальным ограничением. Доменное изменение и успешный результат команды фиксируются одной транзакцией. Временная ошибка инфраструктуры допускает повтор тем же ключом; терминальный результат валидации сохраняется последовательно. В MVP записи ключей не очищаются автоматически.

Ограничения БД независимо от ключа: один активный резерв на сделку, одна подпись организации для конкретных версий, не более одного расчёта сделки, взаимоисключение выплаты и освобождения резерва. Новый ключ / ID события не разрешает повторную выплату.

## 8. Внутреннее событие ЭДО

`POST /internal/edo/events` — отдельный внутренний маршрут без `/api/v1`, без cookie-сессии / CSRF; не браузерный маршрут. Имитатор обращается к нему внутри контура. Максимум тела — 64 KiB.

Заголовки: `X-EDO-Key-ID`, `X-EDO-Timestamp` (Unix seconds), `X-EDO-Signature: sha256=<lowercase hex>`. HMAC-SHA256 считается над UTF-8 `timestamp + "\n" + raw_body`, сравнение постоянного времени. Отклонение транспортного времени — не более 5 минут; `source` соответствует ключу. Неверный ключ, подпись / время — `403 EDO_SOURCE_INVALID`. Секрет только на сервере. Старое тело повторяется с актуальным подписанным транспортным временем, без изменения `occurred_at`.

```json
{
  "schema_version": 1,
  "event_id": "edo-demo-001",
  "source": "edo-emulator",
  "event_type": "document.accepted_by_both",
  "deal_id": "deal-demo-001",
  "deal_version": 1,
  "document_id": "document-demo-001",
  "document_version": 1,
  "document_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "customer_party_id": "company-customer-demo",
  "supplier_party_id": "company-supplier-demo",
  "amount_kopecks": "30000000",
  "currency": "RUB",
  "signed_by_customer": true,
  "signed_by_supplier": true,
  "customer_signature_id": "signature-customer-demo",
  "supplier_signature_id": "signature-supplier-demo",
  "occurred_at": "2026-10-19T09:00:00Z"
}
```

Хеш в примере — заполнитель; в событии нужен хеш точных согласованных байтов. Все поля присутствуют обязательно. `customer_signature_id` / `supplier_signature_id` должны быть непустыми ID сохранённых фактов, когда соответствующий `signed_by_customer` / `signed_by_supplier` равен `true`; при `false` соответствующее поле обязательно имеет значение `null`. Одних булевых флагов недостаточно: ссылки сверяются с сохранёнными фактами, сторонами и версиями. Шаблон `single_signature` передаёт одну действительную подпись, второй флаг `false` и второй ID `null`; результат — `422 SIGNATURES_MISSING`, без выплаты.

Обработка:

1. Проверить размер, транспортную подпись / источник, схему / типы. Неаутентифицированные данные не создают доменное событие.
2. Долговременно сохранить `source + event_id` и SHA-256 исходного тела в inbox. Прежнее тело возвращает прежний результат; другое — `409 EVENT_ID_CONFLICT`. Транспортные заголовки в хеш тела не входят.
3. Сопоставить сделку / версию, стороны, сумму / валюту, документ / версию / хеш, две сохранённые подписи. Одиночная подпись или несовпадение — `422`, без выплаты.
4. В транзакции заблокировать сделку, резерв и счета в устойчивом порядке; повторить проверки согласований, срока, состояния, резерва и отсутствия спора / отмены / проверки. Событие до резерва или других условий отклоняется; повтор сохранённого отказа позднее не запускает выплату.
5. При выполнении всех условий атомарно создать единственный расчёт и проводки, погасить резерв, установить `SETTLED`, записать результат inbox и outbox. Частичный успех невозможен.

Успех — `200 {event_id, result: "settled", deal_id, payment_id}`; повтор возвращает сохранённый ответ. Новое валидное событие с другим ID для исполненной сделки — `200`, `result: "already_settled"` и прежний `payment_id`. Остальные привязки всё равно проверяются. Семантический отказ сохраняется с кодом. При `503` источник повторяет доставку, а не считает выплату отсутствующей.

Противоречивое / позднее событие не отменяет исполненный расчёт. Исключение отражается в аудите; до исполнения применяется предусмотренная проверка / блокировка без автоматического арбитража.

## 9. Ошибки

```json
{
  "error": {
    "code": "INSUFFICIENT_AVAILABLE_FUNDS",
    "message": "Недостаточно доступных тестовых средств",
    "details": {"required_kopecks": "30000000", "available_kopecks": "20000000"}
  },
  "request_id": "request-demo-001"
}
```

| HTTP | Стабильные коды |
|---|---|
| `400` | `INVALID_REQUEST`, `INVALID_AMOUNT`, `IDEMPOTENCY_KEY_REQUIRED` |
| `401` | `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `SESSION_EXPIRED` |
| `403` | `FORBIDDEN`, `CSRF_INVALID`, `EDO_SOURCE_INVALID` |
| `404` | `RESOURCE_NOT_FOUND`, включая чужие ресурсы |
| `409` | `EMAIL_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `EVENT_ID_CONFLICT`, `VERSION_CONFLICT`, `INVALID_STATE`, `CANCELLATION_SELF_APPROVAL` |
| `413` | `PAYLOAD_TOO_LARGE` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `422` | `INSUFFICIENT_AVAILABLE_FUNDS`, `CONSENTS_MISSING`, `DOCUMENT_REQUIRED`, `INVALID_PDF`, `EVENT_BINDING_MISMATCH`, `SIGNATURES_MISSING`, `DEADLINE_PASSED`, `SETTLEMENT_BLOCKED`, `AMOUNT_OVERFLOW` |
| `429` | `RATE_LIMITED` |
| `500` / `503` | `INTERNAL_ERROR` / `TEMPORARILY_UNAVAILABLE` |

`details` необязателен и содержит только разрешённые сведения. Не раскрываются SQL, стек, секреты, чужие email, остатки и существование чужого документа. Клиент обрабатывает `code`, не текст `message`. Таймаут соединения не доказывает отсутствие исполнения: нужно прочитать сделку или повторить исходную команду с тем же ключом.
