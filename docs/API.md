# Контракт API первого MVP «ПоАкту»

Статус на 22 октября: реализованы 24 операции — auth / organisations, `/healthz` / `/readyz`, создание / список / карточка сделки, изменение черновика, версии приватного PDF, два согласия, возврат на доработку и резерв всей суммы. Оператор может читать клиентские учебные счета, пополнять их и выполнять служебные списания с учётом резервов. Реализованы DRAFT, AGREED, FUNDED и вычисляемый при наступлении срока REVIEW_REQUIRED. Тестовые подписи, выплаты, ЭДО, споры / согласованная отмена, уведомления, экспорт и независимый контроль A19 остаются проектом. Это не API Банка России или конкретного оператора ЭДО. Точный контракт действующего сервера — в [справочнике API](api/README.md) и [OpenAPI 3.0.3](api/openapi.json); Swagger UI доступен на `/api-docs/` web-приложения. Запуск и проверки — в [RUNNING.md](RUNNING.md).

## 1. Общие правила

- Браузерный API — `/api/v1`, JSON UTF-8; исключения — загрузка PDF, просмотр и экспорт. Frontend и API работают с одного origin.
- **Изменение предыдущего черновика:** все денежные поля, включая `amount_kopecks`, передаются в JSON **десятичными строками**, например `"30000000"`. В Go и PostgreSQL это целые `int64` / `BIGINT` копейки. JSON-числа, float, экспоненциальная запись, знак `+`, дроби и ведущие нули запрещены. `"0"` допустим для остатков; суммы сделок и зачислений положительны. Верхняя граница — `9223372036854775807`; арифметическое переполнение отклоняется.
- Валюта — `RUB`. ID — непрозрачные строки; версии — положительные целые числа; время — RFC 3339 UTC. Сроки проверяются по серверному времени.
- Неизвестные поля команд, неверные типы и несколько JSON-значений в теле отклоняются. Субъект, его организация и роль определяются сессией, а не телом запроса.
- Чужой ресурс, включая сделку, акт, уведомление и счёт, возвращает `404`; запрещённое действие с доступным ресурсом — `403`.
- Маршрута выплаты в обход условий нет. Любое списание учитывает активные резервы.
- Списки: `{items: [], next_cursor: null}`; `limit` по умолчанию 20, максимум 100; `cursor` непрозрачный. Сортировка по времени создания и ID от новых к старым. Поиск, счётчики, фильтры и экспорт ограничены доступными ресурсами.

## 2. Пользователь, организация и сессия

Регистрация создаёт пользователя, **новую учебную организацию**, членство `ORG_OWNER` и счёт с нулевым остатком. В MVP у пользователя одна организация. Название / реквизиты чужой организации не дают членства. Регистрация не подтверждает реальные полномочия.

`ORG_OWNER` действует за свою организацию. Заказчик и исполнитель — роли организации в конкретной сделке, не роли аккаунта. Организации сторон различаются. Системный `DEMO_OPERATOR` создаётся только начальным наполнением: сейчас он читает клиентские учебные счета, зачисляет тестовые средства и выполняет служебные списания. Сценарии ЭДО / чтение аудита — будущие возможности. Оператор не согласует условия, не резервирует и не подписывает за стороны, не снимает спор и не обходит проверки выплаты. Саморегистрации оператора нет.

Сессия — случайный токен не менее 256 бит; в БД только его хеш. Cookie `pa_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 24 часа от выдачи, `Secure` при HTTPS. Локальный HTTP допускается только в явно заданном DEMO_MODE. Вход меняет идентификатор сессии; выход отзывает её на сервере. Пароли хранятся как Argon2id-хеши. Вход и регистрация ограничиваются по частоте; ошибка входа не раскрывает существование email. Пароль — 12–128 символов.

Все браузерные изменяющие запросы, включая регистрацию, вход и выход, требуют `X-CSRF-Token` и проверки origin. `GET /auth/csrf` выдаёт токен, связанный с защищённой cookie и при наличии сессией. Получение токена разрешено до входа и не создаёт пользовательскую сессию; после входа / регистрации токен обновляется. Внутренний маршрут ЭДО не использует браузерные cookie.

Кабинет также передаёт `X-Expected-User-ID` в защищённых чтениях, изменяющих командах сделок / оператора и выходе. Это необязательное для самостоятельных API-клиентов предусловие отображаемого аккаунта: сервер сравнивает его с пользователем действующей сессии и при несовпадении возвращает `409 SESSION_CHANGED` до выполнения обработчика. Заголовок не назначает субъект или права. Он предотвращает выполнение команды от нового аккаунта после смены общей cookie в другой вкладке. Клиент опускает предусловие при обнаружении сессии через `GET /auth/me`, login / register и получении CSRF; если передать его в `/auth/me`, общий middleware также выполнит сравнение. При конфликте интерфейс перечитывает сессию и показывает текущую организацию; автоматически повторять команду запрещено. Сохранённая команда остаётся в sessionStorage исходной организации с прежним ключом и телом.

| Метод и путь относительно `/api/v1` | Тело / результат | Доступ |
|---|---|---|
| `GET /auth/csrf` | `{csrf_token}` | Без сессии / пользователь |
| `POST /auth/register` | `{email, password, organisation: {name, kind}}`; `kind`: `COMPANY` или `IP`; `201`, пользователь, организация, `session_expires_at`, новый `csrf_token` и cookie сессии | Без сессии |
| `POST /auth/login` | `{email, password}`; `200`, пользователь, организация, `session_expires_at`, новый `csrf_token` и cookie сессии | Без сессии |
| `POST /auth/logout` | Пустое тело; `204`, отзыв и очистка cookie | Пользователь |
| `GET /auth/me` | `{user: {id, email, system_role}, organisation: {id, name, kind, role}, session_expires_at}`; организация оператора может быть `null` | Пользователь |
| `GET /organisations` | `q`, `limit`, `cursor`; только `id`, `name`, `kind`, `is_demo` | Пользователь |
| `GET /organisations/me` | Своя организация и `{account: {id, currency, total_kopecks, reserved_kopecks, available_kopecks}}` | `ORG_OWNER` |

Названия не уникальны: контрагент выбирается по ID. Справочник не раскрывает email, состав участников, остатки, сделки и документы организаций.

## 3. Версии и состояния сделки

Основной путь: `DRAFT → AGREED → FUNDED → READY_TO_SETTLE → SETTLED`.

Матрица действий, возврат на доработку и приоритет блокировок — в [STATE_MACHINE.md](STATE_MACHINE.md). Сейчас реализованы DRAFT → AGREED → FUNDED и возврат AGREED → DRAFT до первого резерва; при истечении срока чтение возвращает REVIEW_REQUIRED без освобождения средств. Остальные переходы таблицы — проектный контракт следующих этапов.

| Состояние | Значение |
|---|---|
| `DRAFT` | Нет двух согласований текущих условий и акта; заказчик может редактировать |
| `AGREED` | Обе стороны согласовали одну версию условий и точные байты PDF; возможен резерв |
| `FUNDED` | Полная сумма зарезервирована; тестовые подписи будут следующим этапом |
| `READY_TO_SETTLE` | Сохранены две подписи; ожидается проверка события |
| `SETTLED` | Завершён единственный расчёт |
| `DISPUTED` | Спор блокирует автоматическую выплату |
| `CANCELLATION_PENDING` | Запрошена согласованная отмена; автоматическая выплата заблокирована |
| `REVIEW_REQUIRED` | Нужен разбор исключения; нет автоматической выплаты / освобождения резерва |
| `CANCELLED` | Согласованная отмена без созданного резерва |
| `REFUNDED` | По согласованной отмене освобождён резерв; это локальное освобождение, не банковский обратный перевод |

Изменение условий или активного документа увеличивает `deal_version`, сбрасывает действующие согласования и переводит в `DRAFT`; исторические факты согласий / подписей сохраняются. `PATCH` условий разрешён только в `DRAFT`; документ можно создавать / заменять в `DRAFT` и `AGREED` до первого резерва. После резерва условия и PDF неизменяемы.

Согласия, подписи, резерв и смена статуса сами по себе не увеличивают `deal_version`. Внутренний технический `row_version` не подменяет её и не вводит новый обязательный параметр API. `expected_version` в PATCH — ожидаемая версия условий. Модель хранения и транзакций — в [DATA_MODEL.md](DATA_MODEL.md).

Исключение для нового основания согласования: утверждённый возврат на доработку создаёт `deal_version + 1` с прежними полями и без активного PDF, переводит AGREED → DRAFT и исключает старые согласия из текущих, сохраняя историю. После нового документа нужны два новых согласия. Действие доступно каждой стороне до первого резерва, без спора / отмены / проверки и до срока; оно не возобновляет заблокированную сделку.

Фактическое изменение условий через PATCH снимает активную привязку PDF для новой версии. Прежний файл остаётся в истории; до согласования требуется заново загрузить / сгенерировать акт. Частичный PATCH может передавать любые поля создания, кроме заказчика из сессии; `expected_version` обязателен, явный `null` вместо изменяемой строки запрещён. После нормализации PATCH без изменений возвращает прежнюю `deal_version` и сохраняет текущие PDF / согласия. При согласовании без актуального документа сервер возвращает `409 DOCUMENT_REQUIRED`, при несовпадении ID / версии / SHA256 — `409 DOCUMENT_MISMATCH`. Для резерва из DRAFT возвращаются INVALID_STATE либо VERSION_CONFLICT при прежней версии. Проверка загруженного PDF не является автоматической смысловой сверкой его текста с условиями; стороны явно согласуют точные байты и контекст сделки.

Создание сделки не считается согласием автора: обе стороны явно принимают одну версию. Согласие связывает `deal_version`, документ, его версию и SHA-256. Без окончательного PDF согласование и резерв невозможны.

`deadline_at` — согласованный предельный срок автоматического исполнения. Наступление срока переводит активную незавершённую сделку в `REVIEW_REQUIRED`, без автоматической выплаты / возврата. Активный запрос отмены сохраняется и может быть завершён; срок остаётся блокировкой выплаты. Проверка срока есть внутри денежных транзакций, независимо от фоновой задачи. Возобновления выплаты из `DISPUTED` / `REVIEW_REQUIRED` в MVP нет: можно согласовать отмену и создать новую сделку. Срок не доказывает отсутствие исполнения работ.

Приоритет сводного status: терминальный исход → REVIEW_REQUIRED при сроке / сохранённой причине проверки → активная отмена → спор → обычная фаза. Открытие нового запроса отмены не снимает прежнюю причину проверки; его можно принять и в REVIEW_REQUIRED. Все блокирующие факты сохраняются и показываются независимо от сводного status.

Объект сделки: `id`, `deal_version`, `status`, `customer_party_id`, `supplier_party_id`, `title`, `description`, `amount_kopecks`, `currency`, `deadline_at`, текущий документ, согласия сторон, подписи, резерв данной сделки, `payment_id`, активный спор / запрос отмены, даты создания / изменения. Чужих остатков и других сделок в нём нет.

Правила условий при создании / изменении черновика: `title` — 1–200, `description` — 1–5000 символов Unicode после обрезки внешних пробелов; обе строки обязательны. ID исполнителя — непустая строка до 128 символов. Общий предел JSON-тела — 16 KiB; допустимая по числу символов строка также должна уложиться в него. Неверный формат срока даёт `400 INVALID_REQUEST`, прошедший срок — `422 DEADLINE_PASSED`; сумма проверяется как положительная каноническая строка int64. Совпадение сторон — `400 INVALID_REQUEST`, неизвестный исполнитель — `404 RESOURCE_NOT_FOUND`. Это проектная конкретизация исходного ТЗ, а не дополнительные решения пользователя.

Карточка и элементы списка имеют одинаковую форму. Для читаемого отображения добавлены `customer` и `supplier` с полями `{id, name, kind}` без остатков. `document` — null либо `{id, deal_id, deal_version, document_version, sha256, file_name, size_bytes, content_type, created_at}` текущего PDF. `agreements` — массив действующих согласий `{id, organisation_id, user_id, deal_version, document_id, document_version, document_sha256, created_at}` только для текущих условий и PDF; уникальность — организация на версию сделки. Повторное согласие той же стороны с новым ключом не создаёт второго голоса. PDF и согласия читаются вместе с условиями одним SQL-снимком. `reserve` — null либо `{id, deal_id, deal_version, account_id, amount_kopecks, currency, status: "ACTIVE", created_at}`. Для будущих функций пока возвращаются `signatures: []`, `payment_id: null`, `dispute: null`, `cancellation_request: null`.

`created_at`, `updated_at` и срок возвращаются в UTC; срок нормализуется до микросекунд PostgreSQL перед хешированием / сохранением. DRAFT, AGREED и FUNDED с истёкшим сроком читаются как REVIEW_REQUIRED, включая фильтр списка по единому времени выполнения запроса БД. Все реализованные команды изменения проверяют время после получения блокировки; документ также проверяет срок после подготовки / записи файла. PATCH нового будущего срока не возобновляет уже просроченную сделку. Сохранённый ответ команды не пересчитывается при повторе ключа; для актуального состояния выполнить GET.

Для списка `q` — до 200 символов; `created_from` / `created_to` — включительные RFC 3339 границы, нижняя не должна превышать верхнюю. Курсор подписан и связан с организацией и всеми фильтрами. Принадлежность сделки проверяется на сервере: посторонняя организация и оператор без организации получают `404` карточки; создание / список для оператора — `403`. При успешном создании атомарно сохраняются результат команды, версия условий, событие аудита DEAL_CREATED и задание outbox. Семантический отказ сохраняет результат и DEAL_CREATE_REJECTED без вымышленной сделки и без задания уведомления. Доставку уведомлений и криптографический контроль A19 это само по себе не реализует.

## 4. Сделки, резерв, спор и отмена

Изменяющие команды этого раздела требуют `Idempotency-Key`. Версия проверяется под блокировкой сделки. Реализованы создание, список / карточка, PATCH, agree, rework и reserve. Disputes, cancellation-requests, audit и export ниже — будущие маршруты; описание выплаты / освобождения относится к будущим этапам.

| Метод и путь относительно `/api/v1` | Тело / действие | Доступ |
|---|---|---|
| `POST /deals` | `{supplier_party_id, title, description, amount_kopecks, currency, deadline_at}`; описание макета в `description`, без отдельной загрузки; заказчик из сессии; `201`, `DRAFT`, версия 1 | `ORG_OWNER` |
| `GET /deals` | `q`, `status`, `role=customer\|supplier`, `created_from`, `created_to`, `limit`, `cursor`; поиск по ID / названию сделки и ID / названию контрагента | Участник |
| `GET /deals/{id}` | Объект сделки | Участник |
| `PATCH /deals/{id}` | `{expected_version, ...изменяемые поля создания}`; только `DRAFT`, `200`, новая версия при реальном изменении, прежняя при no-op | Заказчик |
| `POST /deals/{id}/agree` | `{deal_version, document_id, document_version, document_sha256}`; согласие своей стороны, второе — `AGREED` | Участник |
| `POST /deals/{id}/rework` | `{deal_version, reason}`; непустая причина до 2000 символов; только AGREED до первого резерва и без блокировок; `200`, новая версия DRAFT без активного PDF | Участник |
| `POST /deals/{id}/reserve` | `{deal_version}`; резерв всей суммы из `AGREED`; `201`, резерв и сделка | Заказчик |
| `POST /deals/{id}/disputes` | `{deal_version, reason}`; запись спора и блокировка выплаты | Участник |
| `POST /deals/{id}/cancellation-requests` | `{deal_version, reason}`; запрос и одно согласие инициатора; `201`, `CANCELLATION_PENDING` либо `REVIEW_REQUIRED` при сохраняющейся проверке / сроке | Участник |
| `POST /deals/{id}/cancellation-requests/{request_id}/accept` | `{deal_version}`; согласие другой стороны, затем однократная отмена / освобождение | Другая сторона |
| `POST /deals/{id}/cancellation-requests/{request_id}/reject` | `{deal_version, reason}`; запрос закрывается, `REVIEW_REQUIRED`, без возобновления выплаты | Другая сторона |
| `GET /deals/{id}/audit` | `type`, `from`, `to`, `limit`, `cursor`; история | Участник |
| `GET /deals/{id}/audit/export` | `format=csv\|json`, `type`, `from`, `to`; файл истории сделки | Участник |

Реализованный reserve принимает только `{deal_version}` и возвращает `201 {reserve, deal}`. Он проверяет право заказчика, AGREED, актуальную версию, точный PDF и два согласия разных сторон на его ID / версию / SHA256. До денежных блокировок сервер читает закреплённые байты PDF и сверяет хеш / размер; отсутствие или повреждение файла даёт 503 без изменения денег. После блокировки счёта и чтения существующего резерва заново проверяются срок и available. Недостаток — `422 INSUFFICIENT_AVAILABLE_FUNDS`; AGREED без двух точных фактов — `422 CONSENTS_MISSING`.

Успех не увеличивает `deal_version`, не меняет total и не создаёт фиктивной денежной проводки: резервирует всю сумму, устанавливает FUNDED / дату первого резерва, сохраняет результат, аудит и outbox одной транзакцией. Исполнитель пока ничего не получает. Резерв единственный на весь жизненный цикл сделки. Старый ключ возвращает исходные 201 / ответ; новый ключ уже финансированной сделки — `409 INVALID_STATE`, без второго резерва. После первого резерва PATCH / PDF / agree / rework запрещены. Срок не освобождает ACTIVE-резерв; release / согласованная отмена ещё не реализованы.

`available_kopecks = total_kopecks − reserved_kopecks`. Резерв не уменьшает общий остаток. Выплата уменьшает общий остаток заказчика и активный резерв и увеличивает общий остаток исполнителя на ту же сумму. Отмена освобождает резерв без зачисления исполнителю. Счета, резерв, проводки, состояние, успешный результат команды и outbox изменяются атомарно.

Спор разрешён из `AGREED`, `FUNDED`, `READY_TO_SETTLE`, `REVIEW_REQUIRED`. В `CANCELLATION_PENDING` он фиксируется без потери запроса отмены; выплата остаётся заблокирована. После `SETTLED`, `CANCELLED`, `REFUNDED` команда отклоняется; автоматического возврата нет.

Отмену можно запросить в любом нетерминальном состоянии. Есть не более одного активного запроса; повтор инициатора не создаёт согласие второй стороны. Два действия одной организации не заменяют две организации. После отказа новый запрос имеет новый ID, старые согласия не переносятся. Завершение без резерва даёт `CANCELLED`, с освобождением активного резерва — `REFUNDED`. `SETTLED`, `CANCELLED`, `REFUNDED` терминальны.

Спор, отмена и выплата сериализуются одной дисциплиной блокировок сделки / резерва / счетов. Если блокировка выплаты зафиксирована раньше, расчёт запрещён. Если расчёт уже зафиксирован, следующая блокирующая команда получает конфликт и не меняет деньги. Клиентское время не определяет победителя гонки.

Rework и reserve также сериализуются блокировкой сделки: доработка первой делает прежнюю версию запроса резерва устаревшей; резерв первым запрещает доработку. Rework фиксирует новую версию, снятие активного PDF, аудит с причиной, идемпотентный результат и outbox одной транзакцией, без денежных изменений. Повтор сохранённого старого agree / rework возвращает прежний результат, но не активирует согласие или переход повторно. Для актуальной карточки клиент выполняет GET.

## 5. PDF и тестовые подписи

Первые пять маршрутов таблицы реализованы. Тестовая подпись и всё описание обработки подписей после таблицы — следующий этап; согласие условий не является подписью и не переводит деньги.

| Метод и путь относительно `/api/v1` | Тело / действие | Доступ |
|---|---|---|
| `POST /deals/{id}/documents` | `multipart/form-data`: `expected_deal_version`, `file`; точные байты PDF, SHA-256; `201`, документ и новая версия сделки | Заказчик |
| `POST /deals/{id}/documents/generate` | `{expected_deal_version, template_id: "printing-acceptance-v1"}`; готовый учебный акт по условиям, те же правила версии / хеша | Заказчик |
| `GET /documents/{id}` | Метаданные; `version` необязателен, без него последняя сохранённая версия PDF, даже если активная привязка снята | Участник сделки и соответствующей исторической версии |
| `GET /documents/{id}/view` | Обязательный `version`; PDF для безопасного просмотра | Участник сделки |
| `GET /documents/{id}/download` | Обязательный `version`; те же байты, `Content-Disposition: attachment` | Участник сделки |
| `POST /documents/{id}/sign` | `{deal_version, document_version, document_sha256}`; тестовая подпись своей организации | Участник сделки |

Изменяющие запросы требуют `Idempotency-Key`. Загрузка / генерация возвращает `201 {deal, document}`. Multipart содержит ровно по одному полю `expected_deal_version` и `file`, без дополнительных полей; версия — каноническое положительное целое, имя имеет расширение `.pdf`, тип файла — `application/pdf`. Максимум файла — **5 MiB**, предел всего multipart — 5 MiB + 64 KiB. Неверный MIME / расширение либо содержимое — `422 INVALID_DOCUMENT`, превышение размера — `413 PAYLOAD_TOO_LARGE`; неверный тип всего запроса — `415 UNSUPPORTED_MEDIA_TYPE`.

Проверяется настоящий PDF с ограничениями: до 100 страниц и 5000 объектов; зашифрованные файлы, формы, аннотации / ссылки, JavaScript / действия, вложения, multimedia и неподдерживаемые потоки отклоняются. Это ограниченное статическое подмножество PDF, не антивирусная гарантия. Подробная политика / ресурсные пределы — в [documentfile/README.md](../internal/core/documentfile/README.md). Генерация поддерживает кириллицу и точные целые копейки; неподдерживаемый символ шрифта даёт `422 INVALID_DOCUMENT`, после чего можно загрузить подходящий готовый PDF.

Имя не используется как путь. Сервер хранит файл под случайным внутренним ключом в приватном `DOCUMENTS_DIR`; публичных URL нет. Просмотр / скачивание требуют авторизации и положительного `version`; возвращаются одни и те же закреплённые байты с `application/pdf`, `nosniff`, `no-store` и CSP `sandbox`. Просмотр допускает встраивание только с того же origin; скачивание задаёт `Content-Disposition: attachment`. Перед выдачей проверяются сохранённые SHA256 и размер; расхождение / отсутствие файла даёт временную серверную ошибку без выдачи байтов.

`document_id` обозначает документ сделки и остаётся тем же при замене, `document_version` растёт монотонно; каждая версия неизменяема и имеет SHA-256 точных байтов. Любой новый PDF увеличивает также `deal_version`, даже если байты совпадают, и сбрасывает согласования. Исторические версии доступны только организации, которая одновременно является текущей стороной сделки и стороной той версии условий, к которой относится PDF. Заменённый исполнитель теряет доступ к документам сделки; новый не получает доступ к PDF прежнего исполнителя. Заказчик сохраняет доступ к истории. Исторический PDF не становится активным автоматически.

Подписывать можно только в `FUNDED` / `READY_TO_SETTLE`, текущие согласованные версии до срока, без блокирующего состояния. Факт подписи содержит `signature_id`, пользователя и организацию, сделку и её версию, документ и его версию/хеш, время. Уникальность — организация + версия сделки + версия документа. Повтор возвращает существующий факт; подстановка чужой организации невозможна.

Первая подпись не меняет деньги. Вторая переводит сделку в `READY_TO_SETTLE` и транзакционно создаёт outbox-задание имитатору ЭДО. Это тестовые действия пользователей; HMAC источника не является подписью сторон или квалифицированной электронной подписью.

Основание outbox фиксирует устойчивые event_id, время и привязки события в той же транзакции второй подписи. Смысл события не строится заново из изменяемой карточки. Исходные байты тела сохраняются до первой доставки; повторы меняют только транспортные timestamp / HMAC.

## 6. История, уведомления и оператор

В таблице реализованы GET `/demo/accounts` и POST credits / debits. Остальные маршруты и доставка уведомлений — проект следующих этапов. Команды сохраняют неизменяемый аудит и pending outbox в своих транзакциях; HTTP-чтения истории / уведомлений и worker доставки ещё нет.

| Метод и путь относительно `/api/v1` | Действие | Доступ |
|---|---|---|
| `GET /notifications` | `unread`, `limit`, `cursor`; уведомления текущему пользователю | Пользователь |
| `POST /notifications/{id}/read` | Пустое тело, идемпотентная отметка, `204` | Получатель |
| `GET /demo/accounts` | Клиентские счета `{items, next_cursor}`; строгие `q`, `limit`, `cursor`, поиск по ID счёта / ID / названию организации | `DEMO_OPERATOR` |
| `POST /demo/accounts/{id}/credits` | `{amount_kopecks, reason}` и `Idempotency-Key`; `201 {transaction_id, account}`, положительное зачисление от DEMO_ISSUANCE с двумя проводками / аудитом | `DEMO_OPERATOR` |
| `POST /demo/accounts/{id}/debits` | `{amount_kopecks, reason}` и `Idempotency-Key`; `201 {transaction_id, account}`, списание только available на фиксированный DEMO_DEBITS | `DEMO_OPERATOR` |
| `POST /demo/edo/events` | `{deal_id, template, replay_event_id?}` и `Idempotency-Key`; сервер формирует / доставляет событие; `202`, `{job_id, event_id}` | `DEMO_OPERATOR` |
| `GET /demo/edo/events/{event_id}` | Метаданные, статус доставки и результат обработки (`http_status`, `result` / `error_code`) без секретов | `DEMO_OPERATOR` |
| `GET /demo/audit` | `deal_id`, `type`, `from`, `to`, `limit`, `cursor`; тестовый аудит | `DEMO_OPERATOR` |

Account оператора: `{id, organisation: {id, name, kind}, currency, total_kopecks, reserved_kopecks, available_kopecks}`. Системные счета в список не входят и не принимаются как цель credits / debits. `q` — до 200 символов после trim, буквальная подстрока без регистра во всех трёх полях; limit 1–100, по умолчанию 20. Курсор подписан и связан с оператором, q и limit; неизвестные / повторные параметры запрещены.

Сумма credits / debits — положительная каноническая строка int64, причина — 1–2000 символов после trim, допускаются переводы строк / табуляция. Операция проверяет системную роль на сервере; обычный участник получает 403. Зачисление уменьшает системный DEMO_ISSUANCE и увеличивает клиентский total, списание уменьшает только доступные клиентские средства и увеличивает DEMO_DEBITS. Оба пути дают две неизменяемые равные противоположные проводки. Переполнение клиента, отрицательного противосчёта эмиссии или получателя — `422 AMOUNT_OVERFLOW`, недостаток available — `422 INSUFFICIENT_AVAILABLE_FUNDS`, без частичного изменения.

Шаблоны будущего имитатора ЭДО: `valid`, `single_signature`, `wrong_amount`, `wrong_parties`, `wrong_document`, `wrong_document_version`, `wrong_document_hash`, `wrong_deal_version`, `invalid_hmac`, `replay`, `same_id_different_body`. Для `replay` обязателен `replay_event_id`: сохраняются тело / ID исходного события, транспортная подпись формируется заново. `same_id_different_body` проверяет конфликт дедупликации. `valid` использует только сохранённые подписи; оператор не создаёт подписи за стороны. Произвольное подписание тел и HMAC-секрет браузеру недоступны.

Служебное списание нужно для проверки конкурирующих денежных операций: оно не является выплатой сделки и не погашает её резерв. Проверка доступного остатка, блокировки счетов / резервов, проводки и идемпотентный результат выполняются одной транзакцией через тот же реестр. Сумма положительна, получатель — фиксированный системный учебный счёт, а не произвольный контрагент; отрицательный остаток и расходование активного резерва запрещены.

Уведомления внутри приложения: новая сделка, согласование, возврат на доработку, резерв, подписи, расчёт, спор, запрос / отказ / завершение отмены, переход в проверку. Создаются через outbox после доменной транзакции и не дублируются при повторной доставке. После первой подписи создаются только факт подписи и уведомление; расчётное событие ЭДО появляется после второй. Почта / внешние мессенджеры не обязательны.

Аудит содержит действие, ресурс / версию, пользователя / источник, серверное время, результат, request ID; не содержит паролей, токенов, HMAC-секрета и байтов PDF. Экспорт соответствует правам и фильтрам экранной истории; CSV UTF-8 защищает значения от выполнения как формул. Уведомления и аудит не заменяют денежные проводки.

Начальное наполнение: разные аккаунты заказчика, исполнителя и оператора; остатки заказчика `"50000000"`, исполнителя `"0"`; начальное зачисление имеет проводку. Новые регистрации начинают с `"0"`. Пересоздание демонстрации — отдельная CLI-команда: новый изолированный учебный сценарий с новыми ID и явными проводками начального зачисления. Старые пользователи, сценарии, история и проводки сохраняются. HTTP reset и прямой HTTP-платёж отсутствуют; панель может показывать инструкцию CLI. Точная команда фиксируется при реализации в инструкции запуска.

## 7. Идемпотентность

Ключ обязателен для доменных изменяющих команд. Авторизация и отметка прочтения используют собственную семантику и не требуют `Idempotency-Key`. Ключ — непрозрачная строка длиной 16–128 символов.

Для реализованных браузерных команд ключ содержит только печатные ASCII-символы без пробелов. Некорректная длина / символы дают `400 IDEMPOTENCY_KEY_REQUIRED`. Некорректный JSON, неизвестные поля, `null` вместо изменяемой строки и неверные типы отклоняются до доменной команды. Семантические отказы разобранной команды сохраняются с результатом и аудитом; повтор ключа не создаёт второй факт отказа. Ошибки multipart-структуры / имени / MIME / размера отклоняются в HTTP до доменной команды; разобранный PDF, который не проходит проверку содержимого, сохраняет отказ `INVALID_DOCUMENT`.

Область команд сделки: **организация + операция + ресурс + ключ**; операторской команды — **user_id оператора + операция + ресурс счёта + ключ**; у создания ресурс — коллекция. Хеш нормализованного тела учитывает значимые поля; у загрузки — поля и точные байты файла, но не случайную multipart-границу. То же тело возвращает сохранённые HTTP-статус / результат; другой хеш — `409 IDEMPOTENCY_CONFLICT`. Авторизация проверяется и при повторе.

Одновременные одинаковые команды сериализуются уникальным ограничением. Доменное изменение и успешный результат команды фиксируются одной транзакцией. Временная ошибка инфраструктуры допускает повтор тем же ключом; терминальный результат валидации сохраняется последовательно. В MVP записи ключей не очищаются автоматически.

Независимо от ключа БД уже запрещает второй резерв сделки и изменение опубликованных reserve / ledger / result facts. Будущие ограничения: одна подпись организации для конкретных версий, не более одного расчёта сделки и взаимоисключение выплаты / освобождения резерва. Новый ключ / ID события не разрешает повторную выплату.

## 8. Внутреннее событие ЭДО

Проектный контракт: внутренний маршрут и обработчик ЭДО ещё не реализованы.

`POST /internal/edo/events` — отдельный внутренний маршрут без `/api/v1`, без cookie-сессии / CSRF; не браузерный маршрут. Имитатор обращается к нему внутри контура. Максимум тела — 64 KiB.

Заголовки: `X-EDO-Key-ID`, `X-EDO-Timestamp` (Unix seconds), `X-EDO-Signature: sha256=<lowercase hex>`. HMAC-SHA256 считается над UTF-8 `timestamp + "\n" + raw_body`, сравнение постоянного времени. Отклонение транспортного времени — не более 5 минут; `source` соответствует ключу. Неверный ключ, подпись / время — `403 EDO_SOURCE_INVALID`. Секрет только на сервере. Старое тело повторяется с актуальным подписанным транспортным временем, без изменения `occurred_at`.

```json
{
  "schema_version": 1,
  "event_id": "edo-demo-001",
  "source": "edo-emulator",
  "event_type": "document.accepted_by_both",
  "deal_id": "deal-demo-001",
  "deal_version": 1,
  "document_id": "document-demo-001",
  "document_version": 1,
  "document_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "customer_party_id": "company-customer-demo",
  "supplier_party_id": "company-supplier-demo",
  "amount_kopecks": "30000000",
  "currency": "RUB",
  "signed_by_customer": true,
  "signed_by_supplier": true,
  "customer_signature_id": "signature-customer-demo",
  "supplier_signature_id": "signature-supplier-demo",
  "occurred_at": "2026-10-19T09:00:00Z"
}
```

Хеш в примере — заполнитель; в событии нужен хеш точных согласованных байтов. Все поля присутствуют обязательно. `customer_signature_id` / `supplier_signature_id` должны быть непустыми ID сохранённых фактов, когда соответствующий `signed_by_customer` / `signed_by_supplier` равен `true`; при `false` соответствующее поле обязательно имеет значение `null`. Одних булевых флагов недостаточно: ссылки сверяются с сохранёнными фактами, сторонами и версиями. Шаблон `single_signature` передаёт одну действительную подпись, второй флаг `false` и второй ID `null`; результат — `422 SIGNATURES_MISSING`, без выплаты.

Обработка:

1. Проверить размер, транспортную подпись / источник, схему / типы. Неаутентифицированные данные не создают доменное событие.
2. Долговременно сохранить `source + event_id` и SHA-256 исходного тела в inbox. Прежнее тело возвращает прежний результат; другое — `409 EVENT_ID_CONFLICT`. Транспортные заголовки в хеш тела не входят.
3. Сопоставить сделку / версию, стороны, сумму / валюту, документ / версию / хеш, две сохранённые подписи. Одиночная подпись или несовпадение — `422`, без выплаты.
4. В транзакции соблюдать общий [порядок блокировок](DATA_MODEL.md#денежные-блокировки-и-гонки): inbox → сделка → счета по возрастанию ID → резерв. Повторить проверки согласований, срока, состояния, резерва и отсутствия спора / отмены / проверки. Событие до резерва или других условий отклоняется; повтор сохранённого отказа позднее не запускает выплату.
5. При выполнении всех условий атомарно создать единственный расчёт и проводки, погасить резерв, установить `SETTLED`, записать результат inbox и outbox. Частичный успех невозможен.

Успех — `200 {event_id, result: "settled", deal_id, payment_id}`; повтор возвращает сохранённый ответ. Новое валидное событие с другим ID для исполненной сделки — `200`, `result: "already_settled"` и прежний `payment_id`. Остальные привязки всё равно проверяются. Семантический отказ сохраняется с кодом. При `503` источник повторяет доставку, а не считает выплату отсутствующей.

Противоречивое / позднее событие не отменяет исполненный расчёт. Исключение отражается в аудите; до исполнения применяется предусмотренная проверка / блокировка без автоматического арбитража.

## 9. Ошибки

Таблица объединяет текущие и будущие ошибки. Точный перечень реализованного этапа — в [справочнике](api/README.md#ошибки); пример ниже относится к будущей денежной команде.

```json
{
  "error": {
    "code": "INSUFFICIENT_AVAILABLE_FUNDS",
    "message": "Недостаточно доступных тестовых средств",
    "details": {"required_kopecks": "30000000", "available_kopecks": "20000000"}
  },
  "request_id": "request-demo-001"
}
```

| HTTP | Стабильные коды |
|---|---|
| `400` | `INVALID_REQUEST`, `INVALID_AMOUNT`, `IDEMPOTENCY_KEY_REQUIRED` |
| `401` | `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `SESSION_EXPIRED` |
| `403` | `FORBIDDEN`, `CSRF_INVALID`, `EDO_SOURCE_INVALID` |
| `404` | `RESOURCE_NOT_FOUND`, включая чужие ресурсы |
| `409` | `EMAIL_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `SESSION_CHANGED`, `VERSION_CONFLICT`, `INVALID_STATE`, `DOCUMENT_REQUIRED`, `DOCUMENT_MISMATCH`; будущие `EVENT_ID_CONFLICT`, `CANCELLATION_SELF_APPROVAL` |
| `413` | `PAYLOAD_TOO_LARGE` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `422` | `INVALID_DOCUMENT`, `DEADLINE_PASSED`, `INSUFFICIENT_AVAILABLE_FUNDS`, `CONSENTS_MISSING`, `AMOUNT_OVERFLOW`; будущие `EVENT_BINDING_MISMATCH`, `SIGNATURES_MISSING`, `SETTLEMENT_BLOCKED` |
| `429` | `RATE_LIMITED` |
| `500` / `503` | `INTERNAL_ERROR` / `TEMPORARILY_UNAVAILABLE` |

`details` необязателен и содержит только разрешённые сведения. Не раскрываются SQL, стек, секреты, чужие email, остатки и существование чужого документа. Клиент обрабатывает `code`, не текст `message`. Таймаут соединения не доказывает отсутствие исполнения: нужно прочитать сделку или повторить исходную команду с тем же ключом.
