# Архитектура «ПоАкту»

Обновлено: 24 октября 2026 года. Go + PostgreSQL + TypeScript и архитектурный образец выбраны пользователем. Реализованы авторизация / организации, версии условий и PDF, два согласия / rework, резерв, две тестовые подписи, проверяемая доставка ЭДО и единственная выплата. Спор, запрос отмены, решение второй организации и сохранённый отказ блокируют автоматическое продолжение. Изменения сохраняют версии, результаты команд / inbox, аудит и pending outbox. Доставка уведомлений, экспорт и независимый контроль A19 остаются следующими этапами. Все средства и подписи учебные. Требования — [TZ.md](TZ.md), контракт — [API.md](API.md), выполненные проверки — [STATUS.md](STATUS.md).

## Реализованные этапы документа и резерва

Схема БД развивается последовательными миграциями; перечисление и платёжные разделы ниже описывают существующий код. Раздел A19 отдельно помечен как проект.

| Миграция | Реализованные данные |
|---|---|
| `001_foundation.sql` | Пользователи, организации, членства и сессии; учебные счета, сбалансированные первоначальные проводки и отметка bootstrap |
| `002_deal_drafts.sql` | Агрегат `deals`, неизменяемые `deal_versions`, сохранённые результаты `idempotency_keys`, `audit_events` и pending `outbox` |
| `003_deal_agreement.sql` | `documents`, неизменяемые `document_versions` и `deal_agreements`, указатель текущего PDF в `deals`, ограничения контекста и допустимых runtime-переходов |
| `004_deal_reserves.sql` | Неизменяемый ACTIVE-резерв, операторские результаты, DEMO_CREDIT / DEMO_DEBIT, проекции остатков / резервов, ограничения направления и состояния |
| `005_guard_search_path.sql` | Закреплённый search_path восьми trigger-функций: pg_catalog, доверенная схема приложения, pg_temp последним |
| `006_test_signatures.sql` | Неизменяемые подписи своей организации, READY_TO_SETTLE, единственное основание ЭДО с точными raw bytes / event ID / временем; права runtime и проверки контекста |
| `007_deal_blockers.sql` | Неизменяемые споры, запросы отмены и решения второй организации; сохранённый отказ, освобождение ACTIVE → RELEASED и REFUNDED / CANCELLED; защита обычных команд при блокирующих фактах |
| `008_edo_settlement.sql` | Долговременный inbox, доставка с lease / повторами, операторские результаты ЭДО, единственный settlement / сбалансированная пачка, ACTIVE → CONSUMED и SETTLED |

Метаданные документа и согласия принадлежат модулю `deals`. `internal/core/documentfile` предоставляет разбор PDF, генерацию учебного акта и частное файловое хранилище через потребительский интерфейс `DocumentStore`; отдельного предметного модуля `documents` пока нет. `cmd/poaktu` вручную собирает зависимости и закрывает файловый `os.Root` при завершении сервера.

Заказчик редактирует только `DRAFT`. Фактическое изменение условий создаёт новую `deal_version`, снимает активный PDF и исключает прежние согласия из текущего раунда; изменение без новых значений не создаёт новую версию. Генерация / загрузка PDF разрешена заказчику в `DRAFT` и `AGREED` до первого резерва: создаются новая версия условий и новая версия документа, состояние становится `DRAFT`. Два согласия разных организаций на актуальный контекст дают `AGREED`, без подписи или денежной операции. Каждая сторона может вернуть `AGREED` на доработку с причиной: новая версия сохраняет условия, но не активный PDF / согласия; причина остаётся в аудите. Срок и блокирующее состояние проверяются сервером; истёкший срок отображается как `REVIEW_REQUIRED` и не возобновляется новым сроком через PATCH.

`document_id` стабилен в пределах сделки: таблица `documents` допускает один документ на `deal_id`, а `document_version` растёт при каждой публикации PDF. `document_versions` связывает точные SHA256, размер и частный storage key с `deal_id` / `deal_version`. Текущий указатель в `deals` имеет отложенные внешние ключи на тот же документ и ту же версию условий. Согласие фиксирует организацию / пользователя и кортеж `(deal_id, deal_version, document_id, document_version, SHA256)`; внешний ключ связывает его с метаданными неизменяемого файла, уникальность допускает одно согласие организации на версию сделки. Триггеры запрещают UPDATE / DELETE опубликованных версий и согласий. Карточка собирает текущий PDF и согласия одним SQL-запросом: исторические факты не подставляются в новую версию.

HTTP-роль `poaktu_runtime` получает явные права из `deploy/postgres/runtime_grants.sql` и `edo_runtime_grants.sql`. UPDATE ограничен проекциями счетов, полями агрегата, монотонным status резерва и служебными колонками inbox / доставки. Идентичность резерва, опубликованные версии, согласия, подписи, блокирующие факты, settlements, исходные байты и завершённые результаты не редактируются и не удаляются. DDL / bootstrap / создание оператора и изменение общего `outbox.delivered_at` недоступны. После первого резерва условия / PDF неизменяемы; состояние проходит только проверенные переходы. Права пользователя / организации проверяются приложением; это не RLS и не защита от владельца БД.

Миграция 005 закрывает подмену реальных таблиц временными в DB-проверках. Восьми trigger-функциям из 001–004 назначается `search_path = pg_catalog, <схема применения миграций>, pg_temp`; pg_temp явно последним, а не неявно первым. Это включает первоначальную проверку баланса пачки, проекции, контекст / публикацию резерва, направление проводок и runtime-переходы. Функции остаются SECURITY INVOKER; закрепление имени не выдаёт дополнительных привилегий. Обычная HTTP-роль может иметь TEMP, однако её одноимённые временные таблицы не заменяют реестр внутри guard. Миграции запускаются владельцем с доверенной схемой; это не защита от суперпользователя / владельца схемы и не реализация A19.

## Стартовая схема

Модульный Go-сервер на стандартном `net/http.ServeMux`, pgx и SQL-миграциях. Frontend — React + TypeScript + Vite, отдельная статическая сборка через nginx с reverse proxy `/api/v1`. ЭДО, его worker и координатор расчёта находятся в модуле `edo`; внутренний маршрут закрыт для web-proxy.

Компоненты: сделки и версии условий; тестовые счета и резервы; адаптер ЭДО; координатор расчёта; аудит; outbox для уведомлений; интерфейсы участников.

Сохраняем подход [go-todoapp-1](https://github.com/Adopten123/go-todoapp-1): ручная сборка config / logger / pool → Repository → Service → HTTPHandler в `cmd`, функциональные модули, интерфейсы у потребителя. Проверенный снимок — [REFERENCE_ARCHITECTURE.md](REFERENCE_ARCHITECTURE.md). React / TypeScript и полноценная auth не переносятся из исходника: их там нет в требуемом виде.

```text
cmd/poaktu/main.go
internal/core/{config,domain,errors,logger}
internal/core/repository/postgres/{pool,uow}
internal/core/transport/http/{server,middleware}
internal/core/documentfile/
internal/features/{auth,organizations,deals,settlement,documents,edo,notifications,audit}
  service/
  repository/postgres/
  transport/http/
migrations/
web/
deploy/
compose.yaml
```

Дерево показывает целевое разбиение: domain / errors / logger и отдельные documents / notifications / audit ещё не являются готовыми пакетами. Файловый адаптер находится в core/documentfile; settlement содержит операторские счета и общий ledger. Deals координирует резерв / освобождение, edo — проверку источника, inbox, доставку и выплату в одной предметной транзакции. DTO отделены от SQL, запросы параметризованы, интерфейсы находятся у потребителей. core не собирает все предметные правила; циклических импортов нет. HTTP декодирует запрос, service проверяет вход, repository управляет БД; middleware даёт request ID, recovery, body / time limits и журналирование.

Защищённые запросы кабинета имеют предусловие `X-Expected-User-ID`: общая cookie может смениться в другой вкладке раньше, чем обновится интерфейс. Auth middleware сравнивает ожидаемый ID с пользователем фактической серверной сессии и отклоняет несовпадение до чтения данных / выполнения команды. Заголовок не задаёт субъект и права; внешним API-клиентам он необязателен. При конфликте UI перечитывает сессию без автоматического повтора команды, сохраняя неподтверждённые условия под исходной организацией. CSRF-кеш имеет поколение, чтобы старый ответ не восстановил токен после смены сессии.

## Транзакционный слой

Таблицы, версии, сценарий 300 000 ₽, границы commit и предметные отказы разобраны в [DATA_MODEL.md](DATA_MODEL.md). Текущая схема закреплена миграциями 001–008; история уведомлений / экспорт и независимое обнаружение вмешательства пока не реализованы.

Pool исходного проекта не предоставляет Begin / Tx. Реализованный `UnitOfWork.WithinTx(ctx, fn)` создаёт `pgx.Tx` с Read Committed и передаёт его callback, делает commit после успешной функции и rollback при ошибке до попытки commit. Репозиторий выполняет все записи команды через этот `tx`; подстановка обычного pool внутри такой операции запрещена. Ошибка связи после попытки commit помечается `ErrCommitUnknown`: подготовленный успешный ответ не выдаётся, исход операции не считается доказанным rollback.

Команды согласованного документа сначала проверяют доступ, берут транзакционную advisory-блокировку области ключа `(organization_id, operation, resource, key)`, затем `FOR UPDATE` только строки агрегата. После ожидания отдельный SQL-запрос заново читает текущую версию / стороны и проверяет доступ; это исключает использование снимка JOIN до ожидания блокировки. Затем проверяется сохранённый результат: прежнее тело возвращает прежний ответ, иное — конфликт. Повтор старого agree / rework не меняет текущие факты; клиент перечитывает актуальную карточку отдельным GET. Прежний участник, потерявший доступ после замены исполнителя, не получает сохранённый ответ обходом scope.

Новая версия, привязка документа / согласие, статус, аудит, pending outbox и сохранённый результат фиксируются одной транзакцией. PDF готовится под блокировкой сделки до INSERT новой версии; после генерации / валидации / записи файла повторно проверяется `clock_timestamp()`. Внешних сетевых вызовов здесь нет. При ошибке SQL или неизвестном исходе commit опубликованный blob не удаляется: он мог уже стать частью зафиксированной сделки. Это ограниченная файловая подготовка текущего этапа, а не разрешение выполнять внешний ЭДО или генерацию под будущими денежными блокировками.

`settlement.ledger` даёт общие transaction-local операции без собственного commit. `Post` сам получает счета в порядке ID, перечитывает их после ожидания и до INSERT проверяет положительную сумму, разные from / to, доступный остаток обычного источника и int64-границы обоих счетов. Только DEMO_ISSUANCE допускает отрицательный total; его нижняя int64-граница тоже проверяется. Операторский repository держит те же счета перед текущим замером времени и вызывает Post в той же транзакции. Предметные отказы переводятся в сохранённые 422 без частичных проводок; SQL / неизвестный commit не выдаются как успех.

Координатор выплаты `edo.repository.Process` объединяет блокировку inbox / сделки, проверку точного документа / двух подписей / согласий, счета, резерв, settlement, проводки, SETTLED, аудит, outbox и окончательный результат inbox в одной транзакции. Предварительный приём PENDING имеет отдельный commit, позволяющий восстановить обработку после сбоя. Сетевой вызов доставки выполняется вне этих транзакций.

Порядок общий: область идемпотентного ключа либо строка inbox → сделка → затрагиваемые счета по возрастанию ID → резерв → остальные предметные записи / аудит / outbox / результат. После ожидания агрегат и счета перечитываются свежими SQL-запросами. Команда без сделки блокирует счета в том же порядке и затем не получает сделки. Резерв единственный на deal_id: INSERT при финансировании, затем только ACTIVE → RELEASED либо ACTIVE → CONSUMED; возврат в ACTIVE и изменение основания запрещены. Освобождение / выплата получают его FOR UPDATE после счетов. Криптографической головы аудита ещё нет; при реализации A19 её блокировка должна быть последней. deal_version описывает условия, row_version — техническое изменение агрегата; счётчик не заменяет денежную блокировку.

Reserve дополнительно проверяет AGREED, текущую версию условий, PDF и два факта согласия customer / supplier на точный кортеж ID / версий / SHA256. Под удерживаемой сделкой, **до account locks**, файл читается и сверяется с метаданными; отсутствие / порча не позволяет зафиксировать FUNDED. После последнего ожидания счёта и чтения reserve берётся новый clock_timestamp(), затем проверяются срок и available. Истечение срока во время ожидания не разрешает новое исполнение. Успех одной транзакцией создаёт ACTIVE-резерв, увеличивает reserved заказчика, устанавливает FUNDED / first_reserved_at, сохраняет результат, аудит и pending outbox; deal_version / total и ledger не меняются. Первым выигравший rework делает версию reserve устаревшей; первым выигравший reserve запрещает rework.

Команды reserve используют прежнюю область organization / operation / resource / key. У оператора нет фиктивной организации: operator_command_results имеет область user_id / DEMO_CREDIT либо DEMO_DEBIT / account resource / key. Audit может иметь null actor_organization_id, а outbox — null deal_id для движения счёта. Авторизация текущего субъекта проверяется и при replay; старый успех / отказ не переоценивается по новому времени или балансу. Неизвестный исход commit требует того же ключа / тела и проверки актуального состояния.

## Граница цифрового рубля

Внутренний интерфейс: reserve, settle, release, getStatus. Это наш проектный интерфейс, не официальное API Банка России.

Локальный код реализует резерв, проверяемую выплату, освобождение двумя сторонами и чтение текущего состояния учебного реестра. Это не банковский адаптер. Будущее подключение зависит от реальных возможностей и требований платформы; взаимозаменяемость без проверки не гарантируется.

## Учёт средств

Суммы int64 в копейках; валюта RUB. Доступно = общий остаток − активные резервы. Обычное списание проверяет доступный остаток; выплата расходует только собственный обеспеченный резерв и сохраняет покрытие остальных.

В JSON денежные значения передаются десятичными строками, SQL — BIGINT, frontend — BigInt и строковый разбор рублей. Это уточнение раннего числового примера API до начала реализации. `parseFloat` / `Number * 100` для денег не использовать; проверять диапазон и переполнение.

Выплата погашает собственный резерв и создаёт две проводки; освобождение не меняет total и не создаёт фиктивную денежную пачку. Эти исходы взаимоисключаются через общую блокировку сделки / счета / резерва, однонаправленный lifecycle и уникальность settlement. Срок удерживает ACTIVE-резерв до согласованной отмены и не доказывает отсутствие выполненной работы.

Обычное списание проверяет `total − reserved >= amount` в общем ledger и направляет средства на фиксированный DEMO_DEBITS. Пополнение идёт от DEMO_ISSUANCE. `PostReserved` расходует уже обеспеченный резерв конкретной сделки: одновременно уменьшает total и reserved заказчика, увеличивает total исполнителя. Повторное наличие всей суммы в available не требуется; остальные резервы сохраняют покрытие. Проверки int64 выполняются до арифметики / INSERT; каждая пачка содержит две равные противоположные записи разных RUB-счетов.

Баланс — транзакционно обновляемая проекция проводок, reserved — проекция ACTIVE-резервов. Отложенные constraint triggers сверяют обе межтабличные суммы (с numeric при суммировании), баланс / две записи пачки, направление движения и публикацию reserve вместе с FUNDED. FK / trigger контекста связывают резерв с текущими условиями, сторонами, суммой / RUB, клиентским счётом и точным PDF / двумя согласиями. Это дополнительные ограничения штатной runtime-роли; они не делают PostgreSQL независимым арбитром.

Новые организации нулевые. Bootstrap при обновлении добавляет отсутствующий фиксированный DEMO_DEBITS с нулём до проверки старой отметки foundation_v1, затем сохраняет прежнюю эмиссию / пароли / счета. При чистом запуске начальные 50 000 000 копеек остаются единственной прежней seed-пачкой; повторный старт не повторяет её.

Текущая схема: users / organizations / memberships / sessions; deals / deal_versions / deal_agreements; documents / document_versions / document_signatures; accounts / reserves / ledger_batches / ledger_entries / settlements; deal_disputes / cancellation_requests / cancellation_decisions; idempotency_keys / operator_command_results / edo_command_results; event_inbox / edo_outbox / edo_deliveries / outbox / audit_events. Согласие / подпись организации уникальны для основания, резерв и settlement — для сделки, settlement также уникален по reserve / batch; inbox — по source / event_id. Таблиц notifications и криптографической головы аудита пока нет.

Локальная привязка резерва к deal_id не является доказанным окрашиванием настоящего цифрового рубля.

## Состояния

DRAFT → AGREED → FUNDED → READY_TO_SETTLE → SETTLED.

Дополнительные: DISPUTED, CANCELLATION_PENDING, REVIEW_REQUIRED, CANCELLED до резерва, REFUNDED после согласованного освобождения.

[STATE_MACHINE.md](STATE_MACHINE.md) фиксирует матрицу ролей / действий и утверждённый возврат AGREED → DRAFT до первого резерва. Rework создаёт новую deal_version без активного PDF; прежние согласия остаются в истории и не учитываются в новом раунде. Возврат и резерв сериализуются блокировкой сделки; после резерва доработка запрещена.

Спор, отмена и причины проверки хранятся независимо от status. Сводка имеет приоритет: терминальный исход → проверка / срок → активная отмена → спор → обычная фаза. Новый запрос отмены не снимает причину проверки; его можно завершить и в REVIEW_REQUIRED. Кнопки UI и серверные проверки опираются на все факты и текущее время, а не только на строковый status.

Состояние документа отдельно от сделки. События могут поступать не по порядку; без резерва и всех условий выплаты нет. Истечение срока переводит спорное исключение в предусмотренную проверку, а не автоматически отдаёт деньги одной стороне.

## Обработка события

1. Проверить доверенный источник и подпись сообщения.
2. Сохранить event_id и хеш тела. Повтор с другим содержимым отклонить.
3. Сопоставить сделку, версию, документ, стороны, сумму и двустороннюю подпись.
4. В транзакции заблокировать нужные строки и повторно проверить резерв и отсутствие спора.
5. Создать единственный расчёт, проводки, состояние и outbox.
6. Зафиксировать транзакцию; сохранить outbox для будущей доставки уведомлений.

Гонку спора и выплаты решать одной транзакционной проверкой. Спор после расчёта не возвращает средства автоматически.

Запрос отмены блокирует выплату, но не освобождает резерв. Согласие второй организации освобождает его один раз; один участник не даёт два голоса. Отказ от отмены — REVIEW_REQUIRED, без автоматического возобновления. Для спорной сделки допустима согласованная отмена. Просрочка не вызывает автоматического расчёта / возврата.

## Доверие к ЭДО

Тестовый источник подписывает исходные байты сообщения HMAC-SHA256. Ключ получается отдельным HMAC-SHA256 от постоянного ключа приложения с меткой `poaktu:edo-source-key:v1\x00`; он не выдаётся браузеру, Git или журналам. Key ID — demo-v1, source — edo-emulator. Это проверка источника демо-события, не юридически значимая подпись сторон. Получатель проверяет ровно по одному транспортному заголовку, канонический timestamp ±5 минут и HMAC постоянным по времени сравнением до приёма inbox. Затем строгая схема требует все 18 полей, запрещает неизвестные / повторные ключи и сверяет связи флагов с signature ID / null.

Каждая сторона подписывает только за свою организацию. Вторая подпись до commit фиксирует полный raw body, event ID, occurred_at и ссылки на факты в `edo_outbox`; worker не восстанавливает смысл из поздней карточки. После commit отдельный worker создаёт `edo_deliveries` и отправляет тело в `/internal/edo/events`. Адрес фиксирован доверенной конфигурацией на loopback; redirects / proxy окружения отключены. Через web-proxy маршрут недоступен. Первая подпись создаёт факт и pending-задание уведомления. Получатель сверяет стороны, сумму, версии / SHA256, два действительных signature ID, согласия, срок и полный ACTIVE-резерв.

Worker запускается и останавливается вместе с API; readiness проверяет миграцию 008 / таблицы, stage — edo_settlement. Lease доставки действует 15 секунд; получение задания увеличивает attempts. HTTP timeout — 5 секунд. Сетевой отказ / 5xx, redirect или некорректный ответ оставляют задачу доступной для повтора после паузы 1 секунда, незавершённый lease восстанавливается по сроку. Окончательные 4xx завершают доставку отказом. Завершение проверяет token lease, поэтому поздний ответ старого worker не перезаписывает результат нового. Повтор сохраняет исходные bytes / event ID / occurred_at и обновляет только транспортные timestamp / HMAC. Доставка ЭДО реализована отдельно от ещё не реализованной доставки общих уведомлений outbox.

Inbox различает ожидающий и завершённый результат; после сбоя незавершённое событие не считается успешно обработанным. Точное прежнее тело возвращает сохранённый ответ, другое тело того же source / event_id конфликтует. Семантический отказ окончателен для этого ID. Новый ID уже исполненной сделки возвращает already_settled и прежний payment_id только после проверки исходных привязок / двух подписей. Уникальная выплата по сделке защищает и от другого event_id. После потерянного ответа повтор выясняет зафиксированный результат; таймаут не доказывает отсутствие выплаты. Будущая доставка общих уведомлений должна использовать outbox без дублей.

В пилоте требуются API оператора, подписи и полномочия, статусы и аннулирование документов, согласованная политика противоречивых событий.

Пароли — Argon2id; параметры фиксируются при реализации с опорой на [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## PDF и дополнительные функции

Окончательный учебный PDF фиксируется до резерва. Реализованы загрузка, генерация, метаданные, просмотр и скачивание точной версии. Перезагрузка создаёт новую версию и сбрасывает согласия; после первого резерва замена запрещена. Multipart-handler проверяет единственность полей, расширение `.pdf`, MIME `application/pdf` и предел 5 MiB; одной сигнатуры `%PDF-` недостаточно.

Разбор выполняет закреплённый `pdfcpu v0.16.3` в strict / stateless / offline-режиме без чтения пользовательской конфигурации и сетевых обращений. Политика допускает ограниченное статическое подмножество: запрещены шифрование, включая пустой пароль, формы, аннотации / ссылки, JavaScript / действия, вложения, мультимедиа, внешние потоки и неподдерживаемые фильтры. Проверяются также неиспользуемые и сжатые объекты; сообщённые парсером исправления отклоняются. Ограничения: 100 страниц, 5000 объектов, 1 MiB на объект, 8 MiB на декодированный поток, 32 MiB совокупных декодированных потоков при обходе и кооперативный срок разбора 3 секунды. Это не антивирус, полная изоляция процесса или общий бюджет его памяти; strict-проверка не доказывает отсутствие всех дефектов PDF / viewer и всех низкоуровневых восстановлений парсера.

Генератор `fpdf v0.12.0` использует встроенный Go Regular из `golang.org/x/image v0.47.0`, переносит полный текст условий на следующие строки / страницы и точно форматирует целые копейки. Кириллица не зависит от системных шрифтов; неподдерживаемый символ даёт явный отказ, а не исчезает из документа. Учебный акт содержит ID / версию сделки, стороны, условия, сумму / валюту, срок и маркировку тестового контура. Он не утверждает факт исполнения работ. Точная политика, источники и лицензии — в [описании пакета](../internal/core/documentfile/README.md) и [THIRD_PARTY_NOTICES.md](../internal/core/documentfile/THIRD_PARTY_NOTICES.md).

Файлы находятся в частном volume `DOCUMENTS_DIR`, вне публичной статики. `os.Root` ограничивает операции его каталогом; ключ — случайные 128 бит в виде 32 hex-символов с `.pdf`. Имя пользователя остаётся только очищенными метаданными и никогда не используется как путь. `Put` валидирует байты, записывает временный файл с правами 0600, синхронизирует его и публикует жёсткую ссылку с отказом при существующем имени; перезаписи нет. В Linux синхронизируется также каталог; обычный read-only handle каталога Windows такой операции не предоставляет. Хранилище требует файловой системы с hard links. Чтение ограничено обычными файлами и 5 MiB, а service перед каждой выдачей сверяет длину и SHA256 с БД. Несовпадение не выдаёт байты. Проверка обнаруживает расхождение файла с метаданными, но не заменяет будущий независимый контроль A19 при изменении самой БД.

Метаданные, просмотр и скачивание разрешены владельцу организации, которая является участником **и текущей сделки, и условий запрошенной исторической версии**. После замены исполнителя прежний исполнитель теряет доступ к сделке / PDF, а новый не получает документы чужого прежнего раунда. Заказчик сохраняет свою историю. Запрос метаданных без версии выбирает последнюю версию всего документа, без молчаливого возврата к более старой доступной версии; просмотр / скачивание требуют явную положительную `version`. Путь / storage key в JSON не выдаются. Ответ PDF получает `Content-Disposition`, CSP `sandbox; default-src 'none'; frame-ancestors 'self'` и `Cross-Origin-Resource-Policy: same-origin`. Frontend получает байты через авторизованный API с предусловием аккаунта и открывает `blob:` в отдельной вкладке с `noopener noreferrer`, без вставки PDF в DOM приложения. Это не полная песочница: HTTP-заголовки PDF-ответа не становятся заголовками создаваемого `blob:`. Успешный разбор файла не отменяет авторизацию, ограничения статического содержимого и необходимость учитывать поведение PDF-viewer.

Файловая публикация предшествует commit БД. Отказ или неизвестный исход может оставить недостижимый blob; автоматического удаления нет, чтобы не уничтожить документ уже зафиксированной сделки. При перезапуске volume и привязки сохраняются. Отдельная процедура сборки мусора с доказанным отсутствием ссылок в этом этапе не реализована.

Поиск уже использует параметризованный SQL с пагинацией и org scope. Дальнейший план: уведомления — БД / outbox / опрос UI; CSV / JSON — тот же доступ, защита текстовых CSV-полей от исполнения формул и исключение секретов. Сейчас outbox хранит pending-задания; готовой доставки уведомлений / экспорта нет. Клиент получает результат сервера, а не самостоятельно определяет возможность выплаты.

Оператор читает клиентские счета, пополняет их от DEMO_ISSUANCE и списывает только available на DEMO_DEBITS через общий ledger. Системные счета исключены из списка / цели команды. Панель ЭДО ставит в очередь фиксированные шаблоны valid / single_signature, неверные привязки / HMAC, replay и same_id_different_body; valid использует сохранённые подписи и не подписывает за стороны. Оператор читает последнюю доставку event ID без секретов / raw bytes. Прямого HTTP-платежа и разрушительного reset нет. Отдельная CLI-команда нового demo run остаётся следующим этапом.

## Обнаружение вмешательства администратора БД

19 октября пользователь дополнительно включил демонстрацию обнаружения вмешательства администратора. Требование принято; описанный ниже способ — проектное предложение для обсуждения, реализации и выполненных проверок пока нет. Исходная граница угроз: злоумышленник может менять данные PostgreSQL и восстанавливать её старые копии, но не управляет backend, проверяющей программой, ключами и независимо сохранёнными контрольными точками. Это расширение учебного показа, не заявление о защите от администратора всего хоста.

Предлагаемый минимальный механизм:

1. Запись аудита входит в транзакцию предметной операции и содержит `log_id`, монотонный номер, хеш предыдущей записи и хеш канонически сериализованного события. Формат имеет версию, фиксированные правила кодирования и порядок полей. Голова цепочки обновляется транзакционно; общая блокировка головы берётся последней после предметных блокировок во всех командах. Для небольшого демо допустима сериализация добавления записей.
2. После завершения сценария приостановить новые предметные команды и дождаться завершения текущих транзакций, расчётных outbox-заданий и фоновых изменений. В согласованном read-only снимке сформировать контрольную точку: версия формата, ID контура / журнала, номер и хеш вершины, состав и хеш критического состояния, количество записей и время получения. Время не является независимой доверенной меткой.
3. Критическое состояние охватывает все строки и определённые форматом поля сделок / версий / согласий, документов / подписей, счетов / резервов / проводок / расчётов, споров / отмен, результатов inbox и идемпотентных денежных команд. Сортировка и кодирование детерминированы; состав набора и количества строк входят в хеш. Байты PDF проверяются относительно закреплённого хеша. Проверка одного аудита не покрывает прямой UPDATE остатка или условий.
4. Сохранить эталонную контрольную точку вне полномочий администратора БД, например на втором ПК проверяющего. Для передачи можно подписать её Ed25519 средствами Go; закрытый ключ и закреплённый публичный ключ проверяющего не берутся из проверяемой БД. Подпись не заменяет независимое хранение последней известной точки. Отдельный Rust-сервис не требуется для этого предложения.
5. Отдельный Go CLI сверяет цепочку, внешнюю вершину / номер и критическое состояние. Нужны отдельные результаты: совпадение с указанной точкой, нарушение цепочки, несовпадение состояния / внешней вершины, недоступная или неподтверждённая проверка. Отчёт указывает контур, границу покрытия и время чтения. Старый отчёт не подтверждает состояние сейчас; отсутствие точки / данных не означает успешную проверку.

Цепочка внутри одной БД не защищает от её полного пересчёта. Внешняя точка позволяет обнаружить изменение уже закреплённого префикса, удаление закреплённого хвоста и откат к более раннему снимку. Неподтверждённый интервал после последней точки такой гарантии не имеет. Нельзя автоматически подписывать произвольную новую вершину из изменяемой БД и заменять ею прежний эталон.

Сравнение текущего состояния с контрольным снимком проводится без легитимных предметных изменений между ними. После обычных новых операций несовпадение снимков ожидаемо и само по себе не доказывает вмешательство. Непрерывное обнаружение потребует достаточного журнала для восстановления ожидаемого состояния либо независимого подтверждения операций; это отдельное проектирование. Даже целый журнал подтверждает неизменность закреплённых данных, а не правильность исходного решения или виновника изменения.

Вне гарантии: компрометация backend / проверяющего / ключей, общий root-доступ к БД и эталону, подмена данных до первой доверенной точки, изменения вне заявленного покрытия и кратковременное изменение с восстановлением до проверки. Отдельный volume или контейнер сам по себе не создаёт независимую сторону доверия. Механизм обнаруживает расхождение, но не предотвращает UPDATE, не возвращает деньги и не восстанавливает БД автоматически.

Сценарий и проверки — в [DEMO.md](DEMO.md), критерий A19 — в [TZ.md](TZ.md). Основание подхода: [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) рекомендует обнаружение изменения / удаления журналов и независимое защищённое хранение; [Go Ed25519](https://pkg.go.dev/crypto/ed25519) предоставляет стандартную реализацию подписи. Конкретный протокол выше — наше проектное предложение, не готовый стандарт или результат аудита.

## Compose и проверки

Сервисы: db; одноразовые migrate / access / bootstrap; api; web. Готовность БД → успешные миграции → access с ограниченными правами HTTP-роли → seed → API readiness → frontend. [Зависимости и healthcheck Compose](https://docs.docker.com/reference/compose-file/services/). Сборка frontend выполняется при build, не конкурентной мутацией исходников при startup.

`docker compose up --build` из корня, канонический URL `http://localhost:8080`; порт привязан к `127.0.0.1`, остальные порты внутри Compose. Точный origin нужен для CSRF, поэтому эти два имени не взаимозаменяются в браузере. Не нужны локальные Go / Node. Named volumes для БД, PDF и ключей, повторный startup не удаляет данные. Учебные пароли seeded-аккаунтов — публичные данные стенда; настоящие секреты и .env в Git не входят. Версии образов, digest и зависимости закреплены в файлах сборки; latest не используется. Инструкции — в [RUNNING.md](RUNNING.md); полный контейнерный запуск на текущем ПК пока не подтверждён.

Проверки: unit домена, интеграционные гонки на PostgreSQL, HTTP-права и браузерный сквозной сценарий. CI собирает backend / frontend и выполняет критические проверки. Код и зависимости banking-system не использовать вообще — это уточнённое прямое указание пользователя.

## Реализованный этап тестовых подписей

POST `/documents/{id}/sign` использует ту же дисциплину сохранённых результатов и aggregate-блокировок. Новая подпись требует FUNDED, точных версий / SHA-256 приватного PDF, двух согласий и полного ACTIVE-резерва; текущее время проверяется после ожидания сделки и проверки файла. Счета не меняются: существующий резерв неизменяем, а обычные списания продолжают проверять available.

Первая подпись сохраняет FUNDED. Вторая одной транзакцией сохраняет второй факт, READY_TO_SETTLE, аудит, pending-задание DOCUMENT_SIGNED и одно основание EDO_EVENT_READY. `edo_outbox` хранит неизменяемые bytes / ID / время и ссылки на две подписи; обычный outbox с тем же event ID — основание доставки. UNIQUE и deferred-проверки связывают две подписи, состояние и основание. Все новые / переопределённые trigger-функции в 006–008 закрепляют доверенный search_path по правилу 005.

Новый ключ уже подписавшей организации после проверки прав / актуальных версий / хеша возвращает существующий факт и текущую карточку даже в SETTLED / REFUNDED / при блокировке. Это чтение факта без новой подписи, аудита или outbox; активный резерв / доступность файла для него не требуются. Старый ключ сохраняет точный исторический ответ. Поэтому UI после успеха / replay перечитывает карточку: worker мог уже завершить расчёт.

## Спор и согласованная отмена

`deal_disputes`, `cancellation_requests` и `cancellation_decisions` неизменяемы. Запрос хранит первый голос; отдельное ACCEPTED / REJECTED может записать только другая текущая организация. Pending означает отсутствие решения; в карточке `cancellation_request` содержит только активный запрос. Закрытый объект приходит в результате accept / reject, факты сохраняются в БД.

Общая SQL-проекция карточки и фильтров: терминальный исход → наступивший срок либо когда-либо REJECTED → pending-отмена → спор → обычная фаза. `review_reasons` содержит DEADLINE_PASSED для незавершённой просроченной сделки и CANCELLATION_REJECTED для сохранённого отказа. Новая отмена не снимает причину проверки. Спор / запрос / отказ проверяются отдельно от status в выплате; обычные INSERT версий / согласий / резерва / подписи также защищены guard-функцией от блокирующих фактов.

Accept после блокировки сделки, счёта и резерва одной транзакцией сохраняет второе согласие, ACTIVE → RELEASED, уменьшение reserved и REFUNDED. Без резерва — CANCELLED. Срок не запрещает это совместное завершение. Отказ даёт REVIEW_REQUIRED без движения денег; автоматического возобновления и арбитража нет. Выплата и отмена используют одну сделку / резерв: первый commit определяет допустимый исход второй команды.
