# Контекст проекта

Обновлено: 21 октября 2026 года.

## Задача репозитория

Единый контекст команды ЮЗГУ для совместной разработки, включая работу AI-агентов. Здесь сохраняются решения, исходные предположения, задачи и фактический статус.

## Выбранная тема

Условный B2B-расчёт для МСБ по событию ЭДО. Заказчик резервирует сумму, исполнитель получает оплату после подтверждения согласованного документального условия.

Пользователь назвал тему «самоисполняемый аккредитив / эскроу за 15 рублей». В документации используем «условные расчёты»: правовая форма будущего сервиса, его цена и полная себестоимость ещё не установлены.

## Хакатон

Трек: «Финтех без границ: банк будущего для бизнеса и клиентов». Основное направление — решения для бизнеса. Требуется основной сценарий, доказанная проблема, экономика и путь к банковскому пилоту.

В предоставленных условиях: спринты до 1 ноября, 29 ноября и 8 декабря; финал 11 декабря. Проверить сроки в кабинете организаторов перед сдачей.

## Принятые решения

- Начальный сегмент — сделки между компаниями / ИП.
- Самозанятые без ИП — расширение после проверки процесса и тарифной классификации.
- Каждая сделка: одна сумма, один документ, один полный расчёт. По уточнению пользователя первый прототип хранит несколько независимых сделок.
- Условие оплаты: проверенное событие двусторонней подписи конкретного документа.
- Расчёты и ЭДО в MVP эмулируются; прямого подключения к Банку России нет.
- ПКСК и цифровой рубль — целевая будущая интеграция.
- Собственная криптовалюта, отдельный токен и самостоятельный блокчейн не требуются.
- ИИ не входит в обязательное ядро.
- Старый banking-system полностью исключён по уточнённому указанию пользователя.
- Название «ПоАкту» и стек Go + PostgreSQL + TypeScript утверждены пользователем.
- Backend следует архитектуре go-todoapp-1: модульный монолит, стандартный net/http, core / features, ручная сборка и интерфейсы у потребителя. Дополнены транзакции и аутентификация; [разбор источника](REFERENCE_ARCHITECTURE.md).
- Регистрация; PDF / тестовые подписи; несколько сделок, спор / согласованная отмена, уведомления, поиск и экспорт включены в первый выпуск.
- Docker Compose одной командой; срок — 1 ноября 2026 года. Жюри получает репозиторий и разворачивает локально.
- Два разработчика на разных ПК передают исходники через Git; [ТЗ](TZ.md) и [передача контекста](HANDOFF.md) фиксируют общий контракт и состояние.
- 20 октября пользователь попросил постепенную публикацию в GitHub: каждый следующий законченный и проверенный этап отправлять отдельным push. Порядок закреплён в CONTRIBUTING.md; уже опубликованный каркас содержит пять отдельных коммитов.
- 19 октября пользователь дополнительно включил демонстрацию обнаружения вмешательства администратора БД. Обнаружение изменения относительно эталона не означает предотвращение изменения или защиту от владельца всей инфраструктуры.
- Пользователь утвердил возврат согласованной сделки на доработку до резерва каждой стороной с причиной, сохранением истории и повторным согласованием. После резерва исправление остаётся через согласованную отмену и новую сделку; [матрица состояний](STATE_MACHINE.md).
- Для локального Compose nginx имеет отдельную bridge-сеть ingress с публикацией только на loopback. Связи web → API и API → PostgreSQL проходят через два внутренних сегмента. Первый Linux CI выявил, что web только во внутренней сети становится healthy, но его опубликованный порт недоступен хосту; ingress добавлен только web, без внешнего маршрута для API и БД.
- 21 октября по запросу пользователя добавлены комплексные UI / API-тесты. Playwright проверяет настоящий сервер и PostgreSQL; подменяются только явно заданные сбои интерфейса. Для команд неизвестного исхода проверяется потеря ответа после реального commit, reload и повтор того же ключа / тела. Стенд для прогонов изолируется отдельным Compose-проектом или локальной учебной БД; команды Playwright запускаются последовательно из-за общих артефактов. [Покрытие и границы](TESTING.md).

## Рабочий сценарий для прототипа

По запросу пользователя конкретизировать одну отрасль и документ ассистентом предложен [SCN-001](SCENARIO.md): печать согласованного изображения на готовой упаковке заказчика, акт приёмки печатных работ по всей партии и один полный расчёт. Выбор позволяет связать один результат с одним документом и сохранить границу MVP; спрос, готовность резервировать всю сумму и работа без аванса не доказаны.

Это рабочее предложение для детализации, не выданное за решение пользователя или вывод интервью. Самозанятые остаются дополнительным сегментом исследования. Для реального ЭДО форму документа и событие оператора нужно подтвердить отдельно.

## Конкретизация первого прототипа

Этап `feature/deal-agreement` реализует редактирование условий до резерва, PDF и два явных согласия, затем возврат из AGREED в новую DRAFT. `document_id` стабилен для сделки; версии PDF и условий независимы. Согласие закрепляет точные версии и SHA-256, а изменение условий или PDF убирает прежние согласия из текущего состояния, сохраняя историю. Доступ к историческому PDF требует одновременно текущего участия в сделке и участия в соответствующей исторической версии. Согласие не является тестовой подписью и не двигает деньги.

Этап `feature/deal-drafts` добавляет только создание и чтение черновиков. Длина названия 1–200, описания 1–5000 символов и предел JSON 16 KiB конкретизируют исходный контракт. Срок нормализуется в UTC до микросекунд PostgreSQL; статус просроченного черновика вычисляется по времени запроса БД. Семантический отказ сохраняется вместе с аудитом команды без вымышленного ID сделки; успешное создание — со снимком условий, аудитом и pending outbox. Доставки уведомлений и механизма A19 на этом этапе ещё нет.

Подробности — в [TZ.md](TZ.md). В рамках делегированного проектирования выбраны React / Vite, ORG_OWNER новой учебной организации и отдельный DEMO_OPERATOR, серверные cookie-сессии, SQL / pgx, общий UnitOfWork и outbox. Денежные поля JSON — десятичные строки, int64 / BIGINT в хранении; это уточнение раннего черновика для точной работы TypeScript.

Окончательный учебный PDF закрепляется до резерва. После резерва замена запрещена. Запрос отмены блокирует выплату; отказ и просрочка переводят на проверку, без автоматического возврата или продолжения. Сброс демонстрации создаёт новый учебный сценарий и сохраняет старую историю. Эти решения не являются выводами интервью.

ТЗ содержит требования к продукту и приёмке; сведения об инструментах разработки в него не включать.

После согласия пользователя продолжить обсуждение разобрана [модель данных и транзакций](DATA_MODEL.md): версия условий отделена от версии строки, история согласий / подписей сохраняется, выплата потребляет свой резерв, денежный отказ отличается от инфраструктурного rollback. Противосчёт учебной эмиссии, точный набор таблиц и режим транзакций описаны как проектная конкретизация; миграций и проверенного кода ещё нет. Обсуждение внешнего урегулирования споров не стало решением добавить собственный арбитраж или частичные выплаты.

## Аргумент в пользу цифрового рубля

Исследуем условные расчёты через общую инфраструктуру цифрового рубля и перспективную ПКСК. Доверенное событие должно запускать согласованный сценарий исполнения.

Условная автоматизация возможна и на обычных банковских деньгах. Нужно доказать ценность выбранной инфраструктуры: стоимость обработки, число ручных проверок, время расчёта и путь к межбанковому сценарию. Тезис «это технически возможно только с цифровым рублём» не принят.

В [сравнении альтернатив](ALTERNATIVES.md) разделены тариф перевода, полная стоимость услуги и отвлечение средств. Преимущество по цене пока не доказано: обычный перевод может входить в пакет без добавочной комиссии; опубликованный пример аккредитива относится к специальным условиям. Гипотеза продукта — сокращение ручного запуска расчёта при видимом резерве, а не обещание самой дешёвой платёжной операции.
