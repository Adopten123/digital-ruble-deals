# Модель данных и транзакций «ПоАкту»

Исходная модель: 19 октября 2026 года. На 22 октября миграции 001–005 реализуют основу, версии условий / PDF, согласия / доработку, резерв и операторский ledger. Выплата, подписи, ЭДО, освобождение, спор и независимый A19 остаются проектом; соответствующие разделы ниже не означают готовность кода. Требования — [TZ.md](TZ.md), фактическая схема — [ARCHITECTURE.md](ARCHITECTURE.md), внешний контракт — [API.md](API.md). Окончательная схема закрепляется миграциями.

## Границы модели

Несколько независимых B2B-сделок; у каждой одна сумма, один актуальный акт и не более одной полной выплаты. Деньги и подписи учебные. Пример: заказчик имеет 50 000 000 копеек, сделка — 30 000 000, исполнитель начинает с нуля.

Сервис `deals` отвечает за условия и согласования. `documents` — за PDF и факты подписей. `settlement` — за счета, резервы, проводки и координацию денежного решения. Они используют один UnitOfWork и одну PostgreSQL-транзакцию, когда операция затрагивает несколько областей. Отдельных commit в этих модулях внутри выплаты нет. Арбитраж, частичное распределение денег и возобновление спорной выплаты этой конкретизацией не добавляются.

## Данные и версии

| Область | Основные записи | Связи и ограничения |
|---|---|---|
| Пользователи и доступ | `users`, `organizations`, `memberships`, `sessions` | Организация из сессии; один владелец не получает членство в чужой организации по её названию |
| Сделка | `deals`: ID, `deal_version`, `row_version`, status, даты первого резерва и изменения | Ссылается на актуальную версию условий; `row_version` — внутренний технический счётчик |
| Условия | `deal_versions`: стороны, сумма / RUB, описание, срок, ссылка на версию документа | Неизменяемый снимок; уникальны сделка + номер версии; стороны различаются |
| Согласования | `agreements`: сторона, actor, версия сделки, ID / версия / SHA256 документа, время | Одно согласие организации на конкретную версию; исторические согласия не удаляются |
| Документ | `documents` — идентичность акта сделки; `document_versions` — неизменяемые байты / путь, SHA256, размер, версия | Один документ сделки, несколько версий; уникальны документ + версия; версия связана с конкретными условиями |
| Подписи | `signatures`: actor, организация, сделка / версия, документ / версия / SHA256, время | Одна подпись организации для конкретного основания; подпись не меняет PDF |
| Счета | `accounts`: организация либо системное назначение, RUB, `total_kopecks`, `reserved_kopecks` | Один клиентский RUB-счёт организации; ограничения остатков и проверка переполнения |
| Резерв | `reserves`: сделка, версия, счёт заказчика, сумма, `ACTIVE / CONSUMED / RELEASED` | Один резерв за весь жизненный цикл сделки; повторное финансирование завершённой сделки не требуется |
| Проводки | `ledger_batches`, `ledger_entries`: основание, счета, знаковые изменения в копейках | Каждая пачка сбалансирована; опубликованные проводки не редактируются и не удаляются приложением |
| Расчёт | `settlements`: сделка, резерв, основание подписи, batch, время | Уникальны сделка, резерв и расчётный batch; не более одной выплаты |
| Блокирующие факты | `disputes`, `cancellation_requests`, `cancellation_consents` | Спор и запрос отмены хранятся независимо от отображаемого status; не более одного активного запроса отмены |
| Повторы и доставка | `idempotency_keys`, `event_inbox`, `outbox` | Область ключа и хеш тела; уникальны source + event_id; outbox-задание двусторонней подписи уникально по основанию |
| История | `audit_events`, голова цепочки, `notifications` | Аудит входит в предметную транзакцию; уведомления доставляются после commit, без дублей |

`deal_version` растёт при изменении согласуемых условий / активного PDF либо явном возврате на новый раунд согласования. Обычное согласование, подпись, резерв и переход состояния её не увеличивают. `row_version` меняется при фактическом обновлении агрегата сделки, включая подписи и состояние; не меняется от простого повтора сохранённого результата. Он не подменяет денежные блокировки.

По текущему API `expected_version` в PATCH означает именно `deal_version`; поле не переименовывается этой запиской. При интерактивном создании черновик имеет версию 1, первая загрузка / генерация акта создаёт версию условий 2 и версию документа 1. Далее стороны подписывают фактические версии из ответа сервера, а не константу из демонстрационного JSON. При генерации PDF номер согласуемых условий в нём должен соответствовать новой версии, которую операция собирается сохранить.

«Сбросить согласия / подписи» означает не учитывать старые факты для новых условий. Прежние записи остаются в истории. В рамках MVP подписи возможны только после резерва, когда смена условий уже запрещена. Ссылки и ограничения БД должны исключать привязку документа другой сделки или версии; одного совпавшего имени файла недостаточно.

Конкретизация для защиты от устаревшего акта: фактический PATCH условий сбрасывает ссылку новой версии на активный PDF, сохраняя прежний файл в истории. Для нового согласования нужен заново загруженный / сгенерированный документ; без него — DOCUMENT_REQUIRED. Сгенерированный акт отражает актуальные поля и новую версию. Для загруженного PDF сервер проверяет формат, байты и привязки, но не обещает автоматическую смысловую сверку текста с суммой и предметом сделки: соответствие проверяют стороны перед явным согласием.

Пользователь утвердил rework из AGREED до первого резерва. Он создаёт новую версию с прежними условиями, снимает активный PDF и переводит в DRAFT. Старые записи agreements / document_versions сохраняются, но для нового основания не подходят. Причина, actor, старый / новый номера входят в аудит. Отдельный счётчик «раунда согласий» не нужен: уникальность фактов по deal_version уже разделяет раунды. Детали и матрица — в [STATE_MACHINE.md](STATE_MACHINE.md).

## Учёт средств

Для клиентского счёта:

```text
total = сумма опубликованных ledger_entries счёта
reserved = сумма ACTIVE-резервов счёта
available = total - reserved
0 <= reserved <= total <= MaxInt64
```

`total` и `reserved` — разные транзакционно обновляемые проекции. `available` вычисляется, отдельно не накапливается. Каждая операция проверяет диапазон до арифметики. Сверка проекций с проводками / резервами входит в проверки; одна строка CHECK не проверяет равенство с другими таблицами.

Проектное предложение: у учебной эмиссии отдельный системный противосчёт. Начальное зачисление: клиенту `+50000000`, противосчёту `-50000000`. Его отрицательный остаток обозначает источник учебных средств; он недоступен участникам. Исключение не распространяется на клиентские счета. Служебное списание оператора зачисляет деньги фиксированному системному счёту, не произвольному получателю. Никакой реальной эмиссии или банковской операции нет.

В MVP у денежной пачки две записи разных счетов одной валюты с равными противоположными значениями. Например, выплата: заказчик `-30000000`, исполнитель `+30000000`. Начальное зачисление также имеет пачку и устойчивый уникальный ключ bootstrap, поэтому рестарт не повторяет его.

Резервирование и освобождение резерва не меняют владельца денег и не создают фиктивных денежных проводок: меняются reserve, проекция reserved, состояние сделки, аудит и outbox. Выплата погашает собственный резерв и создаёт денежную пачку одной транзакцией.

Для схемы реализации нужны CHECK / FK / UNIQUE и проверка баланса пачки при завершении транзакции, например deferred constraint trigger, с интеграционными тестами. Межстрочную сумму нельзя объявлять обычным CHECK. Это защита штатного приложения и обычной роли БД; вмешательство суперпользователя рассматривается отдельно по A19. См. [ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

## Транзакционные команды

Каждая команда сначала проверяет сессию / источник, права, форму и область ключа. В таблице перечислены предметные изменения; сохранённый результат команды, аудит и задания outbox входят в тот же commit, где применимо.

| Команда | Проверки под блокировкой сделки | Что фиксируется вместе |
|---|---|---|
| Создать / изменить черновик, заменить PDF | Права заказчика, актуальная версия, допустимое состояние, отсутствие прежнего резерва | Сделка / новая неизменяемая версия; PATCH условий снимает активную привязку PDF; загрузка создаёт новую версию документа; история прежних согласий сохраняется |
| Согласовать | Актуальные условия и точный документ, своя сторона, срок, допустимое состояние | Факт согласия; при втором согласии AGREED |
| Вернуть на доработку | Участник, AGREED, текущая версия, до первого резерва и срока, без блокирующих фактов | Новая версия без активного PDF, DRAFT, причина / actor / история, результат и уведомления; деньги не меняются |
| Зарезервировать | AGREED, два согласия, текущая версия, срок, доступный остаток | ACTIVE-резерв, reserved заказчика `+30000000`, FUNDED, дата первого резерва |
| Подписать | FUNDED / READY_TO_SETTLE, нужные версии / хеш, своя сторона, срок, отсутствие блокирующих фактов | Факт подписи; при второй READY_TO_SETTLE и одно задание ЭДО |
| Обработать событие | Все привязки и сохранённые подписи; затем право на новое исполнение, срок, активный резерв | Единственный settlement / batch / две проводки, оба total, reserved заказчика, CONSUMED-резерв, SETTLED, финальный inbox |
| Открыть спор | Доступное нетерминальное состояние по API | Факт спора и блокировка выплаты; деньги не перемещаются; активный запрос отмены не теряется |
| Запросить отмену | Нетерминальная сделка, нет другого активного запроса | Запрос и согласие инициатора, блокировка выплаты |
| Принять отмену | Другая организация, актуальный активный запрос, расчёт ещё не выполнен | Второе согласие; RELEASED-резерв и reserved `-30000000`, REFUNDED; без резерва — CANCELLED |
| Отклонить отмену / обработать срок | Актуальные факты под блокировкой | REVIEW_REQUIRED; никакой автоматической выплаты или освобождения |

Суммы в таблице относятся к примеру; в реализации берутся из проверенного основания. Правила допустимых исходных состояний сохраняются из API. `status` — сводное состояние, а не единственный источник разрешения выплаты: проверяются также отдельные факты спора, запроса / отказа отмены, срока и состояния резерва. После SETTLED / CANCELLED / REFUNDED возврата к обычному пути нет.

На второй подписи сохраняются устойчивые `event_id`, время события и все привязки к условиям и подписям. Outbox не восстанавливает смысл события из позднее прочитанной карточки. Исходные байты тела фиксируются до первой доставки и сохраняются для повторов; обновляются только транспортные timestamp и HMAC. Сетевого вызова внутри транзакции подписи нет.

## Денежные блокировки и гонки

Дисциплина получения блокировок: запись ключа команды либо inbox → сделка → затрагиваемые счета по возрастанию ID → резерв → остальные необходимые предметные записи. Порядок работы с подчинёнными записями внутри каждого вида команды фиксируется при реализации; каждая команда конкретной сделки сначала держит её блокировку. Операция без сделки получает счета в том же порядке и не начинает затем блокировать сделки. Аудитная голова берётся последней после подготовки остальных записей; после неё не получают новых предметных блокировок, в том числе неявно через FK / триггеры.

Проверка обычного списания: `total - reserved >= amount`. При выплате проверяется собственный ACTIVE-резерв нужной сделки, версии, счёта и суммы; затем атомарно `total -= amount` и `reserved -= amount`. Требовать `available_before >= amount` для такой выплаты ошибочно: у заказчика в примере доступно только 20 000 000, но 30 000 000 уже зарезервированы для этой сделки. После выплаты должно сохраняться `total_after >= reserved_after`, включая резервы других сделок.

Проектный режим — READ COMMITTED с явными блокировками всех путей изменения. Состояния повторно читаются под блокировкой; чтение до неё не разрешает выплату. Обнаруженный дедлок или ошибка до commit требуют отката всей транзакции; разрешён ограниченный повтор целой операции с прежним ключом. Неясный исход commit обрабатывается отдельно, как описано ниже. Проверять это необходимо на PostgreSQL, не только на mock. Основание: [блокировки](https://www.postgresql.org/docs/current/explicit-locking.html) и [изоляция транзакций](https://www.postgresql.org/docs/current/transaction-iso.html).

Срок проверяется по текущему серверному времени после ожидания блокировок перед решением о новом исполнении. `occurred_at` от источника не продлевает срок. PostgreSQL `now()` возвращает время начала транзакции; для этой проверки нужен актуальный замер, например `clock_timestamp()`. Время решения не выдаётся за точное время commit; старое время начала транзакции не разрешает выплату после долгого ожидания. См. [функции времени PostgreSQL](https://www.postgresql.org/docs/current/functions-datetime.html).

Спор и выплата сериализуются через одну сделку. Если commit спора произошёл первым, новая выплата блокируется. Если расчёт уже зафиксирован, поздний спор не удерживает уже выплаченные средства. Выплата и освобождение резерва конкурируют за те же записи и не могут завершиться вместе. Другая сделка той же организации дополнительно конкурирует за её счёт, поэтому два независимых deal_id не позволяют потратить одни средства дважды.

## Результат команды и откат

`WithinTx` должен различать сохранённый предметный результат и ошибку, требующую rollback. Предлагается `Outcome{HTTPStatus, Body}` отдельно от Go error:

- Успех: все изменения и Outcome фиксируются одной транзакцией, HTTP-ответ отправляется только после commit.
- Предметный отказ после установления прав / области ключа: до денежных изменений сформировать отказ, сохранить Outcome и аудит, вернуть из транзакционной функции `nil`, затем отдать, например, 422. Если нужен переход в REVIEW_REQUIRED из-за срока, он фиксируется явно в той же транзакции.
- Ошибка SQL или соединения до отправки commit: прервать операцию и откатить транзакцию; при потере соединения дождаться её завершения на стороне БД. Нельзя проглатывать SQL-ошибку или закоммитить частичные денежные изменения ради сохранения отказа. Неожиданный отказ после мутаций требует их отката; все ожидаемые предметные проверки выполняются до них.
- Потеря связи во время commit: исход может быть неизвестен, а успешный результат уже сохранён. Попытка rollback не отменяет состоявшийся commit. Вернуть неподтверждённый / временно недоступный результат; на новом соединении читать или повторять по прежнему ключу, чтобы установить факт фиксации. Новый денежный ключ по одному таймауту не создавать.
- Прежний ключ и прежнее нормализованное тело: вернуть зафиксированный результат без повторного действия; права всё равно проверить. Другое тело — конфликт, первоначальный результат не перезаписывается. Для новой осознанной попытки после сохранённого отказа нужен новый ключ.

У inbox два этапа: после проверки HMAC / схемы долговременно принять `(source, event_id, raw_body_hash, body)` как PENDING; затем в транзакции обработки заблокировать inbox и выполнить предметное решение. Незавершённый PENDING после сбоя доступен для повтора и не означает успех. Финальный результат inbox, в том числе семантический отказ, фиксируется вместе с решением. Прежний отказ позже не превращается в выплату при повторе того же события.

Другой валидный event_id для уже исполненной сделки после проверки исходных привязок возвращает `already_settled` и прежний payment_id. Он не создаёт проводок и не начинает новый расчёт. Потеря HTTP-ответа не означает отсутствие commit: клиент повторяет исходную команду или читает её результат.

## Файл и БД

Файловый volume не является частью PostgreSQL-транзакции. PDF проверяется и сохраняется под новым серверным неизменяемым путём до фиксации метаданных; внутри транзакции повторно проверяются ожидаемая версия и права. При конфликте файл может остаться невостребованным — его уборка выполняется отдельно с запасом времени и проверкой отсутствия ссылок. Нельзя фиксировать доступный документ, ссылающийся на ещё не сохранённый файл, или перезаписывать байты старой версии. Отметки новых подписей отображаются рядом с PDF и не меняют его хеш.

## Что проверить перед признанием модели рабочей

1. A04 / A08: новая версия условий не удаляет историю; старые согласия и другой PDF не подходят; одна подпись не меняет деньги.
2. A05 / A06: два резерва по 30 000 000 при total 50 000 000 дают один успех; конкурирующее обычное списание не расходует резерв. Штатная выплата собственного резерва при available 20 000 000 проходит.
3. A07 / A11 / A18: одинаковые команды / события / параллельные доставки создают один результат; другое тело конфликтует; сбой после приёма inbox и потеря ответа не создают второй расчёт. Проверяется сохранение отказов после рестарта.
4. A09: после выплаты заказчик total 20 000 000 / reserved 0, исполнитель total 30 000 000; пачка сбалансирована; проекции совпадают с исходными записями.
5. A12 / A13 / A14: спор, отмена, расчёт и срок не дают несовместимых результатов; ожидание блокировки не использует устаревшее время; два голоса одной организации не заменяют две стороны.
6. A16 / A19: рестарт сохраняет факты и результаты; внешний эталон выявляет предусмотренные изменения закреплённого состояния, с границами из архитектуры.

Это план проверок, не отчёт об их выполнении. Переходы и отображаемые действия описаны в STATE_MACHINE.md; далее фиксируются миграции, общий контракт и каркас по HANDOFF.md.
