# Frontend «ПоАкту»: руководство разработчика

Обновлено: 24 октября 2026 года. React-интерфейс поддерживает авторизацию, организации, версии условий / PDF, два согласия, доработку до первого резерва, полный резерв, две тестовые подписи и выплату после проверки ЭДО. Участники открывают спор и согласовывают отмену двумя разными организациями. Оператор управляет учебными счетами и отправляет проверочные события ЭДО. Уведомления, экспорт истории и A19 остаются следующими этапами. Пользовательские действия — в [MANUAL_TESTING.md](MANUAL_TESTING.md); HTTP-контракт — в [справочнике API](api/README.md) и [OpenAPI](api/openapi.json).

## Стек и запуск

React / React DOM 19.3.1, TypeScript 7.0.2, Vite 8.3.4; Playwright 1.64.1. Версии закреплены в [package.json](../web/package.json) и lock-файле. Node.js — ветка 22, не ниже 22.19.0; в контейнере 22.23.3. Используется npm. Router, Redux, React Query, UI-kit и сторонние денежные библиотеки не подключены.

Из корня репозитория:

```sh
npm --prefix web ci --ignore-scripts
npm --prefix web run dev
```

Dev server слушает loopback; открывать `http://localhost:5173`. Backend должен быть запущен с `HTTP_ADDR=127.0.0.1:8081`, `APP_ORIGIN=http://localhost:5173` и отдельной учебной БД. Инициализация / миграции / ключи — в [RUNNING.md](RUNNING.md). Backend не запускается командой npm. Без него интерфейс покажет ошибку подключения, а не вымышленные данные.

Vite проксирует `/api/v1`, `/healthz`, `/readyz` на `127.0.0.1:8081`. `APP_ORIGIN` обязан совпадать с адресом вкладки, включая hostname / порт; Vite proxy сохраняет браузерный Origin. Смена `localhost` на `127.0.0.1` требует соответствующей настройки backend и даёт другое cookie-хранилище. Публичных VITE_* переменных, секретов или настраиваемого внешнего API URL в клиенте сейчас нет.

Для отдельного QA-стенда `npm --prefix web run dev:e2e`: строгий порт 18080, proxy на 18081; backend origin `http://localhost:18080`. Не направлять тесты на рабочую БД. При сборке / dev сначала автоматически готовится локальный Swagger `/api-docs/`.

## Навигация и компоненты

Маркировка `key={session.user.id}` размонтирует старый кабинет при смене пользователя. Swagger — отдельная статическая страница, его deep links не являются маршрутами приложения.

## Загрузка сессии и смена аккаунта

1. App одновременно запускает `/auth/me` и `/readyz`. `401` от me означает экран входа; прочий отказ — bootstrap-ошибка с повтором.
2. После me/login/register ApiClient связывается с показанным `user.id`; новая сессия очищает старый CSRF-кеш. В ответе login/register есть csrf_token, но текущий клиент дополнительно получает актуальный токен через `/auth/csrf`.
3. Все защищённые чтения, включая PDF, изменяющие команды и logout получают `X-Expected-User-ID`. `/auth/me`, `/auth/csrf`, login/register используются для обнаружения / смены сессии без него.
4. При `401` защищённого запроса кабинет скрывается, токен очищается, показан вход. `SESSION_CHANGED` либо `CSRF_INVALID` вызывает перечитывание сессии с сообщением; команда автоматически не повторяется.
5. Logout показывает успешный выход только после 204. При 503 сохраняется настоящий контекст и ошибка; после восстановления можно повторить действие.

Cookie браузера общие для вкладок, sessionStorage — нет. Поэтому нельзя считать видимый заголовок доказательством того, кто исполнит следующий запрос. Привязку ID захватывать **до** асинхронного CSRF. Поколение токена не позволяет старому запросу вернуть прежний токен, снять новый запрос получения CSRF или очистить новый кеш поздним 401. sessionRevision защищает App от устаревших завершений bootstrap / logout / входа. Мгновенной синхронизации вкладок через BroadcastChannel нет: конфликт обнаруживается на следующем защищённом обращении.

В DealAgreement подготовка PDF асинхронна: до вычисления SHA-256 / сверки файла сохраняются поколение компонента и `api.currentIdentity()`. После ожидания оба значения проверяются до записи команды, отправки и обновления интерфейса. Уход с карточки или смена показанного аккаунта не должны превращать подготовленный запрос в команду другого пользователя. HTTP-заголовок ожидаемого пользователя остаётся дополнительной серверной проверкой и не назначает владельца ресурса.

## ApiClient и ошибки

Клиент использует относительный `/api/v1`, `credentials:'same-origin'` и `Accept: application/json`. mutate добавляет CSRF, JSON Content-Type при наличии тела и Idempotency-Key для доменных команд. PATCH отправляется методом PATCH; остальные изменяющие операции карточки — POST. CSRF получают и кешируют в памяти; одновременные обращения используют один Promise. Метод logout отправляет полностью пустое тело. Загрузка PDF использует FormData с `expected_deal_version` и `file`; Content-Type вручную не задаётся, чтобы браузер сформировал корректную multipart-границу.

TypeScript-типы описывают Session, Organisation, OwnOrganisation, Counterparty, Page, CreateDealInput, Deal, DealFilters, а также UpdateDealInput, AgreeDealInput, ReworkDealInput, GenerateDocumentInput, DocumentResult, DealDocument и DealAgreement. Для денежного этапа добавлены DealReserve, ReserveDealInput / ReserveResult и DemoAccount / DemoMoneyInput / DemoMoneyResult. `Deal.document` — null либо метаданные PDF; `agreements` содержит типизированные согласия с привязкой к организации, пользователю, версии условий, ID / версии / SHA-256 документа. `Deal.reserve` — null либо `{id, deal_id, deal_version, account_id, amount_kopecks, currency, status, created_at}`, status резерва — ACTIVE / CONSUMED / RELEASED; Deal содержит payment_id, типизированные dispute / cancellation_request и независимые review_reasons. DemoAccount содержит организацию и три строковых остатка. Типизация успешного JSON — не полноценная проверка схемы во время исполнения: отдельно проверяются деньги / остатки и сохранённые команды. Не добавлять доверие к произвольным данным только потому, что они приведены к типу.

OpenAPI 0.5.0 содержит 32 HTTP-операции: 31 браузерную, включая health / readiness, и внутреннюю обработку ЭДО. Последняя не вызывается ApiClient. ApiClient предоставляет updateDeal, uploadDocument, generateDocument, agreeDeal, reworkDeal, document и documentFile; последний выбирает отдельные маршруты view / download. Для подписи добавлен signDocument. Спор и отмену обслуживают openDispute / requestCancellation / decideCancellation, операторскую очередь и polling — queueEDO / edoEvent. Для денег добавлены reserveDeal, demoAccounts и demoMoney с выбором credits / debits. Полное описание запросов и ошибок поддерживается в OpenAPI, а не дублируется в компонентах.

`ApiError` содержит status, code, requestId. `parseApiError` выдерживает не-JSON ошибку как UNKNOWN_ERROR; `describeError` показывает понятное сообщение, для сетевого TypeError — отсутствие связи. Серверные request ID видны пользователю как код обращения. Успешный 204 не разбирается как JSON; невалидный успешный JSON выдаёт ошибку. Это важно для неизвестного исхода команды.

При добавлении запроса следовать существующему порядку:

```ts
// Компонент передаёт только условия. Субъект и права определяет сервер.
const page = await api.deals({ role: 'customer', status: 'DRAFT' });
const deal = await api.deal(page.items[0].id);
```

В реальном коде сначала проверить наличие items и обработать loading/error/empty. Не перехватывать ошибку, чтобы вернуть вымышленные успешные данные. Кнопка повтора чтения допустима; повтор изменяющей команды требует сохранённых условий и идентичности запроса.

## Деньги, текст и время

`rublesToKopecks` принимает строку рублей с точкой / запятой и максимум двумя дробными знаками. Пробелы внутри, ведущие нули, минус, экспонента и округление не допускаются. Расчёт выполняется BigInt; результат JSON — строка. `parseKopecks` проверяет каноническую неотрицательную строку и предел int64. `formatRubles` группирует целую часть, не пропуская её через Number. `validateBalances` проверяет `total − reserved = available`.

Создание: title 1–200, description 1–5000 Unicode-символов, deadline в будущем, тело не более 16 KiB UTF-8. Регистрация: имя 2–200, пароль 12–128 Unicode-символов. JavaScript `.length` и HTML maxLength считают UTF-16; бизнес-длину считать `[...value].length`. Поэтому HTML допускает до 400 / 10000 единиц для 200 / 5000 кодовых точек; сервер остаётся окончательным валидатором. Поиски сохраняют полное Unicode-значение и сервер ограничивает 200 символами.

Поле datetime-local относится к часовому поясу браузера и переводится через toISOString в UTC; рядом показывается зона. При редактировании неизменённое минутное поле сохраняет исходный `deadline_at` целиком, включая секунды / микросекунды: смена названия не должна побочно округлять срок. Срок в карточке форматируется локально. Для дат фильтра `dateBoundary` строит начало дня и последнюю микросекунду конца дня; нельзя считать местную полночь UTC-полуночью. UI и фильтр списка учитывают DRAFT / AGREED / FUNDED / READY_TO_SETTLE / REVIEW_REQUIRED. Истёкший срок не доказывает выполнение работ.

## Условия, документ и два согласия

Заказчик может редактировать DRAFT: название, описание, сумму, срок и исполнителя. Заказчик самой сделки не меняется. PATCH содержит `expected_version`; при смене исполнителя прежняя организация теряет доступ по серверным правилам. Общий SupplierPicker исключает заказчика и позволяет различать организации по ID. Изменение условий создаёт новую редакцию и снимает активный документ / согласия; неизменённые условия не требуют искусственно увеличивать версию.

Заказчик добавляет PDF либо выбирает «Сформировать акт» с фиксированным `template_id: printing-acceptance-v1`. Клиент до отправки проверяет расширение / MIME, непустой размер до 5 МиБ, начальную сигнатуру `%PDF-` и вычисляет SHA-256. Полноценная проверка структуры и активного содержимого выполняется сервером. Клиентская сигнатура не доказывает безопасность файла. Загрузка / генерация привязана к ожидаемой версии условий; замена PDF создаёт новую версию и сбрасывает согласия. ID документа сохраняется для сделки, `document_version` растёт; карточка показывает имя, размер, версию условий, версию PDF и SHA-256 из ответа сервера.

Для согласия пользователь явно отмечает checkbox, затем нажимает «Согласовать документ». Запрос содержит снимок четырёх полей: `deal_version`, `document_id`, `document_version`, `document_sha256`. Без актуального PDF либо с PDF прежних условий локальная команда не собирается. Отмеченный checkbox сам по себе не создаёт согласия; учитывается результат сервера. В списке сторон согласие показывается только при совпадении всех четырёх привязок. Одно согласие оставляет DRAFT, второе переводит сделку в AGREED. Согласование не является электронной подписью, резервом или выплатой.

Из AGREED каждая сторона может выбрать «Вернуть на доработку», указать причину до 2 000 Unicode-символов и подтвердить действие. Новая версия DRAFT не имеет активного PDF / согласий; прежние данные остаются в серверной истории. Нужны новый документ и два новых согласия. UI показывает действия по роли и состоянию, но срок, блокировки, полномочия и допустимость перехода заново проверяет API.

VERSION_CONFLICT, INVALID_STATE, DEADLINE_PASSED, DOCUMENT_MISMATCH или CONSENTS_MISSING блокируют новые команды до явного «Обновить» вверху карточки. Обновление получает актуальные условия / PDF и сбрасывает старое состояние checkbox. REVIEW_REQUIRED закрывает редактирование и согласование; просмотр доступного PDF сохраняется. После резерва также закрыты редактирование / замена PDF / доработка. Кнопок выплаты, подписи за контрагента и автоматического арбитража здесь нет.

## Резерв и три остатка

DealReserve показывает полную сумму сделки обеим сторонам. «Зарезервировать всю сумму» доступно заказчику из AGREED до срока, если текущий PDF совпадает с версией условий и есть два согласия разных сторон на этот же ID / версию / SHA-256. Клиент собирает только `{deal_version}`; сумму, счёт и полномочия заново определяет сервер. Успех возвращает `{reserve, deal}` со статусом FUNDED, не увеличивая версию согласованных условий. Резерв виден заказчику и исполнителю; исполнитель денег пока не получает.

Для заказчика отдельный GET ownOrganisation получает актуальные `total_kopecks`, `reserved_kopecks`, `available_kopecks`. reserveBalanceSnapshot проверяет равенство остатков, сравнивает сумму и считает поясняющий остаток после резерва только через BigInt. Общий остаток при резерве не уменьшается: например, 500 ₽ / 0 ₽ / 500 ₽ превращаются в 500 ₽ / 300 ₽ / 200 ₽. Показанный снимок **не разрешает и не запрещает** серверную операцию: деньги могли измениться в соседней вкладке или после действия оператора. Недостаток на снимке выводится пояснением, а окончательный отказ INSUFFICIENT_AVAILABLE_FUNDS определяется сервером под блокировкой счёта.

После успешного резерва / повтора клиент перечитывает текущую сделку и остатки. После отказа резерва также обновляется снимок счёта. Переход к «Мой счёт» выполняет новый GET. При неизвестном исходе сохранённая команда остаётся; заголовок карточки прямо сообщает, что средства уже могли быть закреплены, и не называет их свободными. Карточка проверяет соответствие показанного ACTIVE-резерва ID / версии сделки, валюте и полной сумме.

## Учебные счета оператора

Вкладка «Учебные счета» появляется только при `session.user.system_role === DEMO_OPERATOR`. Поиск идёт по ID счёта, ID / названию организации; клиент передаёт q, limit=20 и непрозрачный cursor. Первая страница заменяет items, следующая добавляется; смена q не переносит старый cursor. Все полученные счета проверяются на RUB и согласованность трёх остатков. Выбор строки открывает сумму, основание и credits / debits; полная сумма в рублях преобразуется в копейки через BigInt. Основание обязательно, до 2 000 Unicode-символов.

Зачисление и служебное списание возвращают `{transaction_id, account}`. Они изменяют тестовый реестр, а не платят исполнителю сделки. Служебное списание идёт на системный учебный счёт; активные резервы не расходуются. Клиент не вычисляет право списания по прежнему остатку. После конкурентного резерва сервер может отклонить сумму, которая выглядела допустимой на экране; интерфейс показывает отказ и перечитывает текущий счёт.

После успеха / сохранённого повтора DemoAccounts не подставляет `account` из исторического ответа: выполняется отдельный GET списка с q=ID и выбирается точное совпадение ID. Так отображается нынешний остаток, даже если после первой команды уже было другое зачисление. Для ответа проверяются поколение компонента и соответствие `api.currentIdentity()` исходному userId. inFlight дополняет блокировку кнопок, а защищённый HTTP-запрос несёт X-Expected-User-ID. Права оператора всегда проверяет сервер.

## Просмотр и скачивание PDF

documentFile выполняет защищённый fetch с `Accept: application/pdf`, cookies, `X-Expected-User-ID` и обязательным номером версии. Ошибка обрабатывается через ApiError; успешный ответ с другим Content-Type не открывается как PDF. Метаданные доступны отдельным методом document с необязательным параметром version, но карточка получает их вместе со сделкой.

«Открыть PDF» сначала получает байты `/documents/{id}/view?version=N`, затем показывает обычную ссылку «Открыть загруженный PDF» на Blob URL с `target=_blank` / `rel=noopener noreferrer`. Два явных действия обходятся без программного popup и iframe. «Скачать PDF» аналогично получает `/download?version=N` и показывает ссылку с download / исходным именем. Прямой публичной ссылки на файловое хранилище нет. Blob URL освобождаются при смене документа / версии и размонтировании; устаревший асинхронный ответ не публикуется в новой карточке или аккаунте. PDF хранится на сервере отдельно от frontend-статики; его путь и DOCUMENTS_DIR не передаются браузеру.

## Надёжное создание и восстановление

До POST CreateDeal сохраняет в sessionStorage запись `poaktu:pending-deal:<organisationId>`:

```ts
interface PendingDealAttempt {
  key: string;               // crypto.randomUUID(), создаётся один раз
  input: CreateDealInput;    // точные нормализованные условия
  supplier: Counterparty;   // отображение выбранного исполнителя
}
```

При невозможности записи в storage команда **не отправляется**. При busy либо pending поля блокируются; явный повтор использует прежнее input/key. Не очищать запись при reload, переходе назад, сети / 503, CSRF / смене аккаунта или конфликте ключа. Закрытие вкладки может уничтожить sessionStorage; это не серверная очередь и не резервная копия. При его потере сначала проверить список, не делать автоматическую новую отправку.

`readPendingDeal` проверяет JSON, ключ, обязательные поля, валюту, сумму int64, календарную дату UTC, пределы текста / тела, совпадение исполнителя и отсутствие неизвестных полей input. Пустая строка и повреждённая запись блокируют новую команду; она не удаляется молча. Законная запись с прошедшим сроком сохраняется: исходный POST мог уже успешно завершиться.

После подтверждённого успеха запись удаляется только при совпадении её ключа с ответом; поздний ответ другой формы не удаляет новую команду. После окончательного семантического отказа код освобождает форму для новой команды. Текущий список окончательных кодов: INVALID_REQUEST, INVALID_AMOUNT, AMOUNT_OVERFLOW, DEADLINE_PASSED, RESOURCE_NOT_FOUND, IDEMPOTENCY_KEY_REQUIRED; AMOUNT_OVERFLOW зарезервирован в клиенте, текущий сервер для переполнения возвращает INVALID_AMOUNT. Остальные случаи требуют выяснения результата. Сменивший аккаунт не получает pending другой организации; явное возвращение к исходному владельцу позволяет проверить прежнюю команду.

Не заменять эту логику общим retry(fetch). Таймаут не доказывает rollback; повтор с новым ключом способен создать вторую сделку. sessionStorage исходной организации не является доказательством прав — их заново проверяет API.

## Восстановление команд карточки

Создание черновика и команды уже существующей сделки используют разные записи. DealAgreement сохраняет одну активную команду по ключу `poaktu:pending-agreement:<organisationId>:<dealId>` до первого изменяющего запроса. В JSON находятся `key`, `dealId`, `kind` и точный `input`. kind принимает update / generate / agree / rework / upload / reserve. Резерв сохраняет исходный `input: {deal_version}` и ключ, включая случай, когда после reload текущая карточка уже FUNDED. Запись отделена по организации и сделке; новая команда не перезаписывает уже сохранённую. При ошибке записи запрос не отправляется.

Для JSON сохраняются исходные версии / условия / причина целиком. Для upload сохраняется `input: {expected_deal_version, file_name, size_bytes, sha256}`. Байты PDF в sessionStorage не копируются. После reload пользователь открывает прежнюю сделку и повторно выбирает исходный PDF; до выбора повтор закрыт. Перед отправкой проверяются размер и SHA-256 выбранных байтов. Другой PDF даёт локальную ошибку без POST и изменения сохранённой команды. Идентичные байты можно выбрать под новым локальным именем: FormData всё равно использует сохранённое исходное `file_name`, прежние версию и Idempotency-Key. Случайная multipart-граница не является частью идентичности доменной команды.

readPendingAgreement проверяет тип команды, набор полей, область сделки, ключ, положительные версии, SHA-256, размер, условия и предел JSON. Повреждённая запись блокирует новые действия и не удаляется молча. Законная запись с истёкшим сроком сохраняется: сервер мог исполнить её до потери ответа. Async-подготовка / сверка PDF защищена поколением компонента и снимком показанного пользователя.

После неизвестного исхода, сети / 503, ошибки сессии / CSRF либо IDEMPOTENCY_CONFLICT запись остаётся. Повтор выполняется только явно через «Проверить результат команды». После подтверждённого успеха удаление сверяет ключ, чтобы старый ответ не удалил новый запрос. Затем **всегда выполняется GET актуальной сделки**: сохранённый идемпотентный ответ может описывать историческую версию и не должен возвращать её в интерфейс как текущую.

Окончательные отказы INVALID_REQUEST, INVALID_AMOUNT, AMOUNT_OVERFLOW, DEADLINE_PASSED, RESOURCE_NOT_FOUND, IDEMPOTENCY_KEY_REQUIRED, VERSION_CONFLICT, INVALID_STATE, DOCUMENT_REQUIRED, INVALID_PDF, INVALID_DOCUMENT, PAYLOAD_TOO_LARGE, UNSUPPORTED_MEDIA_TYPE, FORBIDDEN, INSUFFICIENT_AVAILABLE_FUNDS, CONSENTS_MISSING и DOCUMENT_MISMATCH освобождают сохранённую команду для исправления. При конфликте версии / состояния сначала требуется перечитать карточку. INVALID_DOCUMENT — действующий отказ серверной проверки PDF; он получил понятный перевод и окончательную обработку, чтобы отклонённая загрузка не запирала форму. INVALID_PDF сохранён как совместимый клиентский код. Исход определяет серверный ответ, а не предположение о том, что таймаут означает отказ.

Операторские записи хранятся отдельно: `poaktu:pending-demo-money:<userId>:<accountId>:<credits|debits>`. JSON содержит key / userId / accountId / accountName / operation / точный input. При открытии панели читаются только записи этого пользователя; проверяются ключ, область, операция, положительная int64-сумма, основание и неизвестные поля. Повреждённая запись блокирует новые операции этого пользователя. Пока есть неподтверждённая команда, новые денежные команды в панели закрыты, но каждую сохранённую можно явно проверить.

Сеть / 503, SESSION_CHANGED / CSRF_INVALID и IDEMPOTENCY_CONFLICT не очищают операторскую запись. После reload панель показывает исходные сумму / основание / счёт и кнопку «Проверить результат операции», без автоматического POST. Успех удаляет только совпадающий key и перечитывает текущий счёт. Определённые INVALID_REQUEST / INVALID_AMOUNT / AMOUNT_OVERFLOW / INSUFFICIENT_AVAILABLE_FUNDS / RESOURCE_NOT_FOUND / FORBIDDEN / IDEMPOTENCY_KEY_REQUIRED освобождают форму; неизвестный исход не заменяется новым ключом. Другой вошедший пользователь не получает чужую сохранённую команду.

## Асинхронные чтения и формы

Каталог / список / карточка / выбор исполнителя используют счётчик запроса. Ответ принимается, только если номер актуален; cleanup увеличивает его при размонтировании / смене параметров. Старый ответ не должен менять новый экран, ошибку или loading. AbortController сейчас не используется; запрос может закончиться на сервере даже после ухода с экрана. StrictMode в разработке дополнительно проверяет цикл effect/cleanup; не удалять защиту ради устранения повторного GET.

Поля поисковой формы и применённые фильтры разделены. Новая первая страница очищает предыдущие items/cursor; загрузка следующей добавляет результат. При смене фильтров старый курсор не переносится. Неверный период очищает прежнюю выдачу, чтобы она не выглядела результатом невалидного фильтра. Каталог принимает Enter и во время прежней загрузки. Enter в SupplierPicker перехватывается локально и не отправляет общую форму сделки; учитывается IME composition.

Loading, empty и error — отдельные состояния. Пустой ответ каталога допустим; сбой сети не означает отсутствие организаций. Кнопки submit блокируются на время команды; повторное нажатие не создаёт другой ключ. Доступность кнопки не заменяет серверную проверку.

## Стили и доступность

Один CSS-файл с общими переменными, компонентными классами и media queries; нет CSS-in-JS. Разметка использует label, fieldset, nav, заголовки, role=alert/status/search, aria-current и текстовые названия действий. Не делать критические действия только иконкой. Длинные ID / названия и большие суммы должны переноситься без обрезания значимого содержимого; описание сохраняет переводы строк.

Базовая автоматическая матрица 11 состояний × 17 ширин проверяет 187 сочетаний, пересечения соседей, выход за viewport, обрезание глифов и перехват кликов. Для согласованного документа добавлены отдельные проверки метаданных / согласий и сохранённой PDF-команды на 375 px. Эти проверки не заменяют browser zoom, физическую экранную клавиатуру, screen reader и проверку всех браузеров. Полная ручная инструкция — [MANUAL_TESTING.md](MANUAL_TESTING.md).

## Проверка и порядок изменений

Для функции обновить DTO / клиент, компоненты и состояния, локальную валидацию, этот документ и OpenAPI при изменении HTTP. Сначала typecheck, unit, docs:check, build; затем необходимые E2E на отдельном стенде. Добавлять регрессию для нового поведения / дефекта, не считать отсутствие ошибок компиляции полной приёмкой. Подробные команды / артефакты — [TESTING.md](TESTING.md).

Запуски E2E выполнять последовательно: состояние акторов и отчёты общие. Учитывать штатный лимит входов; тестовые помощники сессий используют уникальные аккаунты и явный повтор по Retry-After, не ослабляя сервер.

На предыдущем этапе резервов 22 октября выполнены 42 unit-теста, оба typecheck и production build. Пять focused UI-тестов + setup прошли за 10,3 с: FUNDED у двух сторон и обновление кабинета; недостаток средств / последующее зачисление; потеря ответа резерва после реального commit и reload; операторские поиск / пагинация / защита от списания конкурентного резерва; потеря ответа зачисления и чтение актуального остатка после replay. Новые тесты используют отдельные свежие организации и не расходуют исходные 500 000 ₽ общего демозаказчика. В тесте пагинации реальный сервер ограничен одной строкой на страницу через тестовый route.fetch, чтобы не создавать 21 лишнюю регистрацию; продуктовый limit=20 не меняется. Регистрационный помощник ограниченно повторяет запрос после 429 с соблюдением серверного Retry-After; защитные лимиты сохраняются.

Набор этапа резервов 22 октября прошёл: 90 проверок за 2,7 минуты (42 API + 47 UI + setup). Linux CI на `3911c7f` подтвердил 90 проверок за 3,1 минуты через Compose / nginx. Команда sign использует общий pending карточки с исходным documentId, точным телом и ключом под организацией / deal ID. Неизвестный исход блокирует новую команду до проверки прежней; logout / вход другой организации не переносят полномочия. После исторического ответа выполняется GET текущей сделки, поэтому повтор первой подписи не откатывает актуальные READY_TO_SETTLE / SETTLED / REFUNDED. Истечение срока скрывает новую подпись и сохраняет уже созданные факты и резерв.

## Спор, отмена и завершение расчёта

DealResolution показывает факты независимо от сводного статуса. REVIEW_REQUIRED не скрывает активную отмену, её инициатора / причину и действие другой стороны. Причины DEADLINE_PASSED и CANCELLATION_REJECTED показаны отдельно; отказ в отмене не разрешает автоматически новую подпись / выплату. Причина сохраняется как обычный текст с переносами; клиент проверяет 1–2000 Unicode-символов, сервер проверяет заново.

Команды dispute, cancel-request, cancel-accept и cancel-reject используют тот же общий pending DealAgreement. До запроса сохраняются организация / сделка, точное тело, исходный ключ и requestId решения. Неизвестный исход блокирует создание другой команды до проверки прежней; исторический результат сопровождается GET актуальной карточки. Подтверждение отмены требует явного checkbox, доступно только другой организации и остаётся допустимым после срока.

В SETTLED показываются payment_id и CONSUMED, в REFUNDED — RELEASED и объяснение освобождения ещё не выплаченных средств; CANCELLED означает отсутствие резерва. Кнопки новых блокирующих команд скрыты в терминальных состояниях. Сервер определяет победителя гонки; наличие кнопки до запроса не гарантирует переход.

DealDetail периодически перечитывает READY_TO_SETTLE и показывает ошибку чтения отдельно от подтверждённого состояния. Результат подписи 201 READY исторический: пользователь не должен считать его окончательной выплатой. Счёт перечитывается из API; суммы не пересчитываются в браузере как источник истины.

## Операторские события ЭДО

DemoEDO доступен только DEMO_OPERATOR. Форма содержит ID сделки, один из 11 именованных шаблонов и исходный event ID только для replay / same_id_different_body. Никаких HMAC-ключей, сырых подписей источника и внутренних транспортных заголовков frontend не получает.

Перед POST сохраняется PendingEDO под userId оператора: точное тело и ключ. Повреждённая запись блокирует новую отправку, исходный неизвестный результат можно проверить прежним запросом после reload. ID наблюдаемого события сохраняется отдельно под тем же пользователем. Смена аккаунта размонтирует компонент и отсекает поздние ответы.

202 подтверждает постановку, GET показывает PENDING либо DELIVERED. При PENDING чтение продолжается; ошибка чтения не заменяется успехом. DELIVERED с 4xx показан как отказ выплаты с HTTP / причиной. Успех подтверждается только HTTP 200, result settled / already_settled и согласованными deal_id / event_id / payment_id. Пользователь может перечитать результат вручную. Последняя доставка одного event ID может относиться к повтору; payment_id остаётся прежним.

Регрессии проверяют права второй стороны, независимые блокировки, восстановление точного тела / ключа, строгие сохранённые команды и различие очереди / доставки / выплаты. Локально пройдены 55 unit, оба typecheck / build и 118 системных API/UI/setup. Ручной PAY01–PAY14 — 14 PASS; подробности / ограничения — в [отчёте](reports/2026-10-24-edo-settlement.md).
