# Frontend «ПоАкту»: руководство разработчика

Обновлено: 21 октября 2026 года. Документ описывает текущий React-интерфейс авторизации, организаций и черновиков. Будущие согласование, документы, резерв, подписи, расчёт, споры, уведомления и A19 здесь не выдаются за работающие функции. Пользовательские действия и ожидаемые результаты — в [MANUAL_TESTING.md](MANUAL_TESTING.md); HTTP-контракт — в [справочнике API](api/README.md) и [OpenAPI](api/openapi.json).

## Стек и запуск

React / React DOM 19.3.1, TypeScript 7.0.2, Vite 8.3.4; Playwright 1.64.1. Версии закреплены в [package.json](../web/package.json) и lock-файле. Node.js — ветка 22, не ниже 22.19.0; в контейнере 22.23.3. Используется npm. Router, Redux, React Query, UI-kit и сторонние денежные библиотеки не подключены.

Из корня репозитория:

```sh
npm --prefix web ci --ignore-scripts
npm --prefix web run dev
```

Dev server слушает loopback; открывать `http://localhost:5173`. Backend должен быть запущен с `HTTP_ADDR=127.0.0.1:8081`, `APP_ORIGIN=http://localhost:5173` и отдельной учебной БД. Инициализация / миграции / ключи — в [RUNNING.md](RUNNING.md). Backend не запускается командой npm. Без него интерфейс покажет ошибку подключения, а не вымышленные данные.

Vite проксирует `/api/v1`, `/healthz`, `/readyz` на `127.0.0.1:8081`. `APP_ORIGIN` обязан совпадать с адресом вкладки, включая hostname / порт; Vite proxy сохраняет браузерный Origin. Смена `localhost` на `127.0.0.1` требует соответствующей настройки backend и даёт другое cookie-хранилище. Публичных VITE_* переменных, секретов или настраиваемого внешнего API URL в клиенте сейчас нет.

Для отдельного QA-стенда `npm --prefix web run dev:e2e`: строгий порт 18080, proxy на 18081; backend origin `http://localhost:18080`. Не направлять тесты на рабочую БД. При сборке / dev сначала автоматически готовится локальный Swagger `/api-docs/`.

## Навигация и компоненты

Это SPA без URL router. Разделы задаются состоянием: reload возвращает в начальный кабинет, выбранная карточка / фильтры в URL не сохраняются, deep link сделки отсутствует. Маркировка `key={session.user.id}` размонтирует старый кабинет при смене пользователя. Swagger — отдельная статическая страница, его deep links не являются маршрутами приложения.

| Компонент | Что показывает / хранит |
|---|---|
| App | session, initializing, bootstrapError, notice, readiness, loggingOut; sessionRevision отсекает старые завершения |
| AuthScreen | Режим входа / регистрации, поля, локальная ошибка, busy; COMPANY / IP; публичные учебные аккаунты |
| Workspace | account / deals / catalog; заголовок текущей организации / оператора |
| Account / BalanceCard | Три остатка сервера, время чтения, текущий счёт; нулевые остатки являются данными, ошибка не подменяется нулём |
| Catalog | Ввод query и применённый activeQuery, items, cursor, loading/error, номер актуального запроса |
| Deals | list / create / detail, выбранный ID, признак создания, pending / storageError |
| DealList | Поля фильтров отдельно от применённых filters; items / cursor; ошибки загрузки и локальной валидации |
| CreateDeal | Поля формы, исполнитель, busy, pending; поколение смонтированной формы |
| SupplierPicker | Поиск и курсор организаций; исключает ownId, выбирает контрагента по ID |
| DealDetail | GET актуальных условий, роль своей организации, сроки / стороны; без кнопок будущих команд |

ORG_OWNER видит счёт, сделки и каталог. DEMO_OPERATOR без организации — обзор и каталог, без клиентского счёта / создания сделки. Это удобство интерфейса, а права всегда проверяет backend.

## Загрузка сессии и смена аккаунта

1. App одновременно запускает `/auth/me` и `/readyz`. `401` от me означает экран входа; прочий отказ — bootstrap-ошибка с повтором.
2. После me/login/register ApiClient связывается с показанным `user.id`; новая сессия очищает старый CSRF-кеш. В ответе login/register есть csrf_token, но текущий клиент дополнительно получает актуальный токен через `/auth/csrf`.
3. Все защищённые чтения, создание и logout получают `X-Expected-User-ID`. `/auth/me`, `/auth/csrf`, login/register используются для обнаружения / смены сессии без него.
4. При `401` защищённого запроса кабинет скрывается, токен очищается, показан вход. `SESSION_CHANGED` либо `CSRF_INVALID` вызывает перечитывание сессии с сообщением; команда автоматически не повторяется.
5. Logout показывает успешный выход только после 204. При 503 сохраняется настоящий контекст и ошибка; после восстановления можно повторить действие.

Cookie браузера общие для вкладок, sessionStorage — нет. Поэтому нельзя считать видимый заголовок доказательством того, кто исполнит следующий запрос. Привязку ID захватывать **до** асинхронного CSRF. Поколение токена не позволяет старому запросу вернуть прежний токен, снять новый запрос получения CSRF или очистить новый кеш поздним 401. sessionRevision защищает App от устаревших завершений bootstrap / logout / входа. Мгновенной синхронизации вкладок через BroadcastChannel нет: конфликт обнаруживается на следующем защищённом обращении.

## ApiClient и ошибки

Клиент использует относительный `/api/v1`, `credentials:'same-origin'` и `Accept: application/json`. mutate добавляет CSRF, JSON Content-Type при наличии тела и Idempotency-Key для создания. CSRF получают и кешируют в памяти; одновременные обращения используют один Promise. Метод logout отправляет полностью пустое тело.

TypeScript-типы описывают Session, Organisation, OwnOrganisation, Counterparty, Page, CreateDealInput, Deal, DealFilters. Типизация успешного JSON — не полноценная проверка схемы во время исполнения: отдельно проверяются деньги / остатки и сохранённая команда. Не добавлять доверие к произвольным данным только потому, что они приведены к типу.

`ApiError` содержит status, code, requestId. `parseApiError` выдерживает не-JSON ошибку как UNKNOWN_ERROR; `describeError` показывает понятное сообщение, для сетевого TypeError — отсутствие связи. Серверные request ID видны пользователю как код обращения. Успешный 204 не разбирается как JSON; невалидный успешный JSON выдаёт ошибку. Это важно для неизвестного исхода команды.

При добавлении запроса следовать существующему порядку:

```ts
// Компонент передаёт только условия. Субъект и права определяет сервер.
const page = await api.deals({ role: 'customer', status: 'DRAFT' });
const deal = await api.deal(page.items[0].id);
```

В реальном коде сначала проверить наличие items и обработать loading/error/empty. Не перехватывать ошибку, чтобы вернуть вымышленные успешные данные. Кнопка повтора чтения допустима; повтор изменяющей команды требует сохранённых условий и идентичности запроса.

## Деньги, текст и время

`rublesToKopecks` принимает строку рублей с точкой / запятой и максимум двумя дробными знаками. Пробелы внутри, ведущие нули, минус, экспонента и округление не допускаются. Расчёт выполняется BigInt; результат JSON — строка. `parseKopecks` проверяет каноническую неотрицательную строку и предел int64. `formatRubles` группирует целую часть, не пропуская её через Number. `validateBalances` проверяет `total − reserved = available`.

Создание: title 1–200, description 1–5000 Unicode-символов, deadline в будущем, тело не более 16 KiB UTF-8. Регистрация: имя 2–200, пароль 12–128 Unicode-символов. JavaScript `.length` и HTML maxLength считают UTF-16; бизнес-длину считать `[...value].length`. Поэтому HTML допускает до 400 / 10000 единиц для 200 / 5000 кодовых точек; сервер остаётся окончательным валидатором. Поиски сохраняют полное Unicode-значение и сервер ограничивает 200 символами.

Поле datetime-local относится к часовому поясу браузера и переводится через toISOString в UTC; рядом показывается зона. Срок в карточке форматируется локально. Для дат фильтра `dateBoundary` строит начало дня и последнюю микросекунду конца дня; нельзя считать местную полночь UTC-полуночью. UI учитывает DRAFT / REVIEW_REQUIRED; остальные статусы пока не выводятся как реализованные процессы. Истёкший срок не доказывает выполнение работ.

## Надёжное создание и восстановление

До POST CreateDeal сохраняет в sessionStorage запись `poaktu:pending-deal:<organisationId>`:

```ts
interface PendingDealAttempt {
  key: string;               // crypto.randomUUID(), создаётся один раз
  input: CreateDealInput;    // точные нормализованные условия
  supplier: Counterparty;   // отображение выбранного исполнителя
}
```

При невозможности записи в storage команда **не отправляется**. При busy либо pending поля блокируются; явный повтор использует прежнее input/key. Не очищать запись при reload, переходе назад, сети / 503, CSRF / смене аккаунта или конфликте ключа. Закрытие вкладки может уничтожить sessionStorage; это не серверная очередь и не резервная копия. При его потере сначала проверить список, не делать автоматическую новую отправку.

`readPendingDeal` проверяет JSON, ключ, обязательные поля, валюту, сумму int64, календарную дату UTC, пределы текста / тела, совпадение исполнителя и отсутствие неизвестных полей input. Пустая строка и повреждённая запись блокируют новую команду; она не удаляется молча. Законная запись с прошедшим сроком сохраняется: исходный POST мог уже успешно завершиться.

После подтверждённого успеха запись удаляется только при совпадении её ключа с ответом; поздний ответ другой формы не удаляет новую команду. После окончательного семантического отказа код освобождает форму для новой команды. Текущий список окончательных кодов: INVALID_REQUEST, INVALID_AMOUNT, AMOUNT_OVERFLOW, DEADLINE_PASSED, RESOURCE_NOT_FOUND, IDEMPOTENCY_KEY_REQUIRED; AMOUNT_OVERFLOW зарезервирован в клиенте, текущий сервер для переполнения возвращает INVALID_AMOUNT. Остальные случаи требуют выяснения результата. Сменивший аккаунт не получает pending другой организации; явное возвращение к исходному владельцу позволяет проверить прежнюю команду.

Не заменять эту логику общим retry(fetch). Таймаут не доказывает rollback; повтор с новым ключом способен создать вторую сделку. sessionStorage исходной организации не является доказательством прав — их заново проверяет API.

## Асинхронные чтения и формы

Каталог / список / карточка / выбор исполнителя используют счётчик запроса. Ответ принимается, только если номер актуален; cleanup увеличивает его при размонтировании / смене параметров. Старый ответ не должен менять новый экран, ошибку или loading. AbortController сейчас не используется; запрос может закончиться на сервере даже после ухода с экрана. StrictMode в разработке дополнительно проверяет цикл effect/cleanup; не удалять защиту ради устранения повторного GET.

Поля поисковой формы и применённые фильтры разделены. Новая первая страница очищает предыдущие items/cursor; загрузка следующей добавляет результат. При смене фильтров старый курсор не переносится. Неверный период очищает прежнюю выдачу, чтобы она не выглядела результатом невалидного фильтра. Каталог принимает Enter и во время прежней загрузки. Enter в SupplierPicker перехватывается локально и не отправляет общую форму сделки; учитывается IME composition.

Loading, empty и error — отдельные состояния. Пустой ответ каталога допустим; сбой сети не означает отсутствие организаций. Кнопки submit блокируются на время команды; повторное нажатие не создаёт другой ключ. Доступность кнопки не заменяет серверную проверку.

## Стили и доступность

Один CSS-файл с общими переменными, компонентными классами и media queries; нет CSS-in-JS. Разметка использует label, fieldset, nav, заголовки, role=alert/status/search, aria-current и текстовые названия действий. Не делать критические действия только иконкой. Длинные ID / названия и большие суммы должны переноситься без обрезания значимого содержимого; описание сохраняет переводы строк.

При правке layout проверять 320–1920 px, длинные Unicode-названия, MaxInt64, ошибки и loading. Автоматическая матрица 11 состояний × 17 ширин проверяет 187 сочетаний, пересечения соседей, выход за viewport, обрезание глифов и перехват кликов. Она не заменяет browser zoom, физическую экранную клавиатуру, screen reader и проверку всех браузеров. Полная ручная инструкция — [MANUAL_TESTING.md](MANUAL_TESTING.md).

## Проверка и порядок изменений

Для функции обновить DTO / клиент, компоненты и состояния, локальную валидацию, этот документ и OpenAPI при изменении HTTP. Сначала typecheck, unit, docs:check, build; затем необходимые E2E на отдельном стенде. Добавлять регрессию для нового поведения / дефекта, не считать отсутствие ошибок компиляции полной приёмкой. Подробные команды / артефакты — [TESTING.md](TESTING.md).

`playwright-report`, `test-results/auth`, traces и sessionStorage могут содержать действующие учебные cookie и тела команд. Не коммитить их. Запуски E2E выполнять последовательно: состояние акторов и отчёты общие. Учитывать штатный лимит входов; тестовые помощники сессий используют уникальные аккаунты и явный повтор по Retry-After, не ослабляя сервер.

Для нового endpoint не доверять правам из UI, не передавать владельца в теле вместо сессии, не вычислять деньги через Number и не очищать pending при неизвестном исходе. Существенные изменения границ или хранения фиксировать в CONTEXT.md / ARCHITECTURE.md; фактическую проверку — в STATUS.md, дальнейшую работу — в BACKLOG.md.
