# Независимая проверка целостности A19

Обновлено: 25 октября 2026 года. Протокол v1; миграция 010. Тестовый контур. Расчёты и ЭДО эмулируются.

## Что подтверждает результат

CLI сравнивает согласованное состояние остановленного приложения с конкретной подписанной контрольной точкой, сохранённой независимо от администратора проверяемой БД. Используются SHA-256 и Ed25519 из стандартной библиотеки Go. Отдельная прослойка Rust для этой задачи не требуется.

Доверенными должны оставаться проверяющий бинарный файл, его среда исполнения, приватный ключ создателя эталона, закреплённый публичный ключ и отпечаток последнего принятого эталона. Ключ проверки отличается от APP_KEY: приложение не подписывает точки автоматически. Хранение всего набора рядом с БД не обеспечивает независимость. Для демонстрации на одном ПК это организационная граница; при доступе администратора ко всему хосту она не выдерживается.

MATCH означает совпадение покрытых данных с указанным эталоном. Он не удостоверяет исполнение работ, юридическую силу подписи, отсутствие мошенничества или личность нарушителя. Исправная цепочка внутри БД сама по себе не доказывает отсутствие вмешательства: владелец БД может переписать её целиком. Внешняя точка позволяет обнаружить такое расхождение. Старый действительный эталон вместе с откатом БД к нему также может совпасть, поэтому CLI требует независимо закреплённый SHA-256 **последней принятой** точки. Отпечаток нельзя брать из той же недоверенной папки без внешней сверки.

Не обнаруживаются изменения, полностью восстановленные до проверки, вмешательство до первой доверенной точки и изменения исключённых полей. Защита от администратора ОС, подмены бинарного файла, подключения к подставной БД, вредоносных расширений PostgreSQL и одновременного изменения файлов вне приложения не заявлена. Это прототип обнаружения расхождений, без сертификации или независимого аудита безопасности.

## Покрытие v1

[Фиксированный манифест](../internal/features/integrity/repository/postgres/manifest.go) перечисляет столбцы 28 таблиц: users, organizations, memberships, accounts, ledger_batches, ledger_entries, bootstrap_runs, schema_migrations, deals, deal_versions, idempotency_keys, audit_events, outbox, documents, document_versions, deal_agreements, operator_command_results, reserves, document_signatures, edo_outbox, deal_disputes, cancellation_requests, cancellation_decisions, event_inbox, edo_command_results, edo_deliveries, settlements, notifications.

Сохраняются имена / порядок столбцов, фактические типы, вид отношения, число строк и хеши. Охвачены остатки / резервы / проводки, условия и стороны, версии документов, согласия / подписи, спор / отмена, события ЭДО, ответы идемпотентности и права. Отдельно читаются реальные байты каждого PDF, на который ссылается document_versions: проверяются размер и SHA-256. Недоступный файл не считается совпадением. Недостающая таблица / поле приводит к невозможности проверки. Эталон содержит хеши и количества, без тел документов, паролей и приватных ключей; его метаданные всё равно следует хранить как служебные данные.

Исключены sessions, users.email, users.password_hash, notifications.read_at, outbox.delivered_at, неперечисленные таблицы / столбцы, PDF без ссылки из БД и конфигурация БД / ОС. Прочтение уведомления не меняет покрытый снимок; новая доставка создаёт покрытые notification-факты. Новые поля не включаются автоматически: изменение покрытия требует пересмотра протокола. Перечень исключений подписан и входит в coverage_hash.

## Цепочка аудита

Миграция создаёт боковые audit_chain_head и audit_chain_entries, не переписывая audit_events. Исторические записи упорядочиваются по created_at, затем id с COLLATE C. Это реконструкция, а не доказательство исходного порядка или подлинности. legacy_count сохраняет размер такого префикса. Доверие начинается только с первой независимо принятой точки.

Каждый новый INSERT audit_events дополняет цепочку отложенным constraint trigger в той же транзакции. Общая строка головы блокируется FOR UPDATE; последовательность вычисляется last_seq + 1, без sequence / SERIAL. Откат не оставляет записи цепочки или пропуска. Права runtime разрешают чтение цепочки и вызов функции блокировки головы, но не прямое изменение цепочки / головы или вспомогательных функций. SECURITY DEFINER использует закреплённый search_path. Владелец БД может обходить эти ограничения; это учитывается моделью угроз.

Денежные операции берут блокировку головы после сделки / счетов, затем заново проверяют срок. Поэтому ожидание цепочки не позволяет провести просроченный резерв, новую подпись или выплату. Другие записи получают блокировку в deferred trigger при commit; после неё новые бизнес-блокировки не берутся.

## Байтовое кодирование

[Реализация Go](../internal/core/integrityformat/canonical.go) независимо пересчитывает все события из исходных полей, не вызывая SQL-функции хеширования БД. SHA-256 имеет отдельные домены с завершающим нулевым байтом:

- poaktu:audit:event:v1: канонический массив [id, deal_id, deal_version, type, actor_user_id, actor_organization_id, actor_source, request_id, payload, created_at].
- poaktu:audit:genesis:v1: рамка log_id.
- poaktu:audit:link:v1: рамка log_id, int64 sequence big endian, previous_hash (32 байта), event_hash (32 байта).

Рамка — длина UTF-8 в uint64 big endian и байты строки. Каноническое JSON-кодирование типизировано: n / f / t для null / false / true; s / d с рамкой для строк / десятичных чисел; a / o с uint64 количеством элементов / пар и рекурсивными значениями. Ключи объектов сортируются по байтам UTF-8. Дубликаты имён запрещены. Числа нормализуются точно в десятичном виде без float, незначащих нулей и экспоненты; -0 становится 0. Время БД — UTC с шестью десятичными знаками, диапазон 0001–9999. Иные значения не считаются проверенными.

Хеш строки состояния: домен poaktu:integrity:row:v1 с нулём, рамка имени таблицы и канонический массив перечисленных полей. Для таблицы сортируются 32-байтные хеши строк с сохранением повторов; хешируются домен poaktu:integrity:table:v1 с нулём, рамка канонического дескриптора и uint64 количества строк, затем все хеши. coverage_hash охватывает версию, дескрипторы и исключения; state_hash — coverage_hash и полные TableDigest. PDF имеют отдельные домены pdf-row / pdfs. Точные домены и регистр ключей дескрипторов закреплены [кодом репозитория](../internal/features/integrity/repository/postgres/repository.go) и тестами; это собственный формат, не RFC 8785.

Checkpoint: format=poaktu-integrity-checkpoint-v1, key_id=SHA-256 сырых 32 байт публичного ключа, snapshot, signature. Ed25519 подписывает домен poaktu:integrity:checkpoint-signature:v1 с нулём и канонический объект format / key_id / snapshot. signature — base64url без padding. Публичного ключа внутри файла нет. Отпечаток checkpoint_sha256 — SHA-256 канонического **всего** файла, включая подпись; форматирование / порядок JSON-ключей его не меняют. Обычный sha256sum файла с отступами даст другое значение. CLI выдаёт нужный отпечаток при создании.

## Порядок проверки

Все команды работают только с DEMO_MODE=true и DATABASE_URL тестового контура. keygen не требует БД. DATABASE_URL для независимого чтения должен позволять SELECT всех покрытых таблиц; приватный ключ не требуется verify. DOCUMENTS_DIR должен уже существовать и быть доступен только для чтения; проверяющий не создаёт каталог и не пишет PDF. Пути ключей / эталона должны вести к обычным файлам. Ссылки, лишние PEM-блоки, неизвестные / повторяющиеся JSON-поля, неподдерживаемый формат и файл более 256 KiB отклоняются.

Пример для собранного бинарного файла (каталог external-reference создаёт хранитель заранее):

```sh
poaktu integrity keygen --private-key external-reference/signer.pem --public-key external-reference/trusted-public.pem
# Остановить все API / workers и дождаться завершения активных команд.
poaktu integrity checkpoint --private-key external-reference/signer.pem --out external-reference/checkpoint-001.json --acknowledge-current-state
# Сохранить выданные public_key_sha256 и checkpoint_sha256 независимо.
poaktu integrity verify --checkpoint external-reference/checkpoint-001.json --public-key external-reference/trusted-public.pem --checkpoint-sha256 <сохранённый checkpoint_sha256>
```

Не передавайте signer.pem в окружение serve и не добавляйте ключи в Git / .env. keygen и checkpoint используют исключительное создание файла; существующий файл не перезаписывается. Потерянный / неизвестный исход записи требует осмотра файла, а не слепого повтора с заменой ключей. Новый эталон создаётся только осознанной отдельной командой с acknowledge-current-state. Эта команда доверяет текущему состоянию и не исправляет его.

serve держит общую session advisory lock всё время работы, включая остановку обработчиков. Каждое новое соединение serve также получает её до первого запроса, в том числе после перезапуска БД; migrate / bootstrap тоже берут общую блокировку. Capture получает исключительную транзакционную блокировку без ожидания и читает REPEATABLE READ READ ONLY. Проверка рассчитывает снимок целиком в памяти и рассчитана на размер учебного прототипа. Пока есть активный API, результат QUIESCENCE_REQUIRED. Запуск API ждёт завершения Capture. Это защита от штатных процессов этого приложения; администратор БД может её проигнорировать. Перед созданием эталона требуется завершить pending outbox, inbox, доставки ЭДО и автоматические основания без доставки. Если очередь не пуста, запустите штатные workers, выясните причину и повторно остановите приложение. CLI не помечает задания выполненными.

После обычной работы состояние может законно измениться. MISMATCH требует сверки с историей и внешними доказательствами; он не является автоматическим вердиктом. Не обновляйте эталон, пока причина расхождения не разобрана. При подозрении остановите изменения, сохраните отчёт, доверенный эталон и копию данных / файлов, проверьте ключ и окружение, затем передайте факты уполномоченному человеку. Спор и возможное судебное разбирательство остаются вне автоматического решения приложения.

| Статус | Код выхода | Значение |
| --- | --- | --- |
| MATCH | 0 | Совпадение с указанным независимо закреплённым эталоном |
| CHAIN_BROKEN | 2 | Нарушены связи, хеши, последовательность или полнота аудита |
| MISMATCH | 2 | Покрытые данные / PDF / покрытие отличаются; возможны штатные изменения |
| UNVERIFIABLE | 3 | Нет доверенного эталона / ключа / обязательных данных или они некорректны |
| QUIESCENCE_REQUIRED | 3 | API / workers ещё держат блокировку |
| KEYS_CREATED / CHECKPOINT_CREATED | 0 | Создан новый ключ / эталон; это не результат проверки прежнего состояния |

HTTP /readyz stage=audit_integrity сообщает только о готовности установленной схемы. Зелёный HTTP-индикатор проверки не добавлен: источник проверки должен оставаться независимым.

## Воспроизводимые проверки

Изолированные Go-тесты создают случайные схемы test_ / chain_ и временные файлы. Они проверяют перекодирование SQL / Go, rollback и конкурентные записи, обновление 009→010, runtime-права, подмену аудита / суммы / условий / роли, разрыв и полный пересчёт цепочки, усечение / откат, неверный ключ / подпись, отсутствие таблицы / PDF и изменение байтов PDF. Небезопасные owner-операции запрещены helper-функцией за пределами test_. Исходные пользовательские данные для атак не используются. Отдельно проверяются ожидание головы за deadline и взаимное исключение API / проверки. Реальные выполненные прогоны фиксируются в STATUS и отчёте; наличие теста не означает его успешного запуска.

Основания: [SHA-256 PostgreSQL](https://www.postgresql.org/docs/18/functions-binarystring.html), [отложенные constraint triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html), [advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html), [Ed25519 Go](https://pkg.go.dev/crypto/ed25519).
