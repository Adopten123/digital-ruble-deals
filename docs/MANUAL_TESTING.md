# Ручное тестирование «ПоАкту»

Версия инструкции: 24 октября 2026 года. Базовые кейсы проверяют регистрацию / вход / выход, кабинет, каталог и создание / чтение черновиков; дополнение MONEY01–MONEY08 — согласованный документ, резерв и учебные операции оператора. Наличие кейса не означает, что он уже пройден. Фактический частичный прогон прежних 61 кейса сохранён в [отчёте от 21 октября](reports/2026-10-21-manual-qa.md); новые денежные кейсы не получают его статусы автоматически. Автоматические проверки и их результаты описаны отдельно в [TESTING.md](TESTING.md), запуск стенда — в [RUNNING.md](RUNNING.md).

## 1. Подготовка и данные

Использовать отдельный учебный стенд и только вымышленные данные. Например, поднять Compose-проект `poaktu-manual` на свободном порту 18080 с `POAKTU_ORIGIN=http://localhost:18080` по инструкции из TESTING.md. Не запускать второй стенд на занятом порту и не очищать БД действующей демонстрации. Если проверяется уже открытый стенд `http://localhost:5173`, записать этот адрес в отчёт; не смешивать его данные с результатами другого стенда. `localhost` и `127.0.0.1` не взаимозаменяемы для cookie / Origin.

До начала записать commit / ветку, адрес, дату, браузер и версию, ОС, часовой пояс, zoom и размеры окна. Открыть DevTools → Network, включить Preserve log. Убедиться, что нет активных блокировок запросов / Offline / Local Overrides от предыдущих проверок. Проверить, что видна надпись «Тестовый контур. Расчёты и ЭДО эмулируются».

Подготовить четыре изолированных профиля браузера. Разные вкладки одного профиля используют одну сессию; несколько окон инкогнито также могут использовать общее хранилище. Это не подходит для параллельного входа разных сторон.

| Профиль | Email / назначение | Пароль | Начальные остатки чистого стенда: общий / резерв / доступно |
|---|---|---|---|
| A — заказчик | `customer@demo.poaktu.local`, «Демо Заказчик» | `PoaktuDemo2026!` | 500 000,00 / 0,00 / 500 000,00 ₽ |
| B — исполнитель | `supplier@demo.poaktu.local`, «Демо Типография» | `PoaktuDemo2026!` | 0,00 / 0,00 / 0,00 ₽ |
| C — третья организация | Зарегистрировать `manual-third-<RUN>@example.test`, «ООО Третья организация <RUN>» | `ManualPoaktu2026!` | 0,00 / 0,00 / 0,00 ₽ |
| D — оператор | `operator@demo.poaktu.local` | `PoaktuDemo2026!` | Организации и клиентского счёта нет |

Пароль демо намеренно публичный и предназначен только для локального учебного стенда. `<RUN>` заменить уникальной меткой, например `20261021-1430`; использовать одну метку во всём прогоне. Для регистраций нужны новые email, например `manual-company-<RUN>@example.test` и `manual-ip-<RUN>@example.test`. Не использовать настоящие контакты и пароли.

Записать ID организаций A / B / C из кабинетов. Названия не уникальны; сверять именно ID. Записать исходные три остатка A и B: создание черновиков не должно изменять ни один из них. Если стенд уже использовался, сравнивать с записанными исходными данными, а не сбрасывать его ради таблицы.

Основной черновик:

| Поле | Значение |
|---|---|
| Название | `MANUAL <RUN> — печать упаковки № 01` |
| Исполнитель | «Демо Типография», ID из профиля B |
| Условия | `Печать по макету TEST-01 на 1000 учебных коробках. Результат: вся партия без пропусков печати. Приёмка всей партии одним актом.` |
| Полная сумма | Ввести `300000,01`; отдельно проверить эквивалент `300000.01` |
| Срок | Будущая дата через семь дней, 15:30 в часовом поясе браузера |
| Ожидаемая сумма API | Строка `"30000001"` копеек |

Не выполнять все проверки входа подряд слишком быстро: лимиты — 30 auth-запросов на IP в минуту и 10 на email в минуту. При `429 RATE_LIMITED` зафиксировать причину и дождаться восстановления, не отключать ограничитель. Регистрации и черновики сохраняются; удалять данные и историю для повторения прогона не требуется.

В таблицах каждый кейс выполняется отдельно. `PASS` означает, что получены все указанные ожидаемые результаты, а не только отсутствие сообщения об ошибке.

## 6. Сбои, повторы и несколько вкладок

Для введения сбоя использовать только свой учебный профиль: DevTools → Network → Offline / throttling / Request blocking. После каждого кейса вернуть Online, No throttling и снять все блокировки. ## 7а. Резерв и учебные денежные операции

Для MONEY использовать **новые учебные организации**, не исходные деньги `customer@demo.poaktu.local`. Зарегистрировать заказчика `manual-money-a-<RUN>@example.test` и исполнителя `manual-money-b-<RUN>@example.test` в разных профилях; имена — `MONEY <RUN> Заказчик` / `MONEY <RUN> Исполнитель`. Оба начинают с нуля. В третьем изолированном профиле войти учебным оператором из таблицы раздела 1. Сохранить ID организаций / счёта / сделки и метку RUN. Повторные варианты и сбои выполнять на дополнительных свежих организациях с суффиксом варианта; завершённые резервы не сбрасывать удалением данных.

Основная цепочка MONEY01–MONEY05: **зачислить заказчику 500,00 ₽ → согласовать сделку на 300,00 ₽ → резерв 300,00 ₽ → отказ списания 200,01 ₽ → успешное списание 200,00 ₽**. Во всех суммах ровно две копейки, API передаёт строки целых копеек. Служебное списание оператора идёт на системный учебный счёт и не оплачивает работу исполнителя. Смена роли — новый профиль, не соседняя вкладка с общей cookie.

Для зачисления можно выполнить отдельное известное зачисление `0,01` ₽ до повторной проверки прежней команды. | Условия, сумма / основание, ожидаемая версия, субъект и Idempotency-Key сохраняются. Повтор не создаёт второй резерв / второе зачисление. После replay читается текущая сделка / счёт: например, исходные 500,00 ₽ и последующие 0,01 ₽ отображаются как **500,01 ₽**, а не как старый кешированный остаток. Детерминированный вариант покрывают автоматические UI-тесты, которые сначала получают реальный 201 и только затем обрывают ответ. |
| MONEY08 | У исполнителя / третьей организации проверить отсутствие операторской вкладки; резерв создаёт только заказчик. Эти кейсы — инструкция для будущего или текущего ручного прогона, а не отчёт об успехе. Денежные гонки требуют также параллельных API / PostgreSQL-тестов; последовательные нажатия не заменяют конкурентную проверку. При недоступном инструменте браузера или невозможности подтвердить ветку после commit записывать BLOCKED с причиной. Не отключать штатные лимиты; при 429 дождаться Retry-After. После сбоя вернуть Online / обычную скорость и снять блокировки.

## 8. Что пока не принимать как готовую функцию

Редактирование условий / версии, PDF, два согласия, возврат на доработку до первого резерва, резерв и операторские учебные зачисления / служебные списания реализованы и проверяются по фактическому результату. Само наличие реализации не делает ручной кейс пройденным.

Тестовые подписи, выплата, события ЭДО, споры, согласованная отмена после резерва, уведомления, экспорт и обнаружение вмешательства администратора — **не реализованы на текущем этапе**. Отмечать «НЕ РЕАЛИЗОВАНО», а не PASS. Их отсутствие не маскировать демонстрационным текстом интерфейса. Не пытаться проводить реальные деньги или подписывать реальные документы. Поясняющая схема будущего процесса не является работающей платёжной функцией.

Ручной прогон не доказывает безопасность всей системы, атомарность денежных операций или защиту от администратора инфраструктуры. Текущее число ручных повторов также не заменяет параллельные API / PostgreSQL-тесты. Результаты необходимо связывать с проверенным commit и окружением.

Результат отдельного прогона резерва от 22 октября — [12 PASS и Blob-PDF BLOCKED](reports/2026-10-22-deal-reserves.md). Это фактически выполненные R01–R13; ручные DevTools / сетевые варианты и полный набор устройств не получают эти статусы автоматически.

## 9. Результаты и баг-репорт
