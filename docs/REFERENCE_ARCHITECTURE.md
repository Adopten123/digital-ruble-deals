## Фактическая организация примера

Это модульный монолит с общей инфраструктурой и модулями `users`, `tasks`, `statistics`, `web`.

```text
cmd/todoapp/main.go               # Сборка зависимостей и запуск
internal/core/
  config/                        # Общие настройки
  domain/                        # Доменные типы и проверки
  errors/                        # Общие ошибки
  logger/                        # Логирование
  repository/postgres/pool/       # Интерфейс пула и реализация на pgx
  transport/http/                # Сервер, маршруты, middleware, запросы и ответы
internal/features/<feature>/
  service/                       # Прикладные операции и интерфейс репозитория
  repository/postgres/           # SQL и преобразование моделей хранения
  transport/http/                # HTTP DTO, обработчики, интерфейс сервиса
migrations/                      # SQL up/down
public/index.html                # Статический интерфейс
```

При запуске `main` создаёт конфигурацию, logger и PostgreSQL pool, затем для каждого модуля собирает **Repository → Service → HTTPHandler** через конструкторы. Дополнительный контейнер внедрения зависимостей не используется.

Поток запроса направлен в обратную сторону: **HTTP handler → service → repository → PostgreSQL**. Обработчик разбирает и проверяет DTO, сервис выполняет прикладную операцию и проверяет доменную модель, репозиторий выполняет параметризованный SQL и преобразует модель хранения. Ответ возвращается через DTO. Интерфейсы зависимостей объявлены у потребителей.

HTTP построен на стандартном `net/http` и `http.ServeMux`, API имеет префикс `/api/v1`. Общий слой предоставляет request ID, логирование, CORS, обработку panic, Swagger и корректную остановку сервера. Настройки читаются из окружения, включая envconfig; доступ к PostgreSQL — через pgx/v5.

В примере есть SQL-ограничения и оптимистическая проверка версии при обновлении задачи. Полноценной аутентификации с паролем и сессией нет: модуль `users` управляет профилями. В изученном дереве нет `_test.go` и конфигурации GitHub Actions. Работоспособность исходного приложения в этой задаче не проверялась.

## Адаптация для ПоАкту

Переносится архитектурный подход: модульный монолит, структура `core/features`, ручная сборка зависимостей, интерфейсы у потребителя, разделение HTTP DTO, доменной модели и SQL-модели, общий HTTP-слой и SQL-миграции. Код проекта-ориентира не копируется. Конкретные версии зависимостей из него не считаются автоматически выбранными для ПоАкту.

Следующие части проектируются заново:

- **Транзакции и UnitOfWork.** Исходный Pool предоставляет Query, QueryRow, Exec и служебные методы, но не Begin/Commit/Rollback. Для ПоАкту требуется координатор с единым транзакционным контекстом для блокировок, проверки состояния сделки и спора, резерва, проводок, идемпотентности, входящего события, аудита и outbox. Резерв, денежные проводки и состояние фиксируются одной транзакцией. Оптимистическая версия отдельной строки этого не заменяет.
- **Аутентификация и права.** Регистрация, хеширование пароля, серверная сессия, связь пользователя с организацией и проверка его доступа к сделке создаются заново. Действующая сторона определяется сервером; `user_id` из тела запроса не доказывает полномочия.
- **TypeScript-интерфейс.** В примере интерфейс расположен в одном HTML-файле. Для ПоАкту создаётся отдельное приложение TypeScript с выбранным в ТЗ устройством экранов и сборки.
- **Готовность Docker Compose.** В примере нет полной автоматической цепочки готовности БД, применения миграций и запуска приложения. Для ПоАкту необходимы healthcheck PostgreSQL, одноразовый сервис миграций и запуск backend после их успешного завершения, с одной документированной командой старта.
- **Проверки денежных сценариев.** Добавляются интеграционные проверки транзакций, дубликатов, недостатка средств, конкурирующих списаний и гонки спора с выплатой. Request ID и защита от повторного платежа решают разные задачи.

Старый `banking-system` не используется вообще — это прямое решение пользователя для нового прототипа. Архитектурным ориентиром служит только изученная структура `go-todoapp-1` с указанными дополнениями.
