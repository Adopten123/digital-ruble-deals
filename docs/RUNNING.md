# Запуск и проверки прототипа «ПоАкту»

Обновлено: 24 октября 2026 года. Реализованы регистрация / сессии, учебные счета, версии условий / приватных PDF, два согласия, rework до первого резерва, полный резерв и две отдельные тестовые подписи. Имитатор доставляет событие с HMAC; проверенный факт исполняет единственную выплату. Спор и активная отмена блокируют её; отмену подтверждает другая организация, освобождая только резерв этой сделки. История сделки / оператора и CSV / JSON реализованы. Участники получают сохранённые уведомления внутри приложения, фильтруют их и отмечают прочитанными. Контроль A19 остаётся следующим этапом. Полный объём — в [ТЗ](TZ.md), фактические проверки — в [STATUS.md](STATUS.md), комплексные сценарии UI / API — в [TESTING.md](TESTING.md).

## Docker Compose

Нужны Docker с работающим Linux Engine и Docker Compose. Go, Node.js и PostgreSQL на компьютере жюри не требуются.

Из корня репозитория:

```sh
docker compose up --build
```

Открыть **http://localhost:8080**. Это канонический origin: `127.0.0.1` и `localhost` различаются при проверке CSRF / Origin. Порт опубликован только на loopback. Web подключён к отдельной bridge-сети ingress; связи web → API и API → БД остаются во внутренних сетях. БД и API наружу не публикуются; `/internal/` не проксируется. Разделение внешней и внутренней сети соответствует [модели Docker Compose](https://docs.docker.com/compose/how-tos/networking/).

Порядок запуска: PostgreSQL healthcheck → migrate → access (ограниченные права роли API) → bootstrap → API readiness → web. Миграции проверяют контрольные суммы; bootstrap не повторяет начальное зачисление и не сбрасывает пароли. БД, ключи и PDF сохраняются в named volumes. API и web работают непривилегированными пользователями; ключ доступен API только для чтения. Миграции до 009 применяются поверх существующих данных; чистить volumes для обновления не нужно.

На компьютере разработки Docker Engine пока не удалось запустить из-за WSL2 / виртуализации; приложение проверяется отдельно на локальной PostgreSQL. Предыдущий каркас до черновиков прошёл полный запуск из чистой копии в [Linux CI](https://github.com/Adopten123/digital-ruble-deals/actions/runs/39368496701) на коммите `64a2152`: сборка, readiness, HTTP smoke, повторный bootstrap и перезапуск. Тот же прогон подтвердил Go race-тесты с PostgreSQL 18.6. В следующих этапах CI дополнен проверкой прежнего ID / ключа после перезапуска; текущие результаты именно версии с документами смотреть в [STATUS.md](STATUS.md) и pull request этапа. Проверка на втором пользовательском ПК остаётся в плане.

## Документация API и frontend

На запущенном web открыть `/api-docs/` (Compose: `http://localhost:8080/api-docs/`). Swagger UI и OpenAPI входят в локальную сборку, CDN не требуется. Экспорт схемы — `/api-docs/openapi.json`; исходник — [api/openapi.json](api/openapi.json). Порядок работы с cookie / CSRF и полный справочник текущих операций — [api/README.md](api/README.md). Устройство интерфейса, dev proxy, восстановление команд и команды разработки — [FRONTEND.md](FRONTEND.md).

`npm --prefix web run docs:check` проверяет OpenAPI и совпадение операций с Go. Перед dev / dev:e2e / build автоматически выполняется docs:prepare; после изменения схемы на уже запущенном Vite можно вызвать `npm --prefix web run docs:prepare`. При первом добавлении public-папки требуется перезапуск старого Vite. Сам backend не раздаёт Swagger, открывать его следует через web origin.

Схема OpenAPI 0.7.0 содержит 37 операций: 36 браузерных (включая health / readiness) и одну внутреннюю с HMAC. Внутренний маршрут не доступен через web-proxy. PDF загружается multipart-запросом с `expected_deal_version` и `file`; файл до 5 MiB, расширение `.pdf`, MIME `application/pdf`. Прототип принимает ограниченное статическое подмножество PDF и отклоняет формы / аннотации / активное содержимое / шифрование, поэтому некоторые обычные PDF потребуют нового экспорта. Альтернатива — генерация учебного акта `printing-acceptance-v1` по текущим условиям. Точные правила / ошибки — в [справочнике API](api/README.md#pdf-загрузка-генерация-и-приватное-чтение).

После двух согласий заказчик резервирует всю сумму одной командой. PDF перед резервом должен оставаться читаемым и совпадать с закреплённым SHA256 / размером. Общий остаток не уменьшается, увеличивается reserved; в FUNDED исполнитель ещё не получил деньги. Показ учебных пополнений / списаний выполнять оператором на отдельной синтетической организации: credits выдаёт средства от системного DEMO_ISSUANCE, debits расходует только available и зачисляет на DEMO_DEBITS. Не использовать исходные seeded-счета как общие изменяемые тестовые данные для параллельных прогонов.

## Хранилище PDF

`DOCUMENTS_DIR` задаёт приватный каталог файлов; в Compose это `/var/lib/poaktu/documents` в volume `documents`, смонтированном только в API. При запуске вне Docker задать собственный доступный для записи каталог вне `web/public`, сборки frontend и других публичных статических папок. Нужна файловая система с поддержкой hard link, например NTFS или файловая система Linux volume. Файлы получают случайные внутренние имена; исходное имя не используется как путь.

Чтение идёт только через авторизованные `/api/v1/documents/{id}/view?version=...` и `/download?version=...` с проверкой исторических / текущих сторон, SHA256 и размера. Не публиковать каталог как static volume nginx. Один документ сделки имеет стабильный ID и несколько неизменяемых версий; снятие активного PDF при PATCH / rework не удаляет файлы / историю.

Для переноса стенда сохранять вместе БД, volume PDF и app key. Одна резервная копия БД не содержит байты документов. При временной ошибке / неизвестном исходе commit может остаться файл без доступной записи БД; автоматической очистки таких файлов сейчас нет. Не удалять файл после ошибки команды: результат commit мог сохраниться.

## Учебные учётные записи

Общий публичный пароль стенда: `PoaktuDemo2026!`.

| Email | Назначение | Начальный общий остаток |
|---|---|---:|
| customer@demo.poaktu.local | Владелец организации заказчика | 500 000 ₽ |
| supplier@demo.poaktu.local | Владелец организации типографии | 0 ₽ |
| operator@demo.poaktu.local | DEMO_OPERATOR, без организации | Нет клиентского счёта |

Новая регистрация создаёт отдельную учебную организацию и счёт с нулём. Название компании не даёт членства в существующей организации. Операторский экран показывает клиентские учебные счета и команды пополнения / служебного списания; панель ЭДО позволяет проверять доставку корректных / ошибочных событий. Оператор читает отдельный аудит; участник — историю своей сделки и уведомления. CSV / JSON выгружаются из карточки в пределах доступных версий. Начальные 50 000 000 копеек записываются двумя сбалансированными проводками с отдельным системным противосчётом; реальных денег нет.

Пароли и подключения выше — намеренно публичные данные локального демо, не производственные секреты. Приложение требует `DEMO_MODE=true`. Ключ приложения для CSRF / курсоров и производного HMAC-ключа ЭДО генерируется при bootstrap, хранится в volume и не входит в Git / образ. Подключать реальные счета, документы или производственную БД запрещено.

## Проверка состояния и повторный запуск

```sh
docker compose ps --all
docker compose logs --tail 100 api
docker compose run --rm bootstrap
docker compose restart api web
```

`GET /healthz` показывает работоспособность процесса, `GET /readyz` — доступность БД, схемы до `009_notifications.sql`, завершённого bootstrap и системного DEMO_DEBITS. Readiness возвращает `stage: "notifications"`; это готовность реализованного учебного расчёта, не подтверждение доставки каждого события или реальной банковской интеграции. Приватное хранилище открывается при старте API; readiness не выполняет пробную запись / проверку всех существующих PDF.

Повторный bootstrap сохраняет прежние данные. CLI создания нового изолированного сценария остаётся в плане; разрушительного HTTP reset нет.

При обновлении прежнего стенда обязательно выполнить migrate → access → bootstrap → restart, как это делает Compose. Bootstrap перед проверкой прежней отметки добавляет отсутствующий фиксированный счёт DEMO_DEBITS с нулём; первоначальная эмиссия, пароли и старые остатки не повторяются. Он не пересоздаёт пользователей и не освобождает резервы. Недостаточно просто заменить бинарник, оставив старые миграции / grants.

Остановка с сохранением данных:

```sh
docker compose down
```

Команды удаления volumes не нужны для обычного запуска. Не удалять историю, чтобы повторить показ.

Если 8080 занят, в PowerShell задать **оба** значения и пересоздать стенд:

```powershell
$env:POAKTU_PORT = '8082'
$env:POAKTU_ORIGIN = 'http://localhost:8082'
docker compose up --build
```

## Проверки кода и API

Для разработки нужны Go 1.27.2 и Node.js 22 (проверено локально на 22.19.0, в контейнере закреплена 22.23.3).

```sh
go vet ./...
go test ./... -count=1
go build ./cmd/poaktu
npm --prefix web ci --ignore-scripts
npm --prefix web run typecheck
npm --prefix web test
npm --prefix web run build
```

Без `TEST_DATABASE_URL` PostgreSQL-тесты пропускаются. Для их выполнения использовать отдельную учебную БД; каждый тест создаёт случайную схему и удаляет только её. Пример DSN: `postgres://poaktu_test:local_test_password@127.0.0.1:55439/poaktu_foundation_test?sslmode=disable`. Не задавать production DSN. В CI выполняется также `go test -race` на Linux.

Для запущенного стенда и Node.js:

```sh
node scripts/smoke.mjs
```

Smoke проверяет роли / CSRF / каталог, черновики / повторы / конфликт / конкурентность и приватные PDF. Для расчёта создаёт две отдельные синтетические организации: оператор зачисляет заказчику 50 000 копеек, стороны согласуют PDF, резервируют 30 000 и расходуют оставшиеся 20 000. После первой подписи деньги остаются в резерве; после второй worker доставляет проверяемое событие, заказчик получает 0 / 0 / 0, исполнитель — 30 000 / 0 / 30 000 копеек. Новый корректный event ID возвращает already_settled с прежним payment_id. Общие seeded-счета не меняются, БД не сбрасывается. Собственные сессии отзываются. Файл SMOKE_STATE_FILE формата v6 хранит ID / исходные ключи / тела и результаты без cookie / паролей: следующий запуск проверяет прежние PDF, подписи, выплату, доставку, историю / экспорт, уведомления / прочитанность и точные исторические ответы после перезапуска. Старые форматы v1–v5 читаются для проверки предыдущих этапов. В CI файл находится во временной папке runner. Цель по умолчанию — loopback http://localhost:8080; для dev API задать BASE_URL и точный браузерный APP_ORIGIN.

При разработке вне Docker сначала создать отдельную БД, задать `DATABASE_URL`, `DEMO_MODE=true`, `APP_ORIGIN`, `APP_KEY_FILE`, `MIGRATIONS_DIR` и `DOCUMENTS_DIR`, затем выполнить `poaktu migrate`, выдать явные права роли API последовательно из `deploy/postgres/runtime_grants.sql` и `deploy/postgres/edo_runtime_grants.sql`, выполнить `poaktu bootstrap` и `poaktu serve`. Миграции / bootstrap выполняются владельцем учебной БД, HTTP-сервер — ограниченной runtime-ролью. При нестандартной схеме адаптировать указанный в grants `public`, не выдавать владельца БД самому API. Встроенные миграции / bootstrap не удаляют прежние данные.

Vite использует proxy на `127.0.0.1:8081`; для него `HTTP_ADDR=127.0.0.1:8081`, `APP_ORIGIN=http://localhost:5173` и `npm --prefix web run dev`. На Windows `APP_KEY_FILE` и `DOCUMENTS_DIR` нужно задать доступными локальными путями, а не оставлять Linux-пути по умолчанию. БД / PDF / ключи / SDK / зависимости в репозиторий не коммитятся.

## Состав и версии

Backend: Go 1.27.2, pgx 5.11.0, x/crypto 0.58.0; PDF — pdfcpu 0.16.3, fpdf 0.12.0 и встроенный Go Regular из x/image 0.47.0. Frontend: React 19.3.1, TypeScript 7.0.2, Vite 8.3.4; точные транзитивные зависимости — в lock-файле. Контейнеры: Go 1.27.2, Node 22.23.3, PostgreSQL 18.6, nginx 1.30.6, Alpine 3.24.2; Dockerfile / Compose закрепляют также digest образов. Локальные интеграционные проверки использовали установленную PostgreSQL 18.1 в отдельном кластере. Лицензии PDF-библиотек / встроенного шрифта сохранены в [THIRD_PARTY_NOTICES.md](../internal/core/documentfile/THIRD_PARTY_NOTICES.md) и включены в runtime-образ.

Структура: `cmd/poaktu` собирает config / PostgreSQL / repositories / services / handlers и файловое хранилище; `internal/core` содержит инфраструктуру / documentfile, `internal/features` — auth, organizations, bootstrap, deals, settlement, edo, read-only audit и notifications. Миграция 001 — основа / seed ledger, 002 — версии условий / результаты / аудит / pending outbox, 003 — PDF / согласия, 004 — резервы / операторские результаты / проекции и направления проводок, 005 — закреплённый search_path восьми guard-функций. 006 добавляет подписи / основание ЭДО, 007 — спор / двустороннюю отмену и освобождение резерва, 008 — inbox / доставку и единственную выплату, 009 — уведомления и защищённую первую отметку прочтения / обработки outbox. Для runtime после migrate применяются оба файла runtime_grants.sql и edo_runtime_grants.sql. Применённые миграции не редактировать: добавлять следующую.

Обычная роль API получает явные права из `deploy/postgres/runtime_grants.sql`: создание / чтение предметных фактов и результатов, UPDATE проекций total / reserved и разрешённых полей deals, включая первый резерв. Она не получает DDL, bootstrap, назначения оператора, изменения / удаления опубликованных ledger / reserve / agreement / document / audit / result facts. Для уведомлений разрешены вставка получателя и UPDATE только read_at; для outbox — первое заполнение delivered_at. Guard-функции запрещают переписывание основания / получателя и первоначальных времён. Deferred constraints проверяют сумму проводок / резервов против проекций, баланс пачки и направление операторского движения; runtime-переход в FUNDED требует резерва, изменение после первого резерва запрещено. Это не RLS: права пользователя / организации проверяет сервер.

Миграция 005 сохраняет SECURITY INVOKER и устанавливает guard-функциям `search_path = pg_catalog, <доверенная схема приложения>, pg_temp`. pg_temp указан явно последним: иначе временная таблица может подменить читаемый функцией реестр, даже при фиксации одного public. Схема определяется при миграции, что поддерживает отдельные тестовые схемы; запускать миграции нужно с доверенным search_path владельца БД. Это защита конкретных DB-проверок от подмены имён, не независимый контроль A19 и не защита от владельца всей инфраструктуры. Актуальные выполненные прогоны текущей версии — в [STATUS.md](STATUS.md).

## Доставка ЭДО и обновление существующего стенда

Worker входит в процесс API. Он обращается к собственному /internal/edo/events по loopback-порту из HTTP_ADDR, без браузерного origin / внешнего адреса. Порт должен быть фиксированным; произвольный удалённый адрес доставки не поддерживается. В Compose /internal/ скрыт nginx; только HMAC проверяет источник события, cookie оператора эту проверку не заменяет.

После двух подписей обработчик забирает устойчивое основание, получает lease, отправляет прежние байты / event ID с новой транспортной меткой времени, сохраняет результат. Сеть и 5xx повторяются; итоговый 4xx требует проверки причины и нового исправленного события. GET панели показывает PENDING / DELIVERED, HTTP-статус и результат; DELIVERED не означает успешную выплату. 202 означает только постановку в очередь.

Обновление 006 → 008 не сбрасывает данные. Сохранённые раньше READY_TO_SETTLE автоматически попадают в доставку: при точном событии и отсутствии блокировок они могут исполниться после запуска нового API. Перед обновлением сохраните согласованную резервную копию БД, ключа и PDF, сверьте ожидающие сделки. Это ожидаемое продолжение учебного процесса. На этапе разработки новый стенд выплат изолирован от прежней базы ручных сценариев; перенос / удаление её данных не выполняется.

Спор, запрос отмены, наступивший срок и отказ в отмене не освобождают деньги автоматически. Подтверждение отмены другой организацией допустимо и после срока; активный резерв получает RELEASED и сделка REFUNDED, без перевода исполнителю. Без резерва результат CANCELLED. После SETTLED эти команды недоступны; возврат после выплаты в этот этап не входит.

## Исторический этап обновления с историей / экспортом

Этап feature/deal-history-export добавляет три GET-маршрута и интерфейс, не изменяя миграции 001–008. Повторные migrate / bootstrap сохраняют данные. Пересобрать API и web штатным способом; на том этапе readiness оставалась stage=edo_settlement, поскольку платёжная схема не менялась. ## Обновление с уведомлениями

Этап feature/in-app-notifications добавляет схему 009, GET /api/v1/notifications, пустой POST /api/v1/notifications/{id}/read и worker внутри API. Штатный порядок обновления: migrate → access → bootstrap → restart API / web. Access применяет оба файла `deploy/postgres/runtime_grants.sql` и `deploy/postgres/edo_runtime_grants.sql` после миграций; это нужно и при запуске без Docker. Применённые 001–008 не изменять и volumes не очищать. Сохраняются ключ приложения, PDF, версии условий / подписи, ledger, резервы, выплаты и результаты команд. Readiness теперь проверяет 009 и возвращает stage=notifications.

После старта worker обрабатывает и прежний pending outbox. Старые согласования, резерв / подписи, спор / решения отмены и расчёт могут появиться в кабинете как новые доставки сохранённых фактов. Notification.created_at означает время доставки, event.created_at — исходное время факта; интерфейс показывает оба. Доставка не создаёт повторную выплату и не меняет состояние сделки. Перезапуск / bootstrap не дублируют уведомления и не сбрасывают read_at. Прочитанность отдельна для каждого получателя; повтор отметки сохраняет первоначальное время.

Участник видит вкладку «Уведомления» и счётчик, фильтры «Всё / Непрочитанные / Прочитанные», постраничную ленту, отметку и переход к защищённой карточке. Polling проверяет доставки каждые 15 секунд и при возвращении фокуса; при logout / смене аккаунта старые запросы отменяются. Оператор клиентскую вкладку не получает. Почта / SMS / мессенджеры не используются. Права, получатели, исключённые события и HTTP — в [NOTIFICATIONS.md](NOTIFICATIONS.md).

Smoke v6 проверяет сохранённые доставки обеих сторон и первоначальную отметку прочтения до / после restart; его состояние не содержит cookies / паролей. На этапе выполнены 71 frontend unit, typecheck приложения / E2E, build и focused-набор уведомлений 17 API / UI / setup PASS. Итог общего набора и ручного прогона обновляется в [STATUS.md](STATUS.md); исторические прогоны выше не заменяют проверку новой схемы.
