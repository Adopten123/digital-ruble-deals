# Проверки UI и API «ПоАкту»

Обновлено: 24 октября 2026 года. Проверяются авторизация, организации, версии условий / PDF, два согласия / доработка, резерв, подписи, проверяемая доставка ЭДО / однократная выплата, спор / двусторонняя отмена, учебные счета оператора, история сделки / операторский аудит и CSV / JSON-экспорт. Доставка пользовательских уведомлений и A19 ещё не реализованы; зелёный набор не подтверждает готовность всего [ТЗ](TZ.md).

## Проверки этапа истории / экспорта

В ветке `feature/deal-history-export` реализованы три маршрута чтения истории и экспорта по [контракту API, раздел 6a](API.md#6a-чтение-и-экспорт-истории). Новый набор содержит **10 Go-тестов аудита, 6 API и 8 UI-сценариев**; общий набор — **132 E2E (66 API + 65 UI + setup)** и **63 frontend unit-теста**. Полный локальный прогон этапа завершён: **132 PASS за 5,9 минуты**. После него ручная проверка на 320 px выявила отдельный дефект при системной полосе прокрутки; финальное исправление CSS и регрессия этой границы проверены отдельным focused-прогоном: **9 UI/setup PASS за 12,5 с**. После правки также повторены 63 unit и производственная сборка. После поправки nginx к одному nosniff и перевода layout-фикстуры на внешний same-origin CSS отдельно пройдены 24 transport / audit / Swagger-сценария за 21,2 с. Результат CI окончательного HEAD нужно фиксировать отдельно.

Go проверяет безопасную проекцию фактических payload, различие бизнес-решения об отказе отмены и отклонённой команды, текущие / исторические права сторон, неизвестные типы, одинаковые timestamp, включительные границы, подписанный курсор, headers и предел 5000 событий. Отдельно проверяется CSV: кириллица / кавычки, сохранение LF и CR внутри ячеек, защита `=`, `+`, `-`, `@` после пробелов, управляющих и невидимых форматных символов.

API использует настоящий сервер: участники / посторонний / оператор, смена исполнителя, совпадение списка и CSV / JSON с теми же фильтрами, строгие параметры, идемпотентность без повторных фактов, реальная выплата свежим организациям и source `edo-emulator` без второго payment_id. UI проверяет закрытые отмены после reload, версии / авторов / причины, локальное время вместе с UTC, все страницы в экспорте, применение фильтров, сбой / явный повтор и отбрасывание позднего ответа после смены фильтра или аккаунта. Проверки ширин 320 / 375 / 768 / 1440 px и навигации оператора не заменяют осмотр с настоящей системной полосой прокрутки; он включён в HIST12–HIST13.

Курсор закрепляет верхнюю пару `(created_at, id)` первой страницы и не допускает повторного использования с другим субъектом / ресурсом / фильтрами / limit. Это не общий MVCC-снимок нескольких HTTP-запросов: поздний commit с ранним timestamp может появиться на следующей странице. Один экспорт читает один SQL-снимок. Экспорт и SQL-неизменяемость фактов не доказывают обнаружение вмешательства администратора; это отдельный A19.

## Проверки этапа ЭДО / расчёта

Предыдущий этап feature/edo-settlement: полный Go / PostgreSQL, vet и сборка прошли, включая 007/008 и проверку готовности последней схемы. Upgrade-тест действительно начинает с 001–006, сохраняет два резерва / исторические версии / подписи / ответы, сравнивает все прежние таблицы после 007/008 и повторных migrate / bootstrap, затем доставляет прежнее основание ЭДО ровно один раз.

Новые Go / PostgreSQL сценарии проверяют HMAC / время / строгую схему до inbox, same ID / другое тело, параллельные новые ID, оба порядка payout против dispute / cancel, потерянный ответ после commit, rollback / PENDING и повтор, lease / реальный HTTP sender, срок после ожидания аккаунта, int64 / overflow и выплату собственного резерва при нулевом available. Runtime-права и защищённые SQL-проверки выполняются отдельной ограниченной ролью.

Smoke v4 проверяет реальную выплату двум свежим организациям и повтор после перезапуска: PDF / подписи / исходные ответы, CONSUMED, прежний payment_id, итог доставки и отсутствие повторных проводок. Общие демосчета не расходуются. Полный единый E2E — 118 PASS за 4,4 минуты (60 API + 57 UI + setup), 55 frontend unit и обе проверки типов / сборка успешны. Ручной PAY01–PAY14 — 14 PASS; все 11 шаблонов ЭДО, 1440 / 375 / 320, итоговая сверка БД без расхождений. После исправления только подписи причины отказа отдельно прошли 2 UI/setup и финальная сборка. [Подробный отчёт](reports/2026-10-24-edo-settlement.md) содержит ограничения и CI; предыдущие результаты ниже относятся к своим версиям кода.

## Уровни проверок

Для самостоятельной проверки подготовлены [базовые кейсы, MONEY01–MONEY08, SIGN-01–SIGN-08, PAY01–PAY14 и HIST01–HIST14](MANUAL_TESTING.md): тестовые данные, действия, ожидаемые результаты, ошибки сети, несколько профилей, размеры экрана / zoom и шаблон дефекта. Это инструкция для выполнения; её пункты не объявлены пройденными автоматически.

| Набор | Что проверяет | Данные / среда |
|---|---|---|
| Go unit / integration | Валидацию, пароли / сессии, транзакции, ограничения БД, bootstrap, атомарность черновика / результата команды / аудита / outbox, конкурентные повторы | Настоящая PostgreSQL при заданном `TEST_DATABASE_URL`; отдельная случайная схема на тест |
| Node unit | Точные денежные преобразования, API-клиент, сохранение команды неизвестного исхода, даты / курсоры | Функции frontend; локальный подставной transport там, где проверяется сам клиент |
| Playwright API | Реальные HTTP-маршруты, серверные права, cookie / CSRF, протокол, сохранённые результаты и поиск | Запущенный API и PostgreSQL, без подмены ответов |
| Playwright UI | Формы, переходы, реальную регистрацию / создание / чтение, восстановление после сбоев, desktop / mobile | Chromium и тот же API; явные сбои вводятся перехватом отдельных запросов |
| HTTP smoke | Готовность опубликованного стенда, основной контракт, повторный bootstrap и сохранение черновика / ключа после перезапуска | Compose или локальный API; инструкция в [RUNNING.md](RUNNING.md) |

В UI успешные ответы не подменяются. Перехват используется для явно заданных `401`, `503`, обрыва сети, задержки и окончательного отказа валидации. После снятия сбоя повтор обращается к настоящему серверу. Особенно важный сценарий: `route.fetch()` сначала получает настоящий `201` и ID сохранённого черновика, затем ответ браузеру обрывается. После reload интерфейс восстанавливает условия и ключ; ручной повтор отправляет прежнее тело / ключ, а серверный список содержит ровно прежний ID.

## Подготовка изолированного стенда

Нужны Node.js 22 и работающий тестовый стенд из [RUNNING.md](RUNNING.md). Compose-проект для тестов должен иметь отдельное имя, порт и named volumes, чтобы синтетические записи не попадали в демонстрацию пользователя. Пример PowerShell из корня репозитория:

```powershell
$env:POAKTU_PORT = '18080'
$env:POAKTU_ORIGIN = 'http://localhost:18080'
docker compose -p poaktu-e2e up --build --wait --wait-timeout 180
$env:E2E_BASE_URL = 'http://localhost:18080'
$env:E2E_API_URL = $env:E2E_BASE_URL
Set-Location web
npm ci --ignore-scripts
npm run typecheck:e2e
```

Стенд на стандартном порту 8080 тоже подходит: установить `E2E_BASE_URL=http://localhost:8080` и такое же `E2E_API_URL`; его `POAKTU_ORIGIN` должен совпадать. Не подменять `localhost` на `127.0.0.1` только в одном из значений: cookie / проверка Origin должны соответствовать реальному подключению.

Зависимость `@playwright/test` закреплена как **1.64.1** в `web/package.json` и lock-файле. Для полного набора установить соответствующий Chromium из папки `web`:

```sh
npx --no-install playwright install chromium
npm run test:e2e
```

На Linux для установки браузера вместе с системными библиотеками используется `npx --no-install playwright install --with-deps chromium`. API-проект браузер не запускает и скачивания Chromium не требует:

```sh
npm run test:api
```

Выбрать один нужный запуск. `test:e2e` уже включает API, desktop, mobile и setup. Отдельные команды Playwright запускать последовательно: они используют общие `actors.json`, состояния сессий, папки результатов и HTML-отчёт. Параллельные независимые процессы CLI могут перезаписать эти файлы.

Конфигурация использует одного worker, без автоматических повторов упавшего теста. Сессии четырёх ролей подготавливаются один раз на запуск и затем переиспользуются. Серверные ограничители не отключаются: 30 auth-запросов с одного IP в минуту, 10 на email в минуту и ограничение одновременно проверяемых паролей. Несколько быстрых прогонов подряд могут исчерпать лимит; дождаться следующей минуты или перезапустить только API своего изолированного тестового стенда. Не перезапускать чужую демонстрацию ради тестов.

Для разработки без Docker предусмотрен `npm run dev:e2e`: Vite слушает `127.0.0.1:18080` и проксирует API на `127.0.0.1:18081`. Такой API запускать с отдельной учебной БД, `HTTP_ADDR=127.0.0.1:18081`, `APP_ORIGIN=http://localhost:18080`, отдельным файлом ключа и обычными migrate / bootstrap из RUNNING.md. Этот режим не занимает порты демонстрации 5173 / 8081.

## Границы и результаты запуска

`E2E_BASE_URL` по умолчанию равен `http://localhost:18080`; `E2E_API_URL` по умолчанию совпадает с ним. Отдельный API-origin допускается только с тем же hostname, чтобы состояния cookie работали и в UI. Адреса ограничены HTTP(S) loopback без credentials, пути, query и hash. Setup требует успешный `/readyz` с `contour: "test"` и `stage: "edo_settlement"`. Это защита от ошибочного адреса, а не автоматическое создание или изоляция БД: стенд нужно подготовить отдельно.

Тесты создают синтетические организации и сделки с уникальными ID / названиями. Денежные сценарии используют свежие организации, учебные операторские зачисления, резерв / освобождение и выплату на тестовых средствах. Они не очищают БД, не удаляют историю и не расходуют общий seed; изменяют только созданные ими условия и факты. Поэтому записи на выбранном учебном стенде сохраняются после запуска. Для остановки изолированного Compose-проекта с сохранением данных:

```sh
docker compose -p poaktu-e2e down
```

Удаление volumes не требуется. Следующий запуск может использовать сохранённый учебный стенд.

Артефакты находятся в:

- `web/playwright-report/` — HTML-отчёт;
- `web/test-results/artifacts/` — результаты, снимки и trace при сбое;
- `web/test-results/auth/` — приватные cookie-состояния ролей и `actors.json`.

Все эти папки исключены из Git. Состояния авторизации содержат действующие учебные сессии; их не прикладывать к публичным отчётам. При передаче trace / снимков учитывать, что они могут содержать временные cookie, синтетические email, тела команд и данные выбранного тестового стенда. CI загружает только HTML-отчёт и папку `artifacts`, без `auth`, хранит результат семь дней и останавливает свой контур в шаге `always()`.

## Связь с критериями A01–A20

«Проверяется сейчас» относится к существующим функциям, а не к готовности всего прототипа. Будущие сценарии не добавлены как фиктивно проходящие или пропущенные тесты.

| Критерий | Статус текущего покрытия | Что ещё требуется |
|---|---|---|
| A01 — чистый Compose | Частично: прошлый этап 118 E2E подтверждён Linux CI через Compose / nginx, bootstrap / restart smoke успешны; результат нового CI фиксируется отдельно | Чистый запуск на втором пользовательском ПК |
| A02 — регистрация / вход / выход | Проверяется сейчас Go + API + UI: нулевой счёт, хеш, сессия / отзыв | Повторять проверки при изменениях авторизации |
| A03 — чужие ресурсы / подмена роли | Организации, каталог, сделки, текущие / исторические PDF и аудит / экспорт, прежний и новый исполнитель, подмена ID / роли | Расширять регрессии при новых маршрутах |
| A04 — изменение условий / PDF | Новые версии, сброс согласий, старый replay без реактивации, запрет после резерва; старый PDF нельзя подписать | Повторять при изменении привязок |
| A05 — резерв / недостаток средств | Проверяется Go / API / UI: полный ACTIVE-резерв, недостаток, неизменность total, сохранённый отказ и новый ключ после пополнения | Сохранять проверки при новых денежных командах |
| A06 — денежные гонки | Две сделки / available, резерв против списания; оба порядка payout против dispute / cancel, параллельная доставка и другой ACTIVE-резерв | Продолжать регрессии при новых денежных командах |
| A07 — ключ / конфликт тела | JSON / PDF / деньги / подписи / спор / отмена и операторская очередь, сохранённые успехи / отказы; inbox same ID / другое тело | Не переносить ключ между субъектами / командами |
