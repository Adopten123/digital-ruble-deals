# Реализованный HTTP API «ПоАкту»

Обновлено: 23 октября 2026 года. Версия API — `/api/v1`, этап — `test_signatures`. Тестовый контур. Расчёты и ЭДО эмулируются.

Это справочник **работающего кода**. [OpenAPI 3.0.3](openapi.json) содержит все 25 операций, схемы, параметры, примеры тел и ошибок. Реализованы черновики / версии условий, PDF, два согласия, rework до резерва, резерв всей суммы и операторские счета / пополнения / списания. [API.md](../API.md) сохраняет проект остальных функций ТЗ. Тестовые подписи после резерва и основание ЭДО реализованы. Выплата, доставка ЭДО, споры / согласованная отмена, доставка уведомлений, экспорт и A19 пока не предоставляются этим сервером.

## Адреса и Swagger

| Режим | Приложение / Swagger | API |
|---|---|---|
| Compose | `http://localhost:8080/`, `/api-docs/` | Тот же origin; `/api/v1`, `/healthz`, `/readyz` |
| Разработка | `http://localhost:5173/`, `/api-docs/` | Vite proxy → `127.0.0.1:8081` |
| Отдельный тестовый стенд | `http://localhost:18080/`, `/api-docs/` | Vite proxy → `127.0.0.1:18081` |

Запуск сервера, БД, миграций и учебные аккаунты — в [RUNNING.md](../RUNNING.md). Swagger собирается вместе с frontend; сам Go-сервер HTML документации не раздаёт. Файл для импорта в инструменты: `docs/api/openapi.json`; в запущенном web — `/api-docs/openapi.json`. Для другой настройки портов использовать фактический origin стенда.

Открывать Swagger через HTTP, а не двойным щелчком по HTML. В Swagger:

1. Выполнить `GET /api/v1/auth/csrf` через Try it out → Execute.
2. Скопировать `csrf_token` в Authorize → **csrfToken**. `sessionCookie` вручную не заполнять: cookie `HttpOnly` сохраняет и отправляет браузер.
3. Выполнить login или register. Сменить значение **csrfToken** на новое из успешного ответа.
4. Выполнять защищённые запросы на том же origin. Можно также войти через приложение и затем получить CSRF в Swagger.
5. Для создания взять ID исполнителя из каталога и будущий срок. Для каждой новой доменной команды задать новый `Idempotency-Key`; при повторе неизвестного исхода сохранить прежние ключ и тело. Execute выполняет настоящую команду учебного стенда.
6. После создания загрузить / сгенерировать PDF для актуальной версии. Каждый участник отдельно принимает точные `deal_version`, `document_id`, `document_version`, `document_sha256` из карточки. Для перехода к другому участнику выполнить logout / login и обновить CSRF; оператор не может согласовать за сторону.

Swagger не включает автоповторы, не сохраняет авторизацию в localStorage и не отправляет спецификацию внешнему валидатору. При смене аккаунта в другой вкладке сначала перечитать `/auth/me`, обновить CSRF и проверить организацию. `X-Expected-User-ID` рекомендуется для действий из интерфейса. Авторизация через cookie в браузере описана в [руководстве Swagger](https://swagger.io/docs/specification/v3_0/authentication/cookie-authentication/); настройки UI — в [официальной документации](https://swagger.io/docs/open-source-tools/swagger-ui/usage/configuration/).

## Общие правила

- JSON UTF-8, `Content-Type: application/json`; одно тело-объект до **16384 байт**. Исключения — multipart загрузки PDF и бинарные ответы просмотра / скачивания. Неизвестные поля команд, неверные типы, `null` вместо строк и несколько значений JSON отклоняются. Logout требует полностью пустое тело.
- ID непрозрачны. Отображаемое название не является идентификатором и не подтверждает полномочия. Все роли / организация берутся из серверной сессии.
- Деньги — **десятичные строки копеек** до `9223372036854775807`. Сделка положительна; остатки могут быть `"0"`. Не использовать float / JavaScript Number. `"30000000"` = 300 000 ₽. `"01"`, `"+1"`, `"1.0"`, `"1e2"` и JSON-числа недопустимы.
- Время — RFC 3339. Входной offset преобразуется в UTC; срок создания / изменения усекается до микросекунд перед хешированием и хранением. Серверное время БД определяет наступление срока. Версии передаются положительными целыми JSON-числами, денежные суммы — строками.
- Ответы API получают `X-Request-ID`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, защитную CSP. Тело ошибки содержит `request_id`. В повторном сохранённом отказе он относится к исходной команде, а заголовок — к текущему HTTP-запросу.
- Стандартные ответы неизвестного метода `net/http` и ошибки nginx могут быть текстом/HTML, а не объектом Error. При сбое генерации request ID также возможен простой `503 unavailable`. Клиент должен выдерживать не-JSON ошибку. Go автоматически обслуживает HEAD для зарегистрированных GET; HEAD не является отдельной бизнес-операцией.
- CORS для другого origin не предоставляется. `localhost` и `127.0.0.1` — разные origin; порт тоже значим. В браузере изменяющий запрос получает Origin. В CLI его нужно задать равным `APP_ORIGIN`, даже если запрос идёт напрямую на backend.

## Сессия, CSRF и права

Сессия `pa_session`: случайный токен, в БД хранится хеш; cookie `HttpOnly`, `SameSite=Lax`, `Path=/`, 24 часа, `Secure` при HTTPS. `GET /auth/csrf` возвращает токен и при необходимости cookie `pa_csrf` с такими же защитными атрибутами. Токен связан с cookie и текущей сессией. Вход / регистрация ротируют прежнюю сессию браузера и CSRF; logout отзывает сессию на сервере и очищает обе cookie. Получение CSRF до входа не создаёт пользователя.

Все POST и PATCH требуют `X-CSRF-Token`, точного `Origin=APP_ORIGIN` и отсутствия `Sec-Fetch-Site: cross-site`. Это относится также к login/register и multipart загрузке. На защищённых маршрутах сначала проверяются сессия и необязательное `X-Expected-User-ID`, затем CSRF / параметры HTTP и предметные права. На `/auth/me` заголовок также проверяется общим middleware, если отправлен; при обнаружении текущего аккаунта его следует опускать.

`X-Expected-User-ID` только сравнивает показанный пользователю ID с реальной сессией. При несовпадении `409 SESSION_CHANGED` возникает **до исполнения**. Нельзя использовать заголовок для выбора чужого аккаунта. Для исходной сохранённой команды после конфликта не создавать новый ключ автоматически.

| Кто | Каталог | Свой счёт | Создание / список | Карточка сделки |
|---|---|---|---|---|
| Без сессии | 401 | 401 | 401 | 401 |
| USER / ORG_OWNER | Публичные поля | Только свой | Своя организация | Только заказчик / исполнитель |
| Другая организация | Публичные поля | Только свой | Только свои сделки | 404 чужой сделки |
| DEMO_OPERATOR без организации | Публичные поля | 403 | 403 | 404 |

У пользователя одна организация. Заказчик / исполнитель определяются **для каждой сделки**, не при регистрации. Новая организация получает нулевой счёт. Публичный справочник не раскрывает email, участников, остатки, сделки или документы других организаций.

### Регистрация и ответы сессии

```json
{
  "email": "owner@example.test",
  "password": "LocalDemoOnly2026!",
  "organisation": {"name": "Учебная компания", "kind": "COMPANY"}
}
```

Email нормализуется trim/lowercase, максимум 254 байта. Пароль регистрации — 12–128 символов Unicode, максимум 512 байт; имя — 2–200 символов после trim, без управляющих символов. `kind`: `COMPANY` или `IP`. Login принимает `{email,password}` существующего аккаунта; сервер проверяет пароль и ограничивает его размер 512 байт, а не выдаёт информацию о существовании email.

Authenticated содержит `user:{id,email,system_role}`, `organisation:{id,name,kind,role}` или null, `session_expires_at` и **`csrf_token`**. `/auth/me` возвращает те же поля без `csrf_token`. Session cookie нельзя получить из JavaScript; не переносить её в Bearer-заголовок.

Общий limiter login/register: **30 попыток / минуту на RemoteAddr**, **10 / минуту на нормализованный email**, до четырёх параллельных проверок пароля. За nginx один proxy-адрес имеет общий бюджет; подделанные forwarding-заголовки игнорируются. `429` содержит `Retry-After: 60`, а занятые слоты — `1`. Клиент выдерживает паузу, не отключает защиту и не запускает быстрый цикл повторов. Limiter локален процессу, не является распределённой защитой production-кластера.

### Остатки и список организаций

OwnOrganisation содержит `{organisation,account}`. Account: `id`, `currency:"RUB"`, `total_kopecks`, `reserved_kopecks`, `available_kopecks`. Выполняется `available = total − reserved`; создание / изменение / PDF / согласование / rework ничего не резервируют и не переводят. Не вычислять баланс из списка сделок.

CounterpartyPage: `{items:[{id,name,kind,is_demo}],next_cursor:string|null}`. `q` после trim — до 200 символов; поиск по подстроке названия без учёта регистра и по подстроке ID с учётом регистра. Названия не уникальны. `%` / `_` не являются wildcard. `limit` 1–100, по умолчанию 20; пустой limit тоже даёт 20. Курсор до 2048 символов подписан и привязан к q; сохранять q при следующей странице. Сортировка `created_at DESC,id DESC`. Текущий обработчик организаций игнорирует неизвестные query-поля и берёт первое повторное значение; не переносить сюда строгие правила списка сделок.

### Создание черновика

```json
{
  "supplier_party_id": "ID_ИЗ_КАТАЛОГА",
  "title": "Печать партии упаковки",
  "description": "Печать согласованного изображения. Один акт на всю партию.",
  "amount_kopecks": "30000000",
  "currency": "RUB",
  "deadline_at": "2030-12-25T12:45:00Z"
}
```

Подставить настоящий ID другой учебной организации и будущий срок. Все шесть полей обязательны и строковые. ID исполнителя после trim — 1–128 символов; название 1–200; описание 1–5000. В названии/ID запрещены управляющие символы; описание допускает `\n`, `\r`, `\t`. Trim выполняется до канонизации. Создание не означает согласие сторон, не меняет остатки и не подтверждает работы.

Deal возвращает `id`, `deal_version`, `status`, обе стороны `{id,name,kind}` и их ID, условия, `created_at` / `updated_at`. Сразу после создания версия 1, `document:null`, `agreements:[]`; затем PDF и согласия заполняются. `reserve` — null либо объект резерва ниже. Во всех ответах текущего этапа `payment_id`, `dispute`, `cancellation_request` равны null, `signatures` — до двух типизированных фактов текущего PDF; выплата / спор / отмена ещё отсутствуют.

GET вычисляет `REVIEW_REQUIRED` для истёкшего DRAFT / AGREED / FUNDED / READY_TO_SETTLE по времени БД. Сохранённый ответ команды при повторе ключа остаётся историческим; для актуального состояния сделать GET. Все команды сделки проверяют срок после ожидания транзакционных блокировок, PDF — также после подготовки / записи файла. Изменением срока нельзя возобновить уже просроченную сделку. Фоновое обновление состояния для этих проверок не требуется.

### Изменение условий и версии

```json
{"expected_version":1,"title":"Уточнённый тираж","amount_kopecks":"30000000"}
```

`PATCH /deals/{id}` доступен только заказчику в DRAFT до срока и до первого резерва. `expected_version` обязателен; остальные поля создания необязательны. Строки нормализуются / проверяются так же, как при создании; `null` вместо строки не означает отсутствие поля и даёт 400. Заказчика менять нельзя. Нормализованный no-op возвращает ту же `deal_version` и сохраняет активный PDF / согласия; реальное изменение создаёт `deal_version+1`, снимает PDF и текущие согласия. Прежние версии остаются в БД. Изменение исполнителя сразу меняет доступ к карточке и PDF.

`expected_version` / `deal_version` — версия условий, без технического `row_version`. Несовпадение с текущей даёт `409 VERSION_CONFLICT`; версия проверяется после блокировки сделки. Два конкурентных изменения одной версии с разными ключами не могут создать две новые редакции.

### PDF: загрузка, генерация и приватное чтение

`POST /deals/{id}/documents` принимает ровно два multipart-поля, каждое один раз: текстовое `expected_deal_version` и файл `file`. Версия — каноническое положительное целое; расширение `.pdf`, MIME файла `application/pdf`. Предел файла **5 MiB**, предел всего тела — 5 MiB + 64 KiB. Дополнительные / повторные поля дают 400, неверное расширение / MIME — `422 INVALID_DOCUMENT`, превышение размера — 413. Граница multipart не входит в отпечаток команды; SHA256 точных байтов и нормализованное безопасное имя входят.

Генерация принимает JSON:

```json
{"expected_deal_version":1,"template_id":"printing-acceptance-v1"}
```

Обе команды доступны заказчику в DRAFT / AGREED до срока / первого резерва и возвращают `201 {deal,document}`. Любой новый PDF увеличивает `deal_version` и снимает согласия, даже если байты совпадают. Документ имеет стабильный `id`, номер `document_version` растёт с каждой загрузкой / генерацией. PDF генератора содержит **итоговую** версию сделки, учебную маркировку, условия и точные целые копейки. Согласование, подписание и оплата в тексте различаются; генерация не подтверждает исполнение работ.

Document: `{id,deal_id,deal_version,document_version,sha256,file_name,size_bytes,content_type,created_at}`; `content_type` всегда `application/pdf`, хеш — 64 строчных hex-символа. `Deal.document` содержит только активный PDF текущей версии условий. После PATCH / rework он null, но исторические метаданные и байты сохранены.

`GET /documents/{id}` без `version` читает последнюю сохранённую версию PDF, включая неактивную; с `version` — конкретную. `/view` и `/download` требуют единственного положительного целого `version`; неизвестные / повторные query-параметры дают 400. Документ выдаётся организации, которая является **и текущей стороной сделки, и стороной исторической версии условий этого PDF**. Заменённый исполнитель теряет доступ ко всем PDF сделки, новый не получает старые PDF другой организации. Недоступный документ / версия — 404, оператор без организации также получает 404.

Файлы находятся в приватном `DOCUMENTS_DIR`; клиенту не выдаются storage key / путь и публичный URL. Ответы `/view` и `/download` содержат одни и те же байты `application/pdf` с `nosniff`, `no-store`, CSP `sandbox; default-src 'none'; frame-ancestors 'self'` и `Cross-Origin-Resource-Policy: same-origin`. Download устанавливает `attachment`, view — `inline`. Перед выдачей сверяются SHA256 и размер; повреждённый / исчезнувший файл не выдаётся и даёт 503.

Валидатор принимает ограниченное **статическое подмножество PDF**: до 100 страниц и 5000 объектов, без шифрования, форм, аннотаций / ссылок, JavaScript, действий, вложений, multimedia и неподдерживаемых потоков. Подробные пределы парсера, генератора и файлового хранилища — в [documentfile/README.md](../../internal/core/documentfile/README.md). Это проверка формата / политики, а не антивирус и не смысловая сверка текста с условиями. Неподдерживаемый символ встроенного шрифта при генерации также даёт 422; можно подготовить и загрузить соответствующий политике PDF.

### Два согласия и возврат на доработку

```json
{"deal_version":2,"document_id":"ID_ИЗ_КАРТОЧКИ","document_version":1,"document_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}
```

В `POST /deals/{id}/agree` подставить реальные ID / версию / SHA256 активного PDF, а не хеш-заполнитель примера. Действовать может каждая сторона до срока / первого резерва. Без актуального PDF — `409 DOCUMENT_REQUIRED`, с другим ID / номером / хешем — `409 DOCUMENT_MISMATCH`, с прежней версией условий — `409 VERSION_CONFLICT`. Первое согласие оставляет DRAFT, второе от **другой организации** даёт AGREED. Согласие не является тестовой или квалифицированной подписью и не меняет деньги.

`Deal.agreements` содержит только текущие факты `{id,organisation_id,user_id,deal_version,document_id,document_version,document_sha256,created_at}`. Повтор той же стороны с новым ключом возвращает один факт, не создаёт второй голос. Карточка / список читают условия, PDF и согласия одним SQL-снимком. История согласий сохраняется при смене условий / PDF, но повтор старого успешного ключа не активирует её вновь.

```json
{"deal_version":2,"reason":"Уточнить объём партии перед резервом"}
```

`POST /deals/{id}/rework` доступен каждой стороне только в AGREED до срока / первого резерва. Причина — 1–2000 символов после trim. Результат `200 Deal`: версия +1, DRAFT, без активного PDF и текущих согласий. Причина сохраняется в аудите, исторические PDF / согласия остаются. После нового PDF обе стороны явно согласуют новую версию. Два конкурентных rework создают только одну новую редакцию. Другой этап / факт первого резерва даёт `409 INVALID_STATE`; существующий резерв не освобождается.

### Резервирование и денежные проверки

```json
{"deal_version":2}
```

`POST /deals/{id}/reserve` доступен только заказчику в AGREED до срока / первого резерва. Версия должна совпадать с текущей; активный PDF и два согласия разных организаций проверяются по точному кортежу версий / SHA256 независимо от строки status. Сначала под блокировкой сделки читаются байты PDF и сверяются хеш / размер. Исчезнувший / повреждённый файл даёт 503 без денег; после восстановления можно повторить исходный ключ.

Далее сервер блокирует счёт и читает резерв, заново измеряет серверное время БД и проверяет `total − reserved >= amount`. Истёкший срок даёт `422 DEADLINE_PASSED`, недостаток — `422 INSUFFICIENT_AVAILABLE_FUNDS`, отсутствие двух согласий при AGREED — `422 CONSENTS_MISSING`. Не тот этап / уже финансированная сделка — `409 INVALID_STATE`, старая версия — `409 VERSION_CONFLICT`; без PDF — `409 DOCUMENT_REQUIRED`, неверный контекст — `409 DOCUMENT_MISMATCH`. Исполнитель получает 403, чужая организация / оператор без организации — 404; без сессии — 401.

Ответ `201 {reserve,deal}` содержит Reserve `{id,deal_id,deal_version,account_id,amount_kopecks,currency,status:"ACTIVE",created_at}`; такой же объект находится в `Deal.reserve`. Сумма целиком резервируется, состояние становится FUNDED и сохраняется дата первого резерва; `deal_version` и total неизменны, растёт reserved. Денежных проводок при резервировании нет, исполнитель ничего не получает. Один reserve на deal_id, неизменяемый в текущем этапе. Повтор исходного ключа возвращает прежние байты 201; новый ключ уже FUNDED даёт 409 без удвоения. Для актуальной карточки / остатков после replay сделать GET. После первого резерва изменение условий / PDF / согласий и rework запрещены; истечение срока не освобождает резерв. Подпись, выплата и release будут следующими этапами.

### Учебные счета оператора

`GET /demo/accounts` доступен только DEMO_OPERATOR, обычный участник получает 403. Результат `{items,next_cursor}`, элементы `{id,organisation:{id,name,kind},currency,total_kopecks,reserved_kopecks,available_kopecks}`. Все суммы — строки; системные счета исключены. Строгие параметры: q до 200 символов после trim, limit 1–100 по умолчанию 20, cursor до 4096 символов. Поиск — буквальная подстрока без регистра в ID счёта, ID и названии организации. Сортировка `created_at DESC,id DESC`; курсор подписан и привязан к user_id оператора, q и limit. Неизвестные / повторные поля, пустой / неверный limit и подменённый курсор дают 400. Меняя фильтр, начинать без курсора.

```json
{"amount_kopecks":"50000","reason":"Учебные средства для отдельного сценария"}
```

`POST /demo/accounts/{id}/credits` и `/debits` требуют CSRF / Origin, Idempotency-Key и две строки тела. Сумма — положительная каноническая строка int64, причина — 1–2000 Unicode-символов после trim; переводы строк / табуляция допустимы. Другая роль — 403, отсутствующий / системный счёт — 404. Ответ `201 {transaction_id,account}`: ID денежной пачки и актуальный клиентский счёт, без секрета или системного остатка.

Credit перемещает учебную сумму от DEMO_ISSUANCE клиенту; debit расходует только `available` и зачисляет её на фиксированный DEMO_DEBITS. Резервы других сделок не расходуются. Две разные проводки одной валюты равны по модулю и противоположны; batch / entries неизменяемы. `422 AMOUNT_OVERFLOW` защищает и клиентский total, и отрицательный противосчёт эмиссии, и системный счёт списаний. `422 INSUFFICIENT_AVAILABLE_FUNDS` сохраняет отказ без движения денег. Новый ключ после исправления баланса — новая команда; прежний отказ по прежнему ключу остаётся прежним.

Общий ledger сам блокирует счета в порядке ID, проверяет положительный amount, разные from / to, доступный остаток источника и int64-границы **до INSERT**. Deferred constraints сверяют `total` с суммой всех проводок и `reserved` с ACTIVE-резервами, требуют две сбалансированные проводки и разрешённое направление операторского движения. Это дополнительные ограничения runtime-роли, а не замена авторизации / транзакций или независимый контроль администратора БД. Миграция 005 закрепляет разрешение таблиц внутри guard-функций за доверенной схемой и явно ставит pg_temp последним, закрывая подмену таблиц временными объектами.

### Идемпотентность и неизвестный исход

`Idempotency-Key`: ровно один заголовок, 16–128 печатных ASCII-символов без пробелов; UUID подходит. Область — организация + операция + ресурс + ключ: CREATE_DEAL / `/deals` для создания; PATCH_DEAL, UPLOAD_DOCUMENT, GENERATE_DOCUMENT, AGREE_DEAL, REWORK_DEAL, RESERVE_DEAL / `/deals/{id}` для остальных. Для оператора область — user_id + DEMO_CREDIT / DEMO_DEBIT + `/demo/accounts/{id}` + ключ, отдельная таблица operator_command_results. Сохранить тело и ключ **до** отправки.

| Результат | Что делать |
|---|---|
| 200 / 201 | Сохранить результат. Повтор того же ключа и канонического тела вернёт прежние статус и байты ответа |
| Сохранённый семантический 400 / 403 / 404 / 409 / 422 | Исправление условий — новая команда с новым ключом; старый отказ повторяется |
| 409 IDEMPOTENCY_CONFLICT | Ключ уже связан с другими условиями. Проверить исходную команду и список |
| 409 SESSION_CHANGED | Перечитать сессию, проверить аккаунт. Исходная команда остаётся у исходной организации / пользователя оператора |
| 401 / CSRF_INVALID | Восстановить нужную сессию / CSRF, затем явно проверить прежнюю команду |
| Сеть / timeout / 503 | Исход неизвестен. Повторить **прежнее тело и ключ**, не создавать новую команду |

Синтаксические ошибки JSON / multipart, неизвестные поля, неверные типы, заголовки / CSRF / сессия и скрытый чужой ресурс возникают до сохранения команды. Неверный Idempotency-Key и отказ HTTP-проверок файла по MIME / расширению / размеру не сохраняются. Предметный отказ участнику (например, PATCH исполнителя), неверные условия / сумма, отсутствующий новый исполнитель, stale version / PDF, истёкший срок, недостаток available / переполнение и не прошедшее проверку содержимое PDF сохраняются вместе с аудитом. Сохранённый результат не переоценивается по новому времени; авторизация текущего участника проверяется и при replay.

Успех атомарно включает предметные факты / состояние, результат команды, аудит и pending outbox; доставка outbox ещё не реализована. Файл записывается перед фиксацией БД. Отказ / неизвестный исход commit может оставить недостижимый файл; опубликованный файл автоматически не удаляется, поскольку commit мог состояться. Полученный до ошибки commit успешный DTO не выдаётся клиенту как подтверждённый успех. При повторе старого ключа после других команд для актуальной карточки дополнительно выполнить GET.

### Поиск сделок и пагинация

`GET /api/v1/deals?q=...&status=DRAFT&role=customer&limit=20` принимает только `q,status,role,created_from,created_to,limit,cursor`, каждое не более одного раза. Неизвестные / повторные поля, неверный escape, пустые даты / limit и обратный период дают 400.

`q` до 200 Unicode-символов после trim ищет ID / название сделки и ID / название контрагента без учёта регистра во всех четырёх полях. `role` — customer или supplier, пустой — обе. Даты RFC 3339 включительны: `created_from <= created_at <= created_to`. Frontend разворачивает выбранные календарные дни в своём часовом поясе до последней микросекунды конечного дня.

`status` допускает DRAFT, AGREED, FUNDED, READY_TO_SETTLE, DISPUTED, CANCELLATION_PENDING, REVIEW_REQUIRED, SETTLED, CANCELLED, REFUNDED; текущая реализация может вернуть DRAFT / AGREED / FUNDED / READY_TO_SETTLE / REVIEW_REQUIRED. Допуск остальных фильтров не означает реализацию перехода. Пустой статус — все.

`limit` 1–100 (по умолчанию 20). `cursor` до 4096 символов связан с организацией и **всеми фильтрами, включая limit**. Следующая страница возвращает тот же набор параметров + next_cursor. При изменении фильтра начать заново без курсора. Сортировка — время создания и ID от новых к старым. Страницы не являются замороженным снимком всей БД.

## Ошибки

```json
{"error":{"code":"SESSION_CHANGED","message":"Аккаунт изменился. Обновите кабинет"},"request_id":"synthetic-request-id"}
```

| HTTP | Коды | Значение |
|---|---|---|
| 400 | INVALID_REQUEST, INVALID_AMOUNT, IDEMPOTENCY_KEY_REQUIRED | Валидация данных, запроса или ключа |
| 401 | AUTH_REQUIRED, SESSION_EXPIRED, INVALID_CREDENTIALS | Нет сессии / истекла / отказ входа |
| 403 | FORBIDDEN, CSRF_INVALID | Нет предметного права либо ошибка источника / токена |
| 404 | RESOURCE_NOT_FOUND | Ресурс отсутствует либо скрыт; также отсутствующий исполнитель при создании |
| 409 | EMAIL_CONFLICT, IDEMPOTENCY_CONFLICT, SESSION_CHANGED, VERSION_CONFLICT, INVALID_STATE, DOCUMENT_REQUIRED, DOCUMENT_MISMATCH | Email / ключ / аккаунт либо конфликт текущих условий, состояния или PDF |
| 413 | PAYLOAD_TOO_LARGE | JSON более 16 KiB, файл более 5 MiB либо multipart более 5 MiB + 64 KiB |
| 415 | UNSUPPORTED_MEDIA_TYPE | Нужен application/json либо multipart/form-data для загрузки |
| 422 | DEADLINE_PASSED, INVALID_DOCUMENT, CONSENTS_MISSING, INSUFFICIENT_AVAILABLE_FUNDS, AMOUNT_OVERFLOW | Срок / PDF / согласия, недостаток available либо выход за диапазон int64 |
| 429 | RATE_LIMITED | Учитывать Retry-After |
| 500 | INTERNAL_ERROR | Непредвиденный отказ |
| 503 | TEMPORARILY_UNAVAILABLE | Недоступность инфраструктуры; исход команды нужно выяснить |

Будущие коды из API.md и зарезервированные сообщения frontend не являются текущими ответами сервера. Одинаковые HTTP-коды могут иметь разную семантику: всегда проверять `error.code`.

## Пример CLI: вход, чтение, выход

POSIX shell, curl и jq; запускать из отдельной временной папки. Данные примера публичные учебные. Файлы cookie/ответов содержат действующую сессию, не коммитить и не публиковать. Этот пример не создаёт сделку и не переводит средства.

```sh
set -eu
BASE_URL=http://localhost:8080
ORIGIN=http://localhost:8080
curl --fail-with-body -sS -c cookies.txt "$BASE_URL/api/v1/auth/csrf" > csrf.json
CSRF=$(jq -er .csrf_token csrf.json)
curl --fail-with-body -sS -b cookies.txt -c cookies.txt \
  -H "Origin: $ORIGIN" -H "X-CSRF-Token: $CSRF" \
  -H 'Content-Type: application/json' \
  --data '{"email":"customer@demo.poaktu.local","password":"PoaktuDemo2026!"}' \
  "$BASE_URL/api/v1/auth/login" > session.json
CSRF=$(jq -er .csrf_token session.json)
USER_ID=$(jq -er .user.id session.json)
curl --fail-with-body -sS -b cookies.txt \
  -H "X-Expected-User-ID: $USER_ID" "$BASE_URL/api/v1/organisations/me"
curl --fail-with-body -sS -b cookies.txt \
  -H "X-Expected-User-ID: $USER_ID" "$BASE_URL/api/v1/deals?limit=20"
curl --fail-with-body -sS -b cookies.txt -c cookies.txt -X POST \
  -H "Origin: $ORIGIN" -H "X-CSRF-Token: $CSRF" \
  -H "X-Expected-User-ID: $USER_ID" "$BASE_URL/api/v1/auth/logout"
```

При отказе остановиться и разобрать ответ; не выполнять следующие шаги с пустым токеном. `curl --fail-with-body` требует curl 7.76+. В PowerShell использовать `curl.exe` либо `Invoke-RestMethod` с WebRequestSession; синтаксис переменных этого примера относится к POSIX shell.

## Тестовая подпись после резерва

`POST /api/v1/documents/{id}/sign`, JSON `{deal_version, document_version, document_sha256}`, обязательные сессия / Origin / CSRF / Idempotency-Key. Ответ `201 {signature, deal}`. Signature содержит `id, organisation_id, user_id, deal_version, document_id, document_version, document_sha256, created_at`; массив актуальных фактов читается в `deal.signatures`, метаданные GET документа не меняются.

Участник подписывает только за свою организацию после полного резерва, до срока, при двух согласиях и точном приватном PDF. Первая подпись оставляет FUNDED; вторая создаёт READY_TO_SETTLE и одно устойчивое основание ЭДО. Денег это не перемещает и резерв не освобождает. Доставка и выплата ещё не выполняются.

Неизвестный / недоступный документ, посторонняя организация и оператор — 404. Неверные версии / хеш / состояние — 409. Срок — 422 DEADLINE_PASSED, отсутствие согласий — CONSENTS_MISSING, полного резерва — RESERVE_REQUIRED. Неверное тело — 400. Недоступный / повреждённый файл — 503 без нового факта; исход временной ошибки нужно выяснять тем же ключом.

Тот же ключ повторяет точный исторический ответ; другое тело конфликтует. Новый ключ существующей подписи возвращает тот же факт и актуальную карточку без нового аудита / outbox, даже после срока. После повтора старого ключа перечитать сделку: исторический FUNDED не отменяет последующее READY_TO_SETTLE.
