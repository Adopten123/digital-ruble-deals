В этой итерации проверка выполнена автоматическими тестами настоящего Go API / PostgreSQL и отдельными контекстами Chromium на учебном стенде `localhost:18080` / `localhost:18081`. Браузерный инструмент ручного управления по-прежнему видит внутреннюю страницу ошибки `data:`, поэтому ручные статусы остаются **25 PASS / 17 PARTIAL / 17 NOT RUN / 2 BLOCKED**. Автоматические результаты ниже их не заменяют.

## Найденные и исправленные дефекты

### QA-05. Смена аккаунта в другой вкладке

Две вкладки используют общую cookie. После выхода и регистрации другой организации во второй вкладке первая продолжала показывать прежнюю организацию. Обновление счёта возвращало `200` с остатками нового аккаунта под прежним заголовком. Если первая вкладка была перезагружена и ещё не кешировала CSRF, создание её черновика получало `201` от имени новой организации. Обе ошибки воспроизведены двумя новыми UI-регрессиями до исправления.

Клиент теперь связывает защищённый запрос с показанным пользователем через `X-Expected-User-ID`. Проверка выполняется сервером после аутентификации и до предметного обработчика; несовпадение даёт `409 SESSION_CHANGED`. Источник прав остаётся серверной сессией. Запрос не исполняется от неожиданного аккаунта; кабинет перечитывает сессию и показывает актуальную организацию с предупреждением. Автоматической повторной отправки команды нет. Подробности — в [API.md](../API.md).

Проверены чтение после смены аккаунта, создание без кеша CSRF, отзыв сессии соседней вкладкой и сохранённая команда после смены аккаунта. Команда исходной организации остаётся под её ключом sessionStorage; после явного возвращения к ней отправляются прежние тело / ключ и появляется ровно один черновик. Ошибка logout `503` также не выдаётся за успешный выход; повторный настоящий logout отзывает сессию.

### QA-06. Запоздавший ответ CSRF

После очистки кеша старый незавершённый запрос мог снова записать прежний токен; его `finally` также мог удалить ссылку на новый запрос. Новый unit-тест до исправления не получил ожидаемый отказ устаревшего запроса.

Поколение CSRF-кеша теперь инвалидирует старые ответы и их завершение. Поздний `401` прежнего запроса также не очищает токен новой сессии. Смена аккаунта во время получения CSRF отменяет прежнюю мутацию до её отправки. Защищённая команда захватывает ожидаемый аккаунт до асинхронного получения токена. Добавлены четыре unit-проверки: смена поколения, заголовки защищённых запросов, отмена команды при смене аккаунта во время preflight и поздний отказ прежней сессии.

### QA-07. Повреждённая сохранённая команда

JSON мог синтаксически разбираться, но содержать невозможную дату, пустые условия или сумму вне int64. Пустая строка хранилища считалась отсутствием команды. Unit-регрессия до исправления не получила ожидаемый отказ.

При восстановлении проверяются дата и календарь, пределы суммы / строк, допустимые поля и размер тела. Повреждённая запись блокирует новую команду с понятной ошибкой, сохраняется для выяснения результата и не отправляется. Законная команда с уже прошедшим сроком остаётся доступной для проверки прежнего результата: время не является основанием заменить её ключ. UI-регрессия проверяет пустую запись и корректный JSON с невозможной датой без единого POST; unit-тест дополнительно проверяет календарную дату, переполнение и текстовые границы.

### QA-08. Потеря поиска во время загрузки каталога

Последний локальный прогон завершился с одним таймаутом поиска: поле уже принимало ввод, но заблокированная на время загрузки кнопка submit подавляла Enter. Контролируемая задержка первоначального запроса стабильно воспроизвела отсутствие нового запроса до исправления.

Поиск теперь принимает отправку и во время предыдущей загрузки. Уже существующий номер запроса оставляет актуальной только последнюю выдачу. Новая регрессия удерживает первоначальную загрузку, отправляет поиск через Enter, проверяет результат и затем освобождает старый ответ. Отдельно прошли все четыре сценария кабинета и setup: **5 passed**.

## Проверки

После всех четырёх исправлений полный локальный набор прошёл: **62 passed за 1,5 минуты** (26 API + 35 UI + setup), включая 187 сочетаний layout-матрицы. [Linux CI на `4a7d220`](https://github.com/Adopten123/digital-ruble-deals/actions/runs/39643627257) подтвердил **62 passed за 1,4 минуты**, Go race, сборки, повторный bootstrap и smoke после перезапуска. Node: **21 passed**; production build и проверка типов приложения / E2E также успешны. До этой итерации было 55 автоматических проверок; добавлены пять UI-сценариев сессии, один UI-сценарий повреждённого сохранения и один UI-сценарий поиска, пять Node-проверок и один Go-интеграционный сценарий предусловия аккаунта.

Первый CI-прогон выявил зависимость новых сценариев от общего демо-email: при достаточной скорости повторные входы достигали штатного лимита и получали `429`. Сценарии переведены на отдельные синтетические аккаунты с уникальными email; ограничитель приложения не менялся. Повторный CI на `b8e65da` прошёл. На `4a7d220` push-прогон прошёл все 62 проверки, но параллельный PR-прогон при большей скорости достиг отдельного бюджета общего адреса nginx — 30 auth-запросов в минуту. Тестовые помощники входа / регистрации теперь проверяют `RATE_LIMITED`, соблюдают ограниченный `Retry-After` и делают явный повтор через интерфейс; предел попыток — три, лимиты сервера не менялись. Путь повторного входа дополнительно проверен управляемым `429` с ожиданием одной секунды. После этой правки отдельно прошли все пять сценариев сессии и setup: **6 passed за 11,9 с**, проверка типов E2E успешна; код приложения с момента полного зелёного прогона не менялся.

Полный `go test ./... -count=1` с настоящей PostgreSQL и `go vet ./...` прошли. БД тестов использует случайные изолированные схемы; прежние организации и история учебного стенда не удалялись. Миграции, реальные средства и производственные подключения не менялись.
