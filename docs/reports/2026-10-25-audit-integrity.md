# Приёмка A19 — независимая проверка целостности

25 октября 2026 года. Ветка feature/audit-integrity, [PR #19](https://github.com/Adopten123/digital-ruble-deals/pull/19). База main 090c620. Тестовый контур. Расчёты и ЭДО эмулируются.

## Результат и границы

Реализованы миграция 010, транзакционная боковая цепочка аудита и независимый Go CLI keygen / checkpoint / verify. Снимок охватывает 28 таблиц и реальные байты всех привязанных PDF. Эталон подписывается отдельным Ed25519-ключом, verify требует независимо закреплённые публичный ключ и canonical checkpoint_sha256. API / workers исключаются блокировкой; отсутствие доверенных данных не даёт MATCH. [Протокол / модель угроз](../INTEGRITY.md).

Это обнаружение расхождений относительно конкретного эталона, без определения виновника / исполнения работ или автоматического арбитража. Обычные изменения после эталона тоже дают MISMATCH. Приватный ключ, публичный ключ и последнее закрепление должны контролироваться отдельно от проверяемой БД. Защита от администратора всего хоста и изменений до первой точки не заявлена. В локальном показе ключи лежат в игнорируемом служебном каталоге одного ПК: это проверка механизма, не подтверждение организационной независимости хранения.

После последней правки переподключения выполнены targeted Go, сборка, настоящий restart PostgreSQL / CLI и focused UI. Полный Go race / 148 E2E / новый stopped-live CLI для окончательного коммита проверяет Linux CI; окончательные run IDs / merge фиксируются в PR. Наличие этой строки не означает заранее успешный результат CI.

Проверяющий не вызывает SQL-функции хеширования проверяемой БД. Тест реально заменяет integrity_event_hash_v1 функцией, возвращающей сохранённый ложный хеш, подтверждает её ложное совпадение SQL-запросом и получает CHAIN_BROKEN от Go. Полностью согласованная заново пересчитанная цепочка остаётся внутренне валидной, но отличается от внешнего эталона. Откат к старому валидному эталону может дать MATCH с ним: отдельный тест демонстрирует это ограничение; CLI отклоняет старый файл при закреплённом новом отпечатке.

## Сохранное обновление существующего стенда

Остановлен только проверенный учебный API на 18081, схема обновлена 009→010, повторены оба файла grants и bootstrap. Перед запуском worker сравнены число строк и MD5 отсортированного JSON всех **28 прежних таблиц**, кроме schema_migrations: все отпечатки совпали. Это сверка сохранности обновления, не криптографическое доказательство A19. Применённые 001–009 и пользовательские PDF не переписывались. Новый API возвращает stage=audit_integrity; это готовность схемы, а не отчёт MATCH.

Сквозные тесты создают собственные учебные организации / документы / проводки, не удаляют старые данные. Owner-атаки выполнялись только в случайных test_-схемах; реальные файлы менялись только в t.TempDir. Старый ручной сценарий и пользовательские исследовательские файлы не использовались для атак. Ключи и эталоны в Git / отчёт / CI-artifacts не включены.

## Найденные проблемы и исправления

При отмене блокирующего получения session lock соединение могло оставить запрос в очереди. Получение основной lease заменено на короткие неблокирующие попытки с отменой; неопределённое соединение уничтожается, а не возвращается в pool. Тест отмены / повторного запуска успешен.

Перезапуск БД снимает session locks. Одна удерживаемая lease без восстановления была недостаточна: API мог открывать новые соединения. Теперь AfterConnect каждого соединения serve получает общую блокировку до первого запроса. Это проверено принудительным завершением соединения, тремя повторными Go-прогонами и настоящим restart PostgreSQL с живым API. В CI тот же сценарий добавлен в CLI smoke.

Первый служебный smoke был запущен с неверным именем переменной адреса и получил ECONNREFUSED на 8080 до работы с данными. Повтор с BASE_URL=http://localhost:18080 прошёл. Неуспешный PowerShell readiness-probe после первого старта не считается PASS; готовность подтверждена независимым Node-запросом и setup полного E2E. Ошибки тестовой подготовки исправлены, требования приложения не ослаблялись.
